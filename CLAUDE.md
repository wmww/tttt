# tttt
tttt is a work-in-progress TypeScript reimplementation in C.

## Objective
The project's focus is performance, ideally beating the new typescript-go. But we need to fully support the TypeScript language first. That's what you're working on today.

The oracle is TypeScript 7.1 (`main` at a 7.1 nightly, plan 54; `thirdparty/ensure-typescript.sh`: tsgo's Go sources and native test suite in `thirdparty/typescript`, its CLI at `thirdparty/typescript/built/tsc`). The test suite, libs, probes (`filetest.sh`/`tscbaseline.sh`/`mutate.py`, through `scripts/tsgoprobe.sh`), the sweeps' tool (`tttt-oracle`, `test/oracle/README.md`) and every cached expectation are tsgo 7.1's.

Tests are the oracle, but not the true end goal. Special casing tests, or getting a few more tests to pass under an architecture that is fundamentally flawed doesn't help anyone. Keep the big picture in mind.

This is a massive project and I'm giving you and all the other agent sessions a lot of autonomy. Use it wisely.

## Agents directory
Keep notes for future agent sessions in `agents/`, including:
- `agents/vision.md` - high-level overview of the state of the project, concerns, risks and where you plan to take it.
- `agents/todo.md` - brief summary of the next few sessions, churns often, references plans rather than containing detailed per-session instructions.
- `agents/hacks.md` - contains a comprehensive list of hacks, workarounds and other suboptimal-but-working aspects of the code. Prefer function names over line numbers for stability. Add when writing a hack, or when discovering code that seems sus. Hacks don't need to be immediately addressed, they're meant for discovering and fixing antipatterns.
- `agents/triage.md` - a dumping ground for uninvestigated bugs, potential long-term problems, papercuts, ideas, and anything else an agent doesn't want to deal with at the moment, but a future agent should sort out.
- `agents/bugs/*.md` - reports of issues and problems without an active plan to solve them yet.
- `agents/plans/*.md` - detailed plans for future work.

`agents/` should be committed to git just like code. Create, edit and delete files in `agents/` freely. Remove files that are no longer relevant (eg solved bugs, completed plans) and clean up confusing and unimportant references to previous state.

## Session types
You are to work on this project highly autonomously over many sessions. To facilitate that, you are one of the following types of agents:

### Insights
You are a high level manager. Don't get bogged down in the details of any one problem or refactor. Review vision.md, todo.md, hacks.md and the git log, and keep the project on track. Be on the lookout for patterns spanning many past sessions. Is a particular area of the code base repeatedly more troublesome than expected? Are we accumulating tech debt? Does something *almost* work in a way that's tempting to keep charging forwards, but actually demands a significant refactor? Is the scope or focus of the project drifting from the true goal? These are the sorts of things you need to be thinking about and correcting for. Don't be afraid to make bold decisions.

Delegate to sub-agents or future sessions as needed. For example, instead of doing your own refactor, or even doing a detailed code investigation to write a refactor plan, you could instead write a simple plan that instructs another agent to investigate, make a decision, and write up the real refactor plan if needed. You might spend a lot of time in one session to get things right, or exit quickly if everything's going well. Your main deliverable is maintaining vision.md to the highest quality, and writing todo.md to map out the next 2-10 sessions (before a the next insights session). Always finish todo.md with a triage session.

Each insights session add an entry to a repo-toplevel file: report.md. This is for human consumption, so keep it brief and comprehendable (a 1-4 SHORT paragraphs). Explain what's happened since the last entry, giving a high-level overview of the state of the project, what direction it's going and any concerns you may have.

### Planning
You are to research, derisk and write up the specified plan(s). Be reasonably detailed, but leave things up to the execution agent if they truly depend on information we don't have yet. Include how to validate that the plan has been completed.

### Execution
You're given a plan file (or in some cases just a specified task) and you execute it. Deliverable might be a new feature, a perf improvement, a measurement, a dev tool or a refactor.

### Triage
You're in charge of draining triage.md and otherwise maintaining the repo. Validate and write up bugs, research and write plans, update todo.md based on new information, delete or consolidate old files, etc.

## Workflow
- **Ending your turn ends the session**: nothing wakes you up again. Never end a turn waiting on a background job; run long jobs (`findcrash.py`, `bench.sh`, full suites) in the foreground with a timeout, and commit before starting anything long.
- `todo.md` has a fixed number of sessions before the next insights session. Don't insert sessions ahead of it; new work goes into plans, triage.md, or after the insights entry, which the next insights session reorders.
- When you fix a divergence found outside tsc's suite (corpora, sweeps, a probe), add a cut-down repro to `test/cases/` (`scripts/owntests.sh` for its baselines) that fails without the fix.
- Commit at the end of every session. Commit messages should be a summary of what you did and what happened, generally a paragraph or two. Include doubts and things that went wrong, these will be helpful later.
- Don't use feature branches. If you change branch, always change back by end of session.
- There is no strict chain of command or scoping of agents. An insights agent may write some code, an execution agent may edit vision.md. The structure is just to keep everyone focused on what's usually most useful to them.
- Any agent may "fail", if that's best for the project. If half way through implementing a plan you discover the plan takes the wrong approach, cancel your implementation and report that rather than pushing through.
- Feel free to build tools and scripts, and share them with future agents if they're generally useful. The workflow of this project was originally optimized for humans, so the tooling might need adapting to be optimal for agents.
- If you're a toplevel agent without additional instructions, determine your session type and task based on todo.md. If it's empty/complete, congrats! You're an insights agent.
- Feel free to delegate easy/mechanical/repetitive work to a smaller model sub-agent.
- Disk is shared and filled up once (2026-10-14: a 50 GB Go build cache, now capped by `ensure-typescript.sh`). At session end `git worktree list` shows only the repo (every worktree's commits merged or deliberately dropped, said in the commit message) and your /tmp scratch (dumps, probe trees, `go-build*`) is deleted.
- Sub-agents running in parallel with you or each other must not experiment in the shared tree: give them a worktree (`git worktree add /tmp/wt-x HEAD`, then symlink the untracked `thirdparty/{typescript,typescript-gopath,go,corpora,sources}` into it). The symlinked corpora are shared: probes go elsewhere. Parallel agents must never `git stash` (shared by all worktrees) nor wait on `pgrep -f` patterns (they match each other's builds).
- Be conservative with Fable sub-agents, don't fan out to many of them.
- If you're using Anthropic models, Opus is the smallest model you should use for anything. If only Opus is available, ignore stuff about chosing a model.
- When you are unable to move forward or the project is 100% complete and as performant as its reasonably going to get, create a file `claude-stop` in the project loop to end the dev cycle
- You may edit this file (CLAUDE.md; AGENTS.md is a symlink to it), but keep it compact and meaningful. Favor other files which can be read as-needed for all but the most important content.
- Pull --rebase and push at the end of each session

## Development Scripts
You will use scripts to help you run tests, but some scripts and options are more useful to AI agents than others. All scripts live in `scripts/` (run them from the repo root: they `cd` there themselves), automatically compile the code in src before running tttt, and abort if there are any compile errors. The main scripts you will use are:

- `test/cases/tttt*.ts`: tttt's own regression tests (tsc-suite style headers), run by `scripts/fasttest.sh` with the suite against tsgo's baselines checked in at `test/baselines` (`scripts/owntests.sh [FILE...]` regenerates them)
- `scripts/fasttest.sh --summary`: Shows which new tests pass and which new tests fail, compared to the saved results (`test/baseline_results.ts`). **Save them with `scripts/fasttest.sh -s` before you commit** (`scripts/passcount.py` prints the totals of the saved file), or the next session's summary is polluted by yours
- `scripts/test.sh -f specificTestName -d`: Shows the detailed output of a specific failing test, runs under valgrind, so may fail with a useful message if there are memory errors.
- `scripts/test.sh -f specificTestName --sym`: Shows only symbols for a given test, flag can also be `--err` or `--typ`
- `scripts/filetest.sh path/to/file.ts -d`: Run a test on a file that is not part of TypeScript's existing test suite. This is useful for better understanding how both tttt and tsc work in a simplified case that may not otherwise be tested. You can create any typescript files you want and use this command on them. Prefix with `FAST=1` to use the release build without valgrind (seconds instead of a minute)
- A test file with `// @target: es5,es2015` (any boolean/enum option with several values) is one test per configuration, named `name(target=es5)` like tsc's baselines. `-f name` runs all configurations of it. Compiler options live in `CompilerOptions` (`src/compiler_options.h`), read through `compiler_options()`
- `-f` takes a regex that must match the whole test name (`-f '^async.*'`, not `-f async`), or `-f @names.txt` (one exact name per line; long regex alternations silently match nothing). If a full run gets OOM-killed or hangs, some newly reachable checker path is running away: bisect with `(ulimit -v 6000000; ./release/baseline_tests -f '^a.*')` per letter
- `scripts/failstats.py`: Runs the whole suite (~25s) and reports *why* tests fail in aggregate: checker `log_error`s, missing/spurious diagnostic codes, nearly-passing tests. `--syntax` lists the syntax shapes the parser wrongly rejects, `--code TS2322` lists the tests affected by a code, `-f regex` restricts it, `--jsx` to the tests with JSX. Use it to pick work that moves whole categories. Latest numbers are in `agents/measurements.md`
- `scripts/unimplemented_codes.sh`: After `scripts/failstats.py`, the missing diagnostic codes that `src/` never mentions (checks tttt doesn't have at all), with counts and messages
- tttt's CLI is a drop-in `tsc --noEmit`, and a drop-in `tsc` where the config only emits declarations (`emitDeclarationOnly`: it writes the `.d.ts` and `.d.ts.map` files, plan 64): tsc's output formats and exit codes, nothing else on stdout. **Tools running tttt on shared checkouts pass `--noEmit` with `-p` and `--no-write` with `-b`** (the `-b` corpora emit declarations). Scripts parse its `--pretty false` output with `scripts/tscformat.py`; `--keep-going` (check past gating errors) is tttt's own, for tools that want types anyway (expecttypes, checkerdiff); the diagnostic oracles compare against tsc's CLI and run without it
- `scripts/realworld.py`: Runs tttt on a real project (TypeScript 6's own `src/compiler`, 193k lines, the `TypeScript6` corpus; through its tsconfig) and groups what it reports by code and by offending token, then compares it with tsc's cached diagnostics there (`test/corpora.tsc.jsonl`, `--tsc` regenerates a corpus' entry): every spurious or missing one is a tttt bug; this is the second oracle next to the test suite. `--corpus type-fest|valibot|react|nest|webpack|zod|xstate|drizzle|vue|effect|vscode|excalidraw|tanstack-router|tsc-src|typescript-eslint` checks the other pinned corpora (vscode: 1.39M lines, the scale one) (`thirdparty/ensure-corpora.sh`; the last two with `-b` on a solution config); `zod-root` and `webpack` aren't clean under tsc either
- `scripts/clidiff.py [--corpora] [-f regex] [-k KIND] [-v] [--last]`: tttt as a drop-in tsc (plan 53): `tttt -p P --noEmit --pretty false`'s whole stdout (message text, elaboration chains) and exit code against tsc's, cached (`text` in the source sweep's and the corpora's tsc caches, `--tsc` regenerates the stale ones), on every corpus and source sweep project (~5 min; `--corpora` ~1.5 min); `text` mismatches bucketed by first differing part (header type printing, chain). `--live [--pretty] [--sample N]` runs tsc now; `--emit`: the `emitDeclarationOnly` projects as they are, both CLIs emitting in a bwrap overlay sandbox, the written trees compared too
- `scripts/sweep.py [-f regex]`: the breadth sweep (plan 44): tttt on every DefinitelyTyped package (~8600 small projects incl. the versioned `types/X/vN`, ~2-5 min) against tsc's cached diagnostics (`test/sweep/`), crashes first, then mismatches ranked by root cause across packages (`-k KEY` instances, `--names VERDICT`, `--last` reuses the run). The third oracle: run it next to the corpora after checker changes
- `scripts/sourcesweep.py [-f regex]`: the source sweep (plan 52): tttt on every `tsconfig*.json` (bases others extend aside) of ~150 real repositories (`test/sourcesweep/repos.txt`, installed by `thirdparty/ensure-sources.sh` into `thirdparty/sources`, symlink it in worktrees) against tsc's cached diagnostics (~5 min; `--sample 4` a fixed quarter), crashes first, then mismatches ranked by root cause across repos (`-k KEY`, `-k=-TS6305` for a missing one, `--names VERDICT`, `--last`, `--tsc-new` after adding repos). The fourth oracle: real application and library code with real configs. `--build`: every repo's solution roots (configs with `references`), tsgo `-b --force` sandboxed against `tttt -b` (~3 min; its own cache)
- `scripts/expecttypes.py [-f regex] [-k KIND]`: the types oracle at breadth (plan 44 stage 3 item 2): DefinitelyTyped's 69k `// $ExpectType` assertions, tttt's printed type of each asserted expression (`tttt --expect-types SPANS`) against tsc's (cached), mismatches bucketed by kind (union order, we-any, ...); ~30 s. Run it next to the sweep after checker or printer changes. `scripts/expectprobe.py DIR [--reduce FILE TEXT]` runs one cut-down project (a tsconfig listing the package's .d.ts by absolute path plus a test file of your own) through both sides and deletes chunks of FILE while TEXT stays among the mismatches
- `scripts/dtsstats.py [-f regex] [-k BUCKET] [--names] [--last] [--js]`: the suite's `dts` component (declaration emit, plan 64; `baseline_tests --dts` shows its diffs): failing tests bucketed by first differing line; `--js` the tests with JavaScript inputs (`baseline_tests --dts-js`; `--dts` shows the others')
- `scripts/dtsdiff.py [-f regex] [-k BUCKET] [--show PROJECT [FILE]]`: declaration emit at breadth (plan 64): tsgo's `.d.ts` and `.d.ts.map` files (hashes cached in `test/dts/`, `--tsc` regenerates; its texts kept in /tmp) against what `tttt -p` writes (both in a bwrap sandbox, outputs redirected to /tmp) on the `-p` corpora and every declaration-emitting source sweep project, byte for byte, mismatches bucketed by first differing line or mapping (`--names`, `--sample N`, `--last`); `--tsc-single` caches `tsgo --singleThreaded`'s hashes for the last run's mismatching projects, whose files tttt writes like it are then counted apart (tsgo's own checker split); `scripts/mapshow.py [-s] A.map [B.map]` decodes and compares maps
- `scripts/flagflip.py [-c corpus] [-F flag] [--cells] [-k KEY]`: missing diagnostics on real code (plan 46): every `-p` corpus rechecked with a flag tsc then reports thousands of diagnostics under (noUncheckedIndexedAccess, exactOptionalPropertyTypes, the non-strict modes, ...), against tsc's output cached in `test/flagflip` (`--tsc` regenerates stale cells), ranked by root cause (`TSa->TSb`: tsc's code a reported as b). Run it next to the corpora after checker changes (~80 s)
- `scripts/mutate.py [-n N] [--seed S]`: mutation testing (plan 46 stage 2): one small mutation (operator in the name) to each of N passing single-file suite tests, tsc's baselines cached in /tmp/mutate, mismatches bucketed by first difference (`-k KEY` lists, `--show NAME` diffs one, `--recheck` reruns only tttt). Finds missing checks the clean oracles can't; ~90 s for 8000 mutants
- `scripts/scenarios.py [-f regex] [-v]`: project references and `-b` (plan 41): replays the first command of tsc's own tsbuild/tsc project-reference baselines (a virtual tree written to /tmp) and compares (file, line, code); known divergences are skipped with a reason. `tttt -b [PROJECT...]` checks a solution like `tsc -b` (referenced projects are read from their sources, `--builders J` of them at once, output in build order), `scripts/realworld.py --corpus tsc-src` runs it on TypeScript's `src`
- `scripts/kdiff.py [-k K] [--dt] [-f regex]`: tttt's output at `--checkers 1` against K (default 16) on the source sweep or DT: tsgo's output is checker-count independent (nearly: sequelize/packages/core's TS7022 differs in tsgo too), so a project it lists is almost always a tttt bug (plan 62). The sweeps run tttt at its default checker count; `-k 1 -m 0` compares against a fresh checker per file (`--checker-memory 0`: checker recycling, plan 67, the CLI's default `--checker-memory 256` MB)
- `scripts/perfsweep.py [-f regex] [-j N] [--sample N] [--corpora] [--last]`: perf at breadth: tttt `--checkers 1` against tsgo `--singleThreaded --extendedDiagnostics` on every source sweep project tsgo checks (tsgo's side cached in `test/perfsweep/`, measured cold: tsc --noEmit reads and writes incremental projects' .tsbuildinfo otherwise): check-time, types and RSS ratio distributions, projects ranked by **types ratio** (machine-independent: above ~1.5 is a missing cache or a runaway) and by time. ~1.5 min at `-j 4`, times inflated under load; `--defaults` also times tttt at its default threads and checkers against its K1 run (recycle thrash)
- `scripts/scaleprobe.py [-k KIND] [-n N] [--emit]`: synthetic single declarations/blocks of N members/statements/elements (object literals, classes, interfaces, unions, `&&` chains...) timed against tsgo: finds quadratic paths no corpus is big enough to show (~3 min; `--emit` with declaration emit and maps)
- `scripts/oracles.py [--quick]`: every oracle above (suite lost/gained against HEAD, every corpus, sweep, `$ExpectType`, flagflip, perfsweep, clidiff, dtsdiff...), one line each (~8 min, `--quick` suite, corpora and their clidiff ~2 min); saves the suite's results like `-s`
- `scripts/resultdiff.py [--lost|--gained] [--names]`: After `scripts/fasttest.sh -s`, which test components changed compared to git HEAD's saved results (plain text, unlike the coloured `--summary`). `scripts/failstats.py --code X` reuses the last full `scripts/failstats.py` run: rerun that first
- `scripts/displaydiff.py`: After `scripts/failstats.py`, why tests that pass their errors fail the types component (`--symbols`: the symbols component): mismatching lines bucketed by mechanism (union order, `typeof` reuse, `import()` qualification, `T_1` renaming, class expressions...) with examples (`-k kind`, `-f regex`, `--names`), and how many tests each kind alone fails (the ranking plan 21 uses). `--fine` splits the catch-alls (`other`, `we-any`...) into shape/annotated-node and ranks tests by their first differing line (the queue for silent type differences)
- `scripts/errtextdiff.py`: After `scripts/failstats.py`, the tests with the right codes at the right positions but other text (plan 34): the first differing part of each diagnostic (header type printing, elaboration chain, related info, underline) bucketed, with tests fixed by one kind (`-k kind` prefix, `--names`, `--coarse`)
- `scripts/jsstats.py`: After `scripts/failstats.py`, the JS tests (bugs/js.md): how many pass, and the failing ones by the features they need (CommonJS, expandos, JSDoc tags, JS syntax diagnostics...), with cumulative "could pass" bounds; `scripts/jsstats.py 1cjs,3jsdoc` lists the tests with exactly those categories
- `scripts/syntaxstats.py`: After `scripts/failstats.py`, the TS tests whose *parser* diagnostics differ from tsc's (plan 27), by where they diverge (A-E, M) and by mechanism cluster (recovery, permissive grammar, lexical); `--list CLUSTER` shows first differing errors with source lines, `--names CLUSTER` just names
- Don't `pkill -f <pattern>` in the same command line that contains the pattern (it kills your own shell); find the PID with `pgrep` first
- `scripts/findcrash.py [prefix]`: When the release suite dies (crash, hang, memory runaway: it runs each probe under `ulimit -v` and `timeout`), bisects on test name prefixes and prints the tests responsible
- `TTTT_DEBUG_RELATE=1` logs every top-level type relation query (source, target, ids, result), handy with `scripts/run.sh` or `./release/tttt` on a small file
- `TTTT_DEBUG_RELATE_NESTED=1` logs every nested pair too (depth, result, whether it made a variance measurement unreliable), printed when each finishes; `TTTT_DUMP_VARIANCES=1` prints measured variances (1 co, 2 contra, 3 bi, 4 independent, +8 unreliable, +16 unmeasurable)
- `scripts/variancetrace.py PROJECT [--block NAME]`: variance measurements against an instrumented tsgo (built once into /tmp, the shared checkout untouched): which stored variances differ, and with `--block` both sides' comparisons inside NAME's measurement (`TTTT_DEBUG_VARIANCE=1` is tttt's side of the log)
- `TTTT_RESOLVE_TIMES=1` times name resolution's steps (declare, link, the walk...), `TTTT_LOAD_POOL_STATS=1` the load pool's
- `TTTT_FILE_TIMES=1` prints each checked file's check time (and its unused/declaration pass) on stderr: `sort -k3 -n -r` finds the file a slow project spends its time in
- Deferred function bodies (plan 78, documentation.md "Deferred bodies"): the CLI parses and walks outermost TypeScript function bodies only when a checker needs them (`--no-defer-bodies`: up front), the harness too (`baseline_tests --no-defer-bodies`: up front; `scripts/oracles.py` runs both); `TTTT_DEFER_STATS=1` prints what was deferred, materialized and rerun
- `TTTT_CHECK_ONLY=substring[,substring...]` checks only the files whose path contains one, in a fresh checker (the rest of the program loaded): reproduces at one checker an output that depends on which file a checker saw first (`scripts/kdiff.py`)
- `TTTT_DEBUG_CONTAINERS=1` prints getSymbolChain's sorted candidate containers (module, specifier) and which one names each symbol: why an `import("...")` names one module rather than another
- `TTTT_DEBUG_CYCLE=1` prints the chain of declarations/expressions whenever a declaration's type evaluation reaches itself (where TS7022-style circularity comes from)
- `TTTT_ORDER_STATS=1` counts union-order ties decided by type ids (by class); `TTTT_ORDER_SEED=N` permutes them, so diffing an oracle's output shows whether id order is observable (plan 86's gate)
- `TTTT_DECLARATION_DIAGNOSTICS=1` keeps the declaration diagnostics (TS4xxx/TS9xxx, plan 40) the CLI drops with noEmit when there are other errors (to audit drizzle); `TTTT_DEBUG_DECLARATION_TYPES=1` prints every inferred type the declaration walk prints
- `scripts/pgobuild.sh`: the shipped build, `pgo/tttt` (LTO + PGO, plan 86 stage 1), retrained (~3 min) only when the sources changed. `bench.sh`, `instrcount.sh` and `perfsweep.py` measure it; `release/` (plain -O3) stays the edit-test build every other script uses
- `scripts/instrcount.sh [--bin BUILD] [--save] [corpus...]`: instructions per corpus (single-threaded, the stable perf number to record at session end; `--bin` an old build to bisect a regression). Each is printed against `test/instrcount.txt` and a change over 2% is flagged: **investigate a flagged rise before committing** (a +50% on drizzle went unnoticed for two sessions); `--save` updates the file
- `scripts/bench.sh [--bun PATH]`: Perf benchmark against tsgo (and Bun's `bun check`, measurements.md says how to get it) (wall time, peak RSS, tttt phase split). `scripts/arenasites.sh -p DIR`: binder and checker arena bytes and types by allocating call site; `scripts/memtrack.sh -p DIR`: the malloc heap (the AST) per phase by allocating function, with its share of zero words. `scripts/survivors.sh -m MB -p DIR`: at each checker recycle, what declaration-level roots reach in the arena (plan 79's census, measurements.md) Rerun and update `agents/measurements.md` after perf-relevant changes. `tttt --time` prints each phase's time and resident set, and the checker's arena size and type count. Arena chunks get huge pages only while the system has free 2 MB blocks for them (`huge_pages_take()`; `TTTT_HUGEPAGES=1`/`0` forces)
- `scripts/checkerdiff.py [-k K] [corpus...]`: tttt's diagnostics with `--checkers K` against one checker on the corpora (byte-identical: tsgo's output doesn't depend on K, plan 62) and K twice byte-identical. `baseline_tests --checkers K --dump DIR` does the same for the suite (diff against a K=1 dump). `scripts/threadcheck.sh [corpus...]`: the corpora's output must be byte-identical at `--threads 1` and 4 (threads default to the cores, `--checkers` to one per thread but at most one per 64 KB of checked source; pass `--checkers 1` to compare with the suite's one checker)
- `scripts/tscbaseline.sh path/to/file.ts [types|symbols|errors.txt]`: Prints what tsc (tsgo 7.1) says about a file (the expected side of `scripts/filetest.sh`), handy when writing probes. `scripts/tsgoprobe.sh DIR` baselines a whole directory of test files at once (~40 ms each); `scripts/tsctypeat.sh TSCONFIG FILE LINE NAME` prints tsgo's type of an identifier inside a real project
- `scripts/run.sh path/to/file.ts`: Runs the typechecker as a user would. This produces type errors, but not the detailed information of the tests. It also doesn't run tsc against the file, so generally the test scripts are more useful

Tests are split into three test components, errors, symbols and types. A test component passes if tttt is able to annotate the input code the exact same ways as tsc. In the test output ` - ` marks a passing test component and `ERR`/`SYM`/`TYP` marks a failing one. In the diffs you get from failing tests, removed lines are lines tttt erroneously produced, and added lines are lines tttt failed to produce.

## Code Guidelines
tttt uses [cleat](https://codeberg.org/sphi/cleat) as its standard library, vendored at [thirdparty/cleat](thirdparty/cleat/). Cleat provides containers, strings, error handling, logging, filesystem access and subprocesses, and comes with its own vendored copy of the [STC](https://github.com/stclib/STC) container library. Cleat's own documentation is in [thirdparty/cleat/docs](thirdparty/cleat/docs/) and STC's is in [thirdparty/cleat/stc/docs](thirdparty/cleat/stc/docs/).

`src/prelude.h` pulls in `cleat.h` and is included directly or indirectly in all files. Between them you get, among other things:
- `#define my me->` (from cleat): This allows writing `my foo.bar` instead of `me->foo.bar` in functions that take a pointer argument `me`. This is the preferred style for method-like functions (`me`/`my` is used instead of `this` or `self`)
- `panic("message ", str, " ", num);` (from cleat): Immediately aborts the program with a message to stderr, if running under Valgrind a stack trace is printed to stderr as well, and the source location is a clickable link. `panic_if(condition, ...)` is the conditional form
- `check(condition)` (from cleat): Panics if condition is false, used for sanity checks
- `impossible` (from cleat): Panics if hit, used in places control flow should never hit
- `log_error("message ", str, " ", num)` (from cleat): Used for recoverable errors that do not require aborting, but should nonetheless never happen once the program is complete. `log_warn()`/`log_info()`/`log_debug()` are also available for print debugging, but note that `logger_config.threshold` hides anything below info by default

All of these take a [display](thirdparty/cleat/docs/display.md) sequence rather than a format string.

The project was originally a cleanroom implementation (I didn't read tsc other than tests). that rule is no longer in play but I still recommend paying more attention to what tsc observably does than how it does it.

## Project Structure
Feel free to change code in `src/` as much as you want, you can always revert it with git. Do not change code in `thirdparty/`, but you can look at it or anything you can find to understand what's going on; if a vendored library genuinely needs a fix, add a `thirdparty/*patch.txt` alongside the existing ones so `thirdparty/refresh.sh` reapplies it after a re-download. In particular `thirdparty/typescript/tsc/internal` (tsgo's Go sources) may be enlightening, as this is what we're reimplementing.

Refer to `documentation.md` for a description of the overall architecture of the C code base in `src/`.

Good luck, and have fun!
