# tttt Documentation

"plan N" (and "plan N stage K") here, in code comments and in scripts is a historical tag: the plans were deleted on 2026-10-22 and resolve to `git show af936072c:agents/plans/` (design knowledge still needed is in `agents/notes/`).

## Programs
The repository contains three programs.

### tttt
The actual typechecker, drop-in replacement for tsc. See `build/tttt --help` for usage.

Can be compiled and run with `scripts/run.sh`. This makes a debug build and runs it under Valgrind, so won't be fast.

What the CLI reports follows tsc's `emitFilesAndReportErrors` (`check_files()`, `diagnostic_kind()` in main.c): the
config's parsing diagnostics (its JSON syntax, a missing `extends`) always; parse errors hide everything else; options
and global diagnostics (no file, or in the config) hide the semantic ones (everything else located in a source file);
`--keep-going` reports everything. Message text names files by absolute path, like tsc's CLI
(`source_file_set_message_cwd()`); locations are relative to the working directory.

**What the CLI emits** (plan 64 stage 4): it is `tsc --noEmit` unless the options only emit declarations
(`emitDeclarationOnly` with `declaration` or `composite`, `noEmit` not set): `apply_compiler_options()` sets `noEmit`
otherwise (`Options.implicit_no_emit`, not with `-b` or `--noEmit` on the command line). Emitting, `check_files()` writes
each file's `SourceFile.declaration_output` to its `declaration_output_path` (`write_declarations()`): nothing after any
diagnostic with noEmitOnError, nothing over a path TS5055/TS5056 blocked (`program_emit_blocked()`), TS5033 for a failed
write, `--listEmittedFiles`; JavaScript sources' declarations too (plan 64 stage 6). `-b` does the same per project. JavaScript is never emitted, and no `.tsbuildinfo` is written (a later `tsc -b` rebuilds
everything). `--no-write` emits but writes nothing: **every oracle script passes `--noEmit` with `-p` and `--no-write`
with `-b`** (the two `-b` corpora are `emitDeclarationOnly`); a new tool must too, or it writes into shared checkouts.
`--version` prints `TTTT_TYPESCRIPT_VERSION` (main.c), what the pinned tsgo prints: bump it with the oracle.

Completely written in C. Code lives in [src](src/). The only dependency is [cleat](https://codeberg.org/sphi/cleat), an MIT-licensed standard library for C which comes with its own vendored copy of the STC container library (no relation to the swc-related project of the same name). It's included in this repository under [thirdparty/cleat](thirdparty/cleat/), and automatically compiled by the build system. `thirdparty/refresh.sh` re-downloads it at the pinned commit.

### baseline_tests
Runs tttt against TypeScript's official test suite. See `build/baseline_tests --help` for usage.

Can be compiled and run with `scripts/test.sh` (debug build, under Valgrind, takes minutes) or `scripts/fasttest.sh` (release build, not under Valgrind, takes seconds). Features like regex filtering and displaying diffs are supported, see `scripts/test.sh --help` for details.

Like tsc's harness, a multi-file test whose last file mentions `require(` or `reference path` (or that sets `@noImplicitReferences`) has that file as its only root: the others are part of the program only if something refers to them, and the root comes first in the baselines.

Like tsc's harness, tsc's `tests/lib` folder is at `/.lib` in the mock filesystem (copied in only for tests that mention `/.lib/` or set `@libFiles`): `/// <reference path="/.lib/react16.d.ts" />` finds it, and `@libFiles: react.d.ts,lib.d.ts` makes those files roots after the test's own (a `lib.*.d.ts` among them is shown as `Decl(lib.d.ts, --, --)` and, saying `no-default-lib`, replaces the default lib). The types and symbols baselines go through tsc's `removeTestPathPrefixes` (`/.src/`, `/.lib/`, `/.ts/` disappear).

**The suite** is TypeScript 7.1's native tree (plan 54): `thirdparty/typescript/tsc/testdata/tests/cases/{compiler,conformance}`, baselines in `testdata/baselines/reference/{compiler,conformance}` beside `tests` (`--dir` takes the `tests` directory; `scripts/suite.py` has the paths for the scripts). Like tsgo's runner, configurations that set an option 7.0 removed (`tsgo_skips_configuration()`: module amd/umd/system/none, moduleResolution node10/classic, esModuleInterop/allowSyntheticDefaultImports/alwaysStrict false, baseUrl, outFile, target es5) and the tests in its `skippedTests` (`tsgo_skipped_tests`) aren't tests: not run, not counted, not saved. tsgo's `.types` have no `^^^` underline lines; an `any` still prints its intrinsic name when the test has no errors (`LineNumberedStr.intrinsic_at`). **tttt's own tests** (regressions found on real projects that tsc's suite doesn't cover) are `test/cases/tttt*.ts(x)`, tsc-suite style, with tsgo's baselines checked in flat in `test/baselines` (`scripts/owntests.sh [FILE...]` regenerates them through `scripts/tsgoprobe.sh`, rewriting the header path; an empty `NAME.noerrors` where tsgo reports no errors, and an own test with neither it nor `NAME.errors.txt` doesn't run, so a botched regeneration shows). baseline_tests collects them after the suite (`--own-tests DIR`, default `test`; off with `--dir` unless given, so `filetest.sh` and `mutate.py` don't see them) and `load_own_tests()` rejects a name without the `tttt` prefix, so they can't collide with tsgo's; `baseline_test_result_run()` finds their baselines by the source path, `/.lib` is mounted from the suite's `tests/lib`, and `scripts/suite.py` knows them as kind `tttt`. They count in `baseline_results.ts` like any test. The libs (`thirdparty/lib`) are tsgo's `internal/bundled/libs`, the lib name tables are generated from its `LibMap` (`src/lib_names.py`).

**The other oracles' tools run tsgo** (plan 54 stage 2): the CLI (`thirdparty/typescript/built/tsc`: clidiff, flagflip) and two tools of ours compiled inside tsgo's module from [test/oracle](test/oracle/README.md) with `go build -overlay`: the probe (`scripts/tsgoprobe.sh`: tsgo's test runner on arbitrary files, for `tscbaseline.sh`, `filetest.sh`, `mutate.py`, diffapp) and `tttt-oracle` (per-project diagnostics with `tsc -p P --noEmit` semantics and `$ExpectType` types, for the sweeps). **The cached oracles** (`test/sweep/`, `test/flagflip/`, `test/sourcesweep/`, `test/corpora.tsc.jsonl`) are tsgo 7.1's output through the tools above (plan 54 stage 3), each script's `--tsc` regenerates its cache after a pin moves. `scripts/tsctypeat.sh` asks tsgo for an identifier's type inside a project. The generated C tables come from tsgo's Go sources too: `src/lib_features.py` (getFeatureMap), `src/unicode_identifiers.py`, `src/regex_tables.py`, `src/lib_names.py`. TypeScript 6's sources (commit `4d4f005c`, the previous oracle) are the `TypeScript6` corpus, not an oracle.

Deliberate simplifications of the harness: `apply_setting` ignores emit-only options (`@baselineFile`, `@fullEmitPaths`) and bad values (tsc's harness refuses those tests); `mount_test_lib_folder` copies `tests/lib` per test and `baseline_test_cache_get_program_with_libs` keeps one lib `Program` per lib list, never evicted; `@noTypesAndSymbols` counts symbols and types as passed. `engine.c` (which reads `test/baseline_results.ts`) has no let/const/var distinction, drops array property assignments and `value_loose_eq` stringifies; `failstats.py`'s `line_ratio` is multiset overlap, not a diff. When bisecting, commits f3b836b..f899e4e don't compile (fixed by 7f2a7fa).

The tests target includes most `tttt` code, as well as additional C code in [src/test](src/test/).

### diffapp
A graphical app that allows you to edit TypeScript code and see tsc's and tttt's test output for that code in real time. It watches for changes to tttt's source code, and recompiles and re-runs tttt on save.

Generally run via `scripts/diffapp.sh`. A test name or source file can be specified. If there's already a running instance the script will send the given test to that instance.

It's a nodejs web app with an html/css/js frontend in [test/diffapp](test/diffapp/). It's intended to run locally (basically uses the browser as a GUI toolkit only). The tttt integration lives in [src/test/diffapp_runner.c](src/test/diffapp_runner.c).

## Architecture
To keep development fast, LoC down, Tess sane and (in specific cases) tttt fast, we do things the most straightforward way wherever possible.

### AST
At the core of tttt is a TypeScript AST (Abstract Syntax Tree). This is a data structure that maps to parsed source code, and on which the typechecker runs. AST nodes are:
- `Block` - sequence of statements, often surrounded by `{` `}`s
- `Statement` - chunk of code that does not result in a value, often each on their own line or separated by `;`
- `Binding` - assignments and function parameter lists use bindings. They are often simply identifier names, but can be more complicated in the case of destructuring
- `Expr` - nestable expression, such as a function call or value literal
- `TypeNode` - the *syntax* of a type, as written (functions are named `type_*()`, tags `TYPE_*`). The checker's semantic types are a different thing, `Ty`, see "The type core" below

This list is not exhaustive as there are other structs owned by these. Each of these structs has it's own `.h` and `.c` files. Look through them for more details.

There is no AST node struct or interface (`ast_walk.h` is a read-only walk over every expression under a statement or expression, like tsc's forEachChild recursion, for checks that search a subtree). The AST is simply a *concept* that includes these structs, and is relevant for reasoning about the architecture.

### Span
A span is a reference to a section of source code, often used for error messages. Spans don't own anything, and don't need to be dropped. Identifier names are generally stores as spans. A name written with unicode escapes (`\u0061`) is keyed by its value: symbol tables, `checker_atom()` and `name_equals()` go through `name_cooked()` (`span.h`), which decodes views of a file's text (a memchr for `\` on everything else); what's printed stays the raw text. A span's file is an index into the process-wide `span_files` table (span.c, mmapped chunks), which never shrinks or reuses an index (a dropped file's entry is null); `source_file_id()` reads SourceFile's first word since span.h only sees the incomplete type. Expr's parenthesis offsets are 24-bit (`expr_set_outer_span()` panics past 16 MB of parentheses and trivia).

### Display
tttt has its own rendering pass for AST nodes in [src/display.c](src/display.c), driven by a `Display` struct (`display_type()`, `display_expr()`, ...). It stays separate from [cleat's display system](thirdparty/cleat/docs/display.md) because it's on the typechecker's hot path (every failed type comparison renders both types into a message) and because it has rendering modes cleat knows nothing about: `debug` (the developer-facing tree), `brief` (the same, truncated) and `parsed`.

The two systems are bridged in [src/display.h](src/display.h). `declare_ast_display()`/`impl_ast_display()` generate a cleat display function per AST node, so `Span`, `TypeNode const*`, `Expr const*`, `Error const*` and friends are all in `DISPLAYABLES`, and so is `Ty const*` (a semantic type, printed the way tsc prints it in messages) and can be passed straight to `println()`, `cstr_d()`, `panic()`, `log_error()`, `error_ctx_error_d()` and so on. A plain sequence gets the TypeScript-diagnostic form, `debug_d(x)` gets the developer form and `brief_d(type)` gets the truncated one.

Everything that isn't an AST node goes through cleat's display system directly; `src/` has no `printf`-style format strings left apart from JavaScript's number-to-string precision in `value.c`.

### Parser
The parser (including a minimal custom parsing framework) lives in `parser.c`. We do not compile grammars, combinate or tokenize. We simply take a const char* and use it to build an AST. Like real men.

See dedicated section below for details.

### Program
The `Program` struct owns the source code buffers and ASTs of all loaded files, manages imports, etc.

### CompilerOptions
`CompilerOptions` ([src/compiler_options.h](src/compiler_options.h)) is what tsc calls the same: every boolean option (one X-macro list, with which ones belong to the `strict` family), `target`, `module`, `moduleResolution`, `jsx`, `moduleDetection` and `lib`. `compiler_options_set(options, "strictNullChecks", "false")` takes names and values as they're written in a tsconfig, on the command line (`tttt --target es2020 --strictNullChecks false`) or in a test's `// @target: es2020`; `compiler_options_resolve()` then applies tsc's dependent defaults (`strict` to its family, `target` from a node `module`, `module` from `target`, `moduleResolution` from `module`, `useDefineForClassFields` from `target`...), so every field holds the effective value. The defaults are TypeScript 6.0's (plan 48), the CLI's too: `strict` and `alwaysStrict` true, `target` es2025 (es3 counts as unset), `moduleResolution` bundler unless `module` is node16/node18/node20/nodenext (or none/amd/umd/system: classic), `esModuleInterop`, `allowSyntheticDefaultImports` and `noUncheckedSideEffectImports` true, `types` empty. The options 6.0 deprecates (es5, amd/umd/system/none, node10/classic, baseUrl, outFile, downlevelIteration, esModuleInterop false...) still work, with TS5107/TS5101 unless `ignoreDeprecations: "6.0"` (~1950 suite baselines carry those diagnostics); dropping them waits for a retarget to a 7.x oracle. `moduleDetection` is applied when a file is loaded (`program_add_source_idempotent()`): besides imports and exports, `force` makes every non-declaration file a module and `auto` (the default) does for `import.meta`, `.mts`/`.cts`/`.mjs`/`.cjs`, an ES module package format, and JSX under react-jsx. `compiler_options_lib_files()` gives the standard library files to load: the `lib` list, else the default library of the target (`lib.d.ts`, `lib.es6.d.ts`, `lib.es2016.full.d.ts`...).

Each `Program` owns one (`program_options()`, change it before loading files). Code that parses, resolves names or checks reads the current program's through the thread-local `compiler_options()`, which `program.c` sets around each phase (and its load pool and checker threads for themselves). Most options are parsed but not acted on yet. The resolution options (`baseUrl`, `paths` with the directory they are relative to, `rootDirs`, `typeRoots`, `types`, `moduleSuffixes`, `customConditions`, `config_dir`) are strings and `StrList`s as written; `module_resolution.c` makes them absolute.

### Test configurations
A tsc test whose directives give several values for an option (`// @target: es5,es2015`, `// @strict: *`, `// @module: *,-amd`) is several tests, each with baselines named `name(option=value,other=value)`. `baseline_test_configurations()` (`src/test/baseline_test_case.c`) follows tsc's `getFileBasedTestConfigurations()`: only boolean and enum options vary (a comma in `@lib` or `@types` is a list), `*` means every value of the option, `-x` excludes one, spellings of the same value (`es6`/`es2015`) collapse, option names are sorted. The suite holds one `BaselineTestResult` per configuration; `-f someTest` matches all configurations of a test, `-f 'someTest\(target=es5\)'` one. Tests with `// @noTypesAndSymbols: true` have no `.types`/`.symbols` baselines and are compared on errors alone. The **dts** component (plan 64) is the declaration files of a test's `.js` baseline (the sections after the input files and the JavaScript outputs, before a `DtsFileErrors` section), compared per file by output name with tttt's `SourceFile.declaration_output`, in program order (tsgo's emit order), by output name (the base name of `SourceFile.declaration_output_path`, the path without the test path prefixes with `@fullEmitPaths`); tests with JavaScript inputs count too, also on their own line (`--dts-js` shows their diffs, `--dts` the others'). A test with the component passes only if it passes too (`dts: true/false` in `baseline_results.ts` only for tests that have it). tttt's own tests keep their `.js` baseline (the dts component) when they set `@declaration` or `@composite`.

### Symbols, tables, scopes (the binder, `scope.h`/`scope.c`)
The model is tsc's, because the symbols baseline, the merging rules and the diagnostics encode it:
- A `Symbol` has tsc's `SymbolFlags` (what it *means*: value, type, namespace, alias), its `parent` container (set for exports only, like tsc), every declaration that contributed to it as a `SymbolDecl { kind, flags, node, name, full }` (the AST node: `Binding`, `FunctionImpl`, `ClassDecl`, `InterfaceDecl`, `EnumDecl`, `EnumCase`, `TypeDecl`, `GenericItem`, `InferredType`, mapped key, `NamespaceDecl`, `PortItem`, `export default` expression, builtin) and, for namespaces, enums and modules, one `exports` table **shared by all declaration blocks**. Symbols, tables and scopes live in the arenas of the program's `Binder` (scopes and their `ScopeRare` in a scope arena of their own, so `scope_release()` can pop walk-only scopes) and are never copied or freed individually; what only aliases and modules need is in side structs (`SymbolAlias`, `SymbolModule`), other rare fields in `SymbolRare` (`symbol_rare()`).
- **Merging is `declare_symbol(table, name, includes, excludes)`** with tsc's `*Excludes` masks verbatim: `var`+`var`, function+namespace, class+interface, enum+enum, interface+anything that isn't a type, alias+anything that isn't an alias merge; anything else is TS2300 / TS2451 (block scoped) / TS2567 (enums) on every declaration of both sides, and the newcomer gets a detached symbol. Across files (the globals, an ambient module's or a global namespace's exports) tsc merges a file's declarations of a name as one symbol: a conflict there takes the file's earlier declarations of the name out of the other files' symbol into one of the file's own, which its later ones join (`declare_file_conflict()`, `SymbolRare.file_conflicts`), and `binder_link()` reports both sides whole (`report_file_conflict()`: one code, TS2649 into a namespace). Builtin types are symbols in tttt's globals (not in tsc's), so a declaration named like one (`class number`) gets a detached symbol too. Side rules (TS2434, TS2440, duplicate type parameters) are checks next to it.
- A `SymbolTable` is insertion ordered (namespace members come out in declaration order), scanned linearly up to 8 entries and indexed beyond, keyed by views into the source, and may overlay a read-only `parent` table: a test program sees the globals of the cached lib program without copying them, and adding to a lib symbol clones it into the overlay first (`clone_parent_symbol`). Nothing is written to the frozen original; references inside the lib AST still point at it, so the checker maps every symbol it is handed through `binder_redirect()` (`Binder.overlays`, only consulted by programs that have overlays) and lib-internal uses see the program's additions.
- A `Scope` is `{ parent, kind, locals, container }` and **persists**: the file scope is on the `SourceFile`, a namespace block's on its `NamespaceDecl`; function/block/type-parameter scopes are made by the resolve walk (nothing keeps a pointer to those; every scope knows the function it is in, `Scope.function`, and during the walk the flow builder of its container, `Scope.flow`). Declarations made in a module/namespace/enum scope go to the container's `exports` when exported (or when the scope is an ambient *export context*), to `locals` otherwise; scripts and `declare global` declare into `Binder.globals`. `var`s hoist: `block_add_names()` of a function/module/namespace/static-block scope also runs `statement_hoist_names()`, a statement-only walk that declares the `var`s of nested blocks, which those blocks then skip. Scope chains are shorter than the AST's nesting: blocks that are `if` branches, loop bodies, `switch`, `try`... get no block scope of their own (`branch_names_scope()`), and an ambient `declare` declaration gets no `scope_new_self()` scope unless unused checks are on.
- **Lookup is by meaning and sees through aliases**: `scope_resolve(scope, name, meaning)` walks the parents, checking locals and then the container's exports (so a second `namespace N {}` sees the first one's exports, and non-exported members stay out of `typeof N`); a symbol matches when its flags have the meaning or when it is an alias whose target does. That is what lets `import { Node } from "./types"` (an interface) merge with a local `function Node()`.
- **Imports and exports are alias symbols** (`scope_add_port()`): import/export specifiers, default imports, `import * as`, `export * as`, `import x = A.B.C` (resolved lexically from the scope it was written in), `export default x`. `symbol_resolve_alias()` is memoised with an in-flight state. A module's `export *` targets are a list on the module symbol; `module_resolved_exports()` flattens them once (own exports shadow stars, first star wins, `default` doesn't travel, cycles are fine). What can't be resolved becomes a *placeholder* symbol that has every meaning and is `any`.
- **Modules.** The parser records every module a file names in `SourceFile.module_refs` (`ModuleRef { path, span, file, module }`: import/export declarations, `import x = require("m")`, `import("m")` types and expressions, `declare module "m"`), wherever it is written; the program loads the files from that list. `binder_module_of_ref()` says what a name refers to: an ambient module of that name (`Binder.ambient_modules`: every `declare module "m" {}` block of every script declares into one module symbol), else the module symbol of the file the program found, else a pattern ambient module (`"*.css"`, longest prefix). `declare module "./a" {}` inside a *module* is an augmentation: its declarations go straight into the exports of the module it names (everything in it is exported). `declare module "m";` is a shorthand module: imports from it are placeholders (any). `export = x` is an export named `export=` (an alias, or a variable for other expressions) and `module_export_equals()` is what importing the module gives (`import x = require()`, `import * as`, default imports, named imports look into it). `export as namespace N` is a global alias of the module. `globalThis` is a namespace symbol whose exports *are* the globals table (`binder_redirect()` maps the shared lib program's one to the current program's).
- **Import types** (`import("./a").B<T>`, `typeof import("./a")`) are `IdentifierType`s with an `import_ref`: the names are looked up in the module's exports instead of the scope, for `typeof` as values and then as properties from `import_prop_start` on. `import("./a")` the expression is a call of the keyword identifier `import` (`KEYWORD_IDENTIFIER_IMPORT`, carries the `ModuleRef`) and gives a `Promise` of the module's type.
- **Symbol accessibility when printing** (`symbol_chain.c`, a port of tsc's getSymbolChain / getAccessibleSymbolChain / needsQualification / getContainersOfSymbol): how a symbol is named from a `Scope`. The tables in scope are tsc's, from the inside: block/function locals, a module's or namespace's locals (with its exported declarations, like tsc's locals with an `exportSymbol`) and then its exports, the globals. A symbol is named by the first table that has it by name, or through an alias in it (`import * as ns` gives `ns.x`, `import b = a.E` gives `b.x`), else by its container's chain (`N.x`); a module that nothing names starts no chain (symbols baseline) or `import("m")` (types, `yield_module`). The symbols baseline passes no meaning (tsc's `symbolToString(symbol, node.parent)`), so shadowing never qualifies there; the types printer passes one (`out_symbol_name()` in `ty/ty_display.c` with `TyDisplay.enclosing`). The test traversal tracks the enclosing file/namespace scope (`BaselineTestCase.enclosing`); function and block scopes don't change how anything is named. Without an enclosing scope (error messages) names are bare, like tsc's lookupSymbolChainWorker (`N.E` prints `E`; enum members keep their enum: `E.A`), and fully qualified (`TyDisplay.fully_qualified`) only where a message shows a source and a target that would print the same (`display_pair()` in `ty/relate.c`, tsc's getTypeNamesForErrorDisplay).
- **Symbols are what the checker knows things by.** AST nodes that declare something keep a `Symbol*` (`symbol`), identifiers keep the symbol the name found (`symbol`, maybe an alias: what the symbols baseline shows) and the one that has the meaning the name is used with (`target`, aliases resolved: `symbol_for_meaning()`, cached so checking never chases alias chains). `this` is a `ThisRef { kind, symbol }` found through `Scope.this_ref` (class instance, class static side, `any`, or a `this` parameter). Nothing in a `Symbol` is written after `binder_link()`; per-symbol checker state is `SymbolLinks` in `Checker.links`.

### LazyType
`LazyType` is a struct owned by the AST: the memoised, cycle-detecting type of whatever contains it (an `Expr`, an `InitializedBinding`, a for-each variable, a `FunctionImpl`, a class field or accessor). It exists so that something can *refer* to a type during name resolution, long before the type can be evaluated. Declared things (classes, interfaces, enums, aliases, namespaces) don't have one: their types are memoised per `Symbol` by the type core.

The process goes something like this:
1. An AST struct, for example `Expr`, contains a `LazyType`
2. In the resolve names phase, it calls `lazy_type_bind(&lazy, LAZY_TYPE_EXPR)`, which sets the tag and gives the LazyType a *slot* number
3. Whoever needs to refer to that type keeps a pointer to the LazyType or to what contains it: a `Binding` points at the LazyType of what is assigned to it (`Binding.source`, the initializer or the for-each variable type), an element of a destructuring pattern at its parent pattern (`Binding.parent`), a class property at its field/accessor LazyType (`Prop.lazy`). There are no link nodes: a `TypeNode` is syntax only, exactly what the parser made
4. Later, in the typecheck phase, whoever wants the type calls `lazy_type_get()` (`ty_binding_type()` for a binding: the written type, else what is assigned, else the property/element of the parent pattern's type)
5. The tag of the LazyType is `LAZY_TYPE_EXPR`, so `lazy_type_evaluate()` uses the pointer to the LazyType to calculate a pointer to its containing `Expr` and calls `expr_evaluate_type()`, which returns a `Ty const*`
6. That goes into the LazyType's memo (`LazyMemo`), and future calls to `lazy_type_get()` return it directly

LazyTypes play a critical role in detecting self-referential types. While a LazyType is being evaluated its memo is in an in-flight state. If something tries to evaluate a declaration's LazyType again in the same call stack, that request gets `TY_CIRCULAR` (an `any`), and the declaration and everything resolved since is circular: tsc's `pushTypeResolution`, one per-checker stack (`Checker.resolving`, `ty_resolving_push()`) that declarations, annotated bindings and the names in patterns (`ty_binding_type()`; a pattern itself only marks from its first name above it, like tsc which doesn't push it), inferred and signature return types, declared and mapped properties, type aliases, interface bases and the base-constraint walk push, so that every declaration of a cycle ends up `TY_CIRCULAR` and reports it (TS7022, TS7023, TS2502, TS2577, TS2456, TS2615, TS2310). Resolving a call starts a new region of it (tsc's `resolutionStart`); the return type of what it resolved to is taken outside that region, like tsc's checkCallExpression. The regions are a stack of resolution barriers (`Checker.barriers`, `ty_barrier_push()`: a call's first resolution, the outermost variance measurement), and `ty_resolving_reenters()` says whether something in flight is only in flight below the innermost barrier, so it is resolved again rather than circular (plan 88). That is the job of *declarations* (where tsc detects and reports circularity): an expression's memo that is hit again while in flight just evaluates again (control flow analysis of a loop re-enters the expressions of the loop body, see "Control flow"; `LazyMemo.hits` stops a runaway), so that the answer doesn't depend on who asked first.

**The memo is not in the LazyType.** The LazyType itself never changes after the resolve names phase: it's a tag and a slot number, and the memo lives in the slot storage (`LazySlots`, a sparse three level table allocated on first touch; slots are handed out in per-thread blocks of a memo page, a fresh block per parsed file and per materialization, `lazy_slots_new_block()`, so a page holds one file's slots) of the current `Checker` (`current_checker` / `current_lazy_slots`, thread local). Each `Program` has a checker, created by `program_make_current()`, which `program_typecheck()` calls; call it yourself to look at the types of a program that wasn't typechecked. With `--checkers K` (`program_set_checkers()`; the CLI's default, 0, is one per thread but at most one per 64 KB of checked non-lib source, `auto_checker_count()`; the test harness's is 1) `program_typecheck()` makes K-1 more and deals the files to them (`deal_files()`: two contiguous runs of program order per checker, by size, so that neighbours that share types share a checker; each checker starts with its share's biggest file, `share_first`, the rest in order: the biggest file is the critical path when it comes late, `TTTT_NO_COSTLIEST_FIRST=1` turns it off; a checker done with its share takes the last unclaimed files of the running share with the most source left, `steal_file()`, so which checker checks a file depends on timing: `TTTT_NO_STEAL=1` turns that off), and runs them on `--threads N` threads (`program_set_threads()`, the calling thread included; which thread runs a checker doesn't matter); each reports into its own `ErrorCtx`, merged and put in tsc's order (`error_ctx_sort_and_dedupe()`) afterwards, and the output doesn't depend on K (tsgo's doesn't; `scripts/kdiff.py`, `scripts/checkerdiff.py`): ties the type order would break by type id (per checker) are broken by tsgo's CompareTypes keys instead (`ty/order.c`). While checking, the binder and the program's `ErrorCtx` are frozen (writes are `log_error`ed). **Checkers are recycled** (plan 67): with a checker memory budget (`program_set_checker_memory()`, the CLI's `--checker-memory MB`, default 256 MB split between the checkers but at least 96 MB each; the library and test harness default never recycles), once a checker holds more than its share after a file (`checker_memory()`: its arena and tables, not the LazyMemo pages, whose count depends on how the parser threads numbered the slots), `check_share()` runs the after-check pass (unused, declaration diagnostics and emit) for the files that checker checked and goes on in a fresh one. The output doesn't depend on it (nothing a file reports depends on a checker's history; `--checker-memory 0`, a fresh checker per file, is an oracle: `scripts/kdiff.py -k 1 -m 0`, `scripts/oracles.py`'s recycle), but a dropped checker's types are gone: anything that reads types after `program_typecheck()` (`program_checker_of()`: `--expect-types`, the harness's types walk) needs the default. This keeps the AST read-only while checking, which is what lets many programs share one lib AST (the test harness does) and lets several checkers work on one AST at once. One choice is made program-wide on purpose: tsc's undefinedProperties (the declaration of the `?: undefined` member a normalized union of object literals gets, which decides its place in the member order and how declaration emit prints it) is first-need per checker in tsc, history by design; tttt keeps one entry per name for the program (ty.h's `UndefinedProps`, members.c's `undefined_choice()`: the candidate first in declaration order among those the files' checks meet, then those only the emit walk does), records each print of such a member per file (`Checker.observing_file`), and `program_typecheck()` checks the files that printed a choice a later candidate replaced again at the end, in one private checker per round (`recheck_stale_undefined_props()`, `checker_new_private()`), so the output is the same whatever the checkers and recycles (a fixpoint: a recheck that meets a new candidate sends the files that printed the replaced choice to another round, at most 3; hacks.md has the bounds). `LAZY_TYPE_EVALUATED` is the tag of `expr_implicit_any()`: nothing to evaluate, no slot. A `LazyMemo` holds type ids, not pointers (`lazy_memo_evaluated()`): `ty_alloc()` registers every Ty in its checker's id table (`lazy_slots_add_type()`), so a type made outside ty_alloc() can't be a memo's result.

### The type core (`src/ty/`)
Semantic types are `Ty` (`src/ty/ty.h`), and everything that has a type evaluates to one: written types are lowered from their `TypeNode` (`ty_from_node()`), expressions are checked by `ty_check_expr()`, functions, classes, interfaces, enums, namespaces and merged declarations have their types built from the AST. There is no other representation: the value-semantic `Type` trees this project started with (cloned, dropped, substituted into) are gone, and `TypeNode` is never created, cloned or resolved by the checker (there is no `type_clone()`).

The statement/expression walk (`statement_typecheck()`, `expr_typecheck()`, `binding_typecheck()`, `class_decl_typecheck()`...) stays in the AST files and asks the type core for types and checks. Like tsc's, it checks a function expression's body (arrows, object literal methods and accessors), a class expression's members, a JSX element's tag, attributes and children and a `void` operand after the statements of its file, in the order met (`Checker.defer_checks`, `Checker.deferred`, `check_deferred()` in program.c, tsc's checkNodeDeferred; not deferred, because nothing observable was found: an assertion's comparability check, variance annotation checks, the arguments of a failed call), and asks for an unannotated function's return type at each `return` before the returned expression (tsc's checkReturnStatement): which question comes first decides cycles and the order types are made in. The type core's checks: `ty/check.c` has the ones with tsc's error wording (`ty_check_assignable()` for TS2322 and its elaboration, `ty_check_property_access()`, `ty_is_comparable_either_way()`), and `ty_of_node()` lowers a written type with the current checker.

- **Symbols know their AST nodes** (`Symbol.decls`, filled by `scope_init_declaration()`), and `lower.c` turns a symbol into types from them. `ty_declared_type_of(symbol)`: interface / class instance type (one `TY_DECLARED` per symbol, the type parameters of later interface declarations unified with the first's), enum, enum member, type alias body, type parameter (`SYMBOL_TYPE_PARAMETER`: declared ones, `infer X`, mapped type keys), in-flight detection for circular aliases. `ty_static_type_of(symbol)`: the static side of a class, the object of an enum. `ty_type_of_symbol(symbol)`: the symbol as a value, from the declarations that contribute one (the first variable declaration, function signatures, class static side, enum object, namespace object, enum member, `export default` expression); one contribution is that type, several are `ty_merged_value_type()`. Variables aren't memoised per symbol: the binding's own LazyType is the memo and the cycle detector. The members of a declared type come from the same nodes: every merged interface body, a class's fields/methods/accessors (overloads hide the implementation signature), inherited instance members, and for the static side `prototype`, static members, inherited static members and the construct signatures (the class's own, else the base class's with this class as the return type).
- **Enums** (`enums.c`): an enum's type is the union of its members' types with the enum as the union's alias (that's how it prints as `E`, and `formatUnionTypes`-style collapsing prints a full run of members inside a bigger union as `E` too). A member's type is a literal type keyed by (value, enum), so members with equal values share a type, like in tsc (the member's declared type is the fresh twin, the enum union holds the regular ones, a written `E.x` is regular); a member whose initializer isn't a compile time constant gets an opaque "computed" type (`TYF_ENUM`). Values come from a small constant evaluator over `Expr` (literals, unary/binary operators, references to other members). The enum object (`typeof E`) has a readonly property per member and the numeric reverse mapping.

- A `Checker` owns an arena, a type id counter and the intern tables. Every `Ty` is immutable once published and interned, so **pointer equality is type identity**: `List<string>` is one pointer no matter how often or where it's written. Ids are handed out in creation order and intrinsics are created in tsc's order. Union members are sorted by tsc 6's stable type order (`ty/order.c`: `ty_compare()`, a sort key cached in `Ty.order_key`, `ty_compare_tie()` for equal keys), whose last tie-break is still the type id; object literal, mapped type and namespace members are sorted by declaration (`builder_sort_stable()` in members.c, tsc's getNamedMembers).
- Intern keys are small arrays of `u64` words (a `KEY_*` tag followed by ids/pointers, `ty_internal.h`) in one open addressing table type (`InternTable`). `Checker.types` holds literals, unions/intersections, references, tuple targets, deferred types and instantiated anonymous types; `Checker.links` holds everything that is *about* an AST node or `Symbol` (`SymbolLinks`: declared and static types; merged value types, type parameters, anonymous types by node, alias instantiations), so the AST is never written to. `intern_slot()` pointers die on the next insert into the same table; use `intern_get()` and look the slot up again when the value takes interning to compute.
- Kinds: intrinsic, literal (incl. enum members; a regular literal and its fresh twin are two `Ty`s, see Freshness under Expressions), type parameter, declared (interface, class instance/static side, enum object, namespace value, tuple target), reference (generic declared type + arguments; arrays are references to the global `Array`, tuples to a tuple target), anonymous (type literal / function type by AST node, or `{target, mapper}` instantiation), union/intersection (sorted by id, cheap reductions only, alias is part of the identity like in tsc), and the deferred `keyof`/indexed access/conditional types, whose constructors resolve eagerly when they can. A mapped type becomes ordinary properties and index signatures once its key type is known (`expand_mapped()`).
- `Ty.flags` (`TYF_*`) are about the type itself (and what could be inside it, like `TYF_COULD_CONTAIN_TYPE_VARIABLES`); `Ty.xflags` (`TYX_*`) propagate from members/arguments/properties to the unions, references and object literals built from them (tsc's ObjectFlags.PropagatingFlags). The only one is `TYX_CONTAINS_WIDENING`: without strictNullChecks the `null`/`undefined` expressions, `void e`, a bare `yield` and `[]`'s element are `TY_NULL_WIDENING`/`TY_UNDEFINED_WIDENING` (print as `null`/`undefined`, aliases of the plain intrinsics under strictNullChecks), and `ty_widened_nullable()` turns only those into `any`; `report_errors_from_widening()` (binding.c) is tsc's TS7005/TS7006/TS7018 from that widening.
- **Union origins** (`Ty.composite.origin`, tsc's UnionType.origin): what a union was built as, printed instead of its members and part of its intern key (same members, different origin = different type, like in tsc). A union of named unions (aliased or with an origin) remembers them (`union_with_origin()`: `A | <A's members>` is `A`), `A & (B | C)` distributed by the cross product (`intersection()`, tsc's getCrossProductIntersections) remembers the intersection when that is shorter, `keyof X` of an aliased/class/interface/reference type remembers `keyof X` (TY_KEYOF origin), and narrowing's `ty_union_filtered()` filters the origin alongside. Origins are plain `Ty`s outside the intern table, made only when the union is new (`OriginSpec`). The relation takes tsc's two origin shortcuts in `structured_related_members()`. Origins aren't instantiated yet (plan 37 B stage 2).
- **The missing type** (`TY_MISSING`, tsc's missingType, only under exactOptionalPropertyTypes: `ty_undefined_or_missing()`): the `undefined` an optional property or tuple element's type has (`ty_optional_prop_type()`, tsc's getOptionalType); it prints as `undefined`, a union drops it next to a real `undefined`, and it sorts first (`ty_contains_missing()` looks at member 0). **An optional property's type carries its undefined** (plan 82): `prop_type()` and `FoundProp.type` are tsc's getTypeOfSymbol, `T | undefined` (missing under exactOptionalPropertyTypes; a real undefined for a parameter property and a binding pattern's initialized element), added where the property is made (`prop_type_slow()`, `instantiated_prop_type()`'s mapped rule, object literal methods, spreads), never by readers; destructuring-default props (`PROP_PATTERN_OPTIONAL`) stay bare like tsc's. Relations, inference, index constraints and the printer take missing out (`ty_remove_missing()`, tsc's getNonMissingTypeOfSymbol), as do write targets; TS2375/TS2379/TS2412 are the exactOptional variants of TS2322/TS2345. Likewise **optional parameters and tuple elements**: `SigParam.type` of a `?` or initialized parameter is tsc's getTypeOfParameter, with a real undefined, added in `signature_resolve()` (`SigParam.undefined_added` says so: `ty_sig_param_symbol_type()` is the symbol's type the printer shows, without an initializer's undefined; `ty_sig_param_declared_type()` the annotation's, a setter's), and every tuple reference adds undefined-or-missing to its optional elements (`ty_reference_with_this()`, tsc's TupleNormalizer.add); readers just read.
- **The optional marker** (`TY_OPTIONAL`, tsc's optionalType): the `undefined` of an optional chain that ended, in the types of the accesses, calls and `!`s inside a chain (`a?.b` of `a?.b.c`, which the parser marks `continues_chain`); the chain's end gets a plain `undefined` instead (`propagate_optional()` in `ty/expr.c`). It prints as `undefined` and a union keeps it next to a real one, so `a?.b.c` with an optional `b` still sees b's own `undefined` (TS18048): whoever reads the object, callee or receiver of a chain takes it out with `ty_optional_expression_type()` (tsc's getOptionalExpressionType).
- **Members are lazy** (`members.c`): `ty_members()` resolves props, call/construct signatures and index signatures on first use; `prop_type()` and `signature_resolve()` lower or instantiate the types inside on first use. That is what makes recursive types legal and cheap. A signature's resolved state (type parameters, `SigParam`s, counts, `this`, and its effective target and mapper: a JSDoc `@type` tag's signature, the clones of its own type parameters) is one record, `SigResolved`, behind `Signature.res`: `signature_resolve()` returns it, `sig_res()` reads it without resolving (`sig_resolved_none`, zeros, before), `sig_target()`/`sig_mapper()` the target and mapper as of now (`Signature.target`/`mapper` are as made and never written after). It is allocated when resolution starts and filled in place (a re-entry sees what is resolved so far), immutable once done (plan 86 stage 4f S1: the step to a write-once word). An instantiated signature (`{target, mapper}`) gets fresh copies of its own type parameters that have a constraint or default (`clone_type_params()`, `TyParamState.clone_of`); `ty_signature_instantiation()` replaces a signature's type parameters by type arguments (memoised), `ty_instantiate_signature_in_context_of()` infers them from another signature's parameters (tsc's instantiateSignatureInContextOf), which is how a generic source signature is related to any target (`compare_signatures()`).
- **Instantiation never copies** (`instantiate.c`): `ty_instantiate(ty, mapper)` returns `ty` itself unless it has `TYF_COULD_CONTAIN_TYPE_VARIABLES`, rebuilds interned kinds through their constructors, and turns an anonymous type into an interned `{target, mapper}` pair restricted to the type parameters the node actually mentions (`free_params`).
- **Functions** (`function.c`): the type of a function declaration, function expression, method, accessor or constructor is an anonymous object type with one signature that is read straight off its `FunctionImpl` (`Ty.anonymous.function`, `Signature.function`): type parameters from its `Generic`, parameter types from the bindings, and the return type from the annotation or, lazily, from the `return` statements of the body (`ty_function_return_type()`: the union of what `block_collect_return_types()` finds, subtype reduced and widened, plus `undefined` when the end of the body is reachable or there is a bare `return;` (strict), `void` without returns, `never` for a function expression that can't return, wrapped in `Promise` for async functions, memoised per function with an in-flight state so a function that returns its own call is `any`). A function *type* (`(a: T) => R`) is a `TYPE_CALLABLE` node that owns a body-less `FunctionImpl`.
- **Namespaces and merged declarations** (`lower.c`, `members.c`): the value of a namespace (or of a module, for `import * as ns`) is a declared type by `Symbol` with a property per value among its exports, by export name and in declaration order (`ty_namespace_type()`; the type of such a property is `ty_type_of_symbol()` of the member, `Prop.symbol`). A symbol several declarations give a value to (function overloads, a function/class/enum merged with a namespace) gets the members of all of them (`ty_merged_value_type()`): anonymous for overloads alone, by name (`typeof f`) otherwise.
- **Relations** (`relate.c`): `ty_is_related(source, target, relation)` for assignable, comparable, strict subtype (union reduction) and an assignable variant with strict nulls. It follows tsc's structure because the observable results depend on it: simple relations by flags first, then a per-relation cache on the checker keyed by `(source id, target id)`, a "maybe" stack for pairs that are being compared further up (assumed related, made definitive when the outer comparison finishes), a deep-nesting check on the generic target of the types on the stack (what terminates infinitely expanding generics), and for two references to the same generic type a comparison of the type arguments by *measured variance* (`get_variances()`, marker type parameters, cached in `Checker.links` once measured; a measurement in flight is a `VarianceClaim` on the stack of whoever started it, `Checker.claims[CLAIM_VARIANCES]`, never a state in the links: plan 86's overlay). Signatures follow tsc's signaturesRelatedTo (instantiations of one type pair up, a single signature on each side keeps its type parameters, N x M erases them and only the first source signature explains a failure) and compareSignaturesRelated (two callback parameters are compared as signatures, the other way around: `CallbackMode`). Which comparisons run with `report` is observable, because a cached failure is only computed again (and a pair on the stack only assumed related) for a comparison that reports. `ty_explain_unrelated()` reruns a failed check in reporting mode and returns tsc's elaboration chain, outermost line first; the first line is either the generic TS2322 head or something that replaces it (TS2741 missing property...). Lines are collected innermost first in `RelationState.lines`, the last one being the head of tsgo's error chain: a pair's own "not assignable" line is left out when the line below it says it already (an excess property, a missing property or readonly line about the same types: `relation_line_said()`, tsgo's reportRelationError), a property step merges with a property step or a signature's (never shown, `elided`) return types marker two lines below it into one path line ("The types of 'a.b' are incompatible between these types.", `report_property_incompatible()`, tsgo's reportError). `TTTT_DEBUG_RELATE=1` logs every top-level query, `TTTT_DUMP_VARIANCES=1` every measured variance. `VARIANCE_UNRELIABLE` comes from a checker-wide flag (`variance_reports`, set when a compared type mentions a marker) and is cached as `CACHE_UNRELIABLE`; alias markers are by type id (`KEY_ALIAS_MARKER`). Build constraint: relate.c sits at GCC's `inline-unit-growth` limit, so code added anywhere can cost a hot inlining elsewhere (`find_prop` into `props_related_impl`): reporting helpers are `[[gnu::cold]]`, rare paths `[[gnu::noinline, gnu::cold]]`; check `-fopt-info-inline-missed` when an innocent change shows in `scripts/instrcount.sh`.
- **Calls** (`call.c`): `resolve_call()` collects the call or construct signatures of the callee's apparent type (a union is called member by member, an intersection through all its members' signatures), and `resolve_with_signatures()` takes the first candidate that fits, like tsc's `resolveCall`: arity (`ParamShape` spreads a tuple rest parameter out, `Args` spreads tuple spread arguments out), type arguments inferred from the arguments, every argument related to its parameter, with a subtype round before the assignable round when there are overloads. Arguments are checked with the candidate's parameter types as contextual types; a generic candidate infers in two passes (context-sensitive arguments, ie lambdas with unannotated parameters or context-sensitive returned expressions and literals containing them, come second and see the parameter type instantiated with what the first pass found), also from the contextual type of the call to the return type at low priority. The second pass also takes, in argument order, generic function arguments where the parameter wants a non-generic signature (instantiated in its context, or, if the call returns a function and not everything is inferred yet, propagated: the argument's type parameters become the returned function's, tsc's higher-order inference, `Candidate.inferred_type_params`) and calls of generic functions that return functions (which then see the other arguments' inferences through `Checker.outer_inference`). Explicit type arguments (`f<A>(x)`, a `GenericParamsExpr` around the callee) select candidates by type parameter count (TS2558), replace inference, and are checked against the constraints (TS2344). When nothing fits the errors are tsc's: TS2554/2555/2575 for arity, the argument error of a lone candidate, TS2769 with one "Overload n of m" branch per candidate otherwise. A tagged template (`` tag`a${x}` ``) is a call too (`ty_tagged_template_return_type()`): a stand-in `CallExpr` with the tag as callee and the substitutions as arguments, after a `TemplateStringsArray` that `collect_args()` adds for `CallInfo.tagged_template`; an unterminated template is an incomplete call (no minimum arity). A decorator is a call too (`ty_check_decorator()`, from `class_decl_typecheck()`, which checks the decorators of the class, its members and their parameters): `decorator_call()` builds tsc's legacy or ES decorator signature for the site (synthetic arguments in `DecoratorCall`, the signature is the decorator expression's contextual type), `collect_args()` passes those for `CallInfo.decorator`, the argument count goes by the candidate (`DecoratorArity`, tsc's getDecoratorArgumentCount, TS1278/TS1279), errors go under TS1238-1241's heads, and the return type is checked against what the site accepts (TS1270/TS1271); `@f` meant as `@f()` is TS1329. **A call is resolved once** (`call_return_type()`, tsc's `links.resolvedSignature`): the first resolution, wherever it happens (an outer call's inference round, one of its overloads), is remembered per node with the errors it reported, and the typecheck walk (`ty_call_typecheck()`) reports those instead of resolving again. It resolves with the raw contextual type (`ExprCtx.raw_contextual`): an outer call's inferences are applied inside `infer_type_arguments()`.
- **Inference** (`infer.c`): one walker (`infer_types()`) for generic calls and for `infer X` in conditional types. It keeps covariant and contravariant candidates apart (parameters flip the direction under `strictFunctionTypes`, reference type arguments by measured variance), knows priorities (a naked type parameter in a union gets what the other members didn't match), and records whether the type parameter was only seen at the top level of a parameter type. `inference_call_result()` is tsc's `getInferredType` for calls (literal widening unless the constraint is primitive or the type parameter is at the top level of the return type, common supertype, covariant preferred over contravariant when it fits, `unknown`/default/constraint fallbacks are in `infer_type_arguments()`); `inference_conditional_result()` is union / intersection. `InferParam.fixed` is the seam for the context-sensitive second pass that comes with contextual typing.
- **Expressions** (`expr.c`): `ty_check_expr(expr, contextual)` is the one entry point. There are no parent pointers to find a contextual type through, so the rule is the other way around: **whoever knows an expression's contextual type checks it with that type before anything else asks**, and the result is the expression's memo (`lazy_type_set()`, with the contextual type it was computed for in `LazyMemo.context`); `ty_expr_type()` reads the memo and only checks without context if nobody got there first. A variable declaration checks its initializer with the annotation, `return` with the function's return type (`Checker.return_context`), an assignment with the target's type, a call checks each argument with its parameter type (per overload candidate), object and array literals pass the property/element type of their own contextual type down (`contextual_prop_type()`, `contextual_element_type()`), and `expr_typecheck()` evaluates an expression's own type before walking into it. A function expression takes the types of its unannotated parameters from the first contextual signature it meets and keeps them (`assign_contextual_signature()`: links keyed by parameter, read back by the parameter's own LazyType; tsc does the same), while literals are simply checked again for a new contextual type. What is read later, lazily, goes the other way: once a call is resolved, the contextual return type of a function in its arguments and the contextual type of an object literal there (for `this`) are derived through the resolved signature along a path recorded from the arguments (`ContextAnchor`, `ty_record_call_anchors()`: tsc's getContextualType walking up to `links.resolvedSignature`); before that the first contextual signature (`KEY_CONTEXT_RETURN`) and the literal's last context stand in for tsc's pushed contextual type. A function expression asked for (its parameters, its inferred return) before anything checked it settles its context first (`ty_settle_function_context()`): the resolve walk records its *context root* (`FunctionImpl.context_root`: the expression statement, condition, initializer or return expression the walk checks that pushes context down to it), which is checked then as the walk would, outermost first and flow-isolated, so its contextual signature doesn't depend on what was checked before (tsc's getContextualSignature resolving the enclosing call on demand). **Freshness** (tsc's model): a literal expression (and `-1`, `!x` of known truthiness, an enum member's value) evaluates to the *fresh* twin of its literal type (`ty_fresh_literal()`, a separate interned `Ty` with `TYF_FRESH_LITERAL`); written types and everything derived from them hold regular ones. Only fresh literals widen (`ty_widened_literal()`; `ty_base_type_of_literal()` widens regardless, for operators and messages): a mutable location (`check_for_mutable_location()`) widens unless the contextual type has room for literals and then regularises, a declaration (`ty_widened_for_declaration()`) widens without regularising (`const e = E.x` holds the fresh `E.x`), an inferred unit return type likewise. Relations normalise to regular (`ty_regular()`) at every entry, so caches never see fresh literals; so do switch clause types, index keys, `typeof`, intersection members, and the `.types` printer (expression types print regular). An object literal expression is a fresh object type too (`TYF_FRESH_OBJECT`, `OBJECT_LITERAL_FRESH`): relations see it as it is and give it excess property checks (`has_excess_properties()`, TS2353 at the property name via `TyReportLine.span`); declarations, inferred return types, inferences, `typeof` and union target members see its widened twin (`ty_widened_objects()`, built lazily with the properties widened recursively; tsc's getWidenedType, which also subtype-reduces a union once a member widened to an empty object). In between there is tsc's regular object literal (`ty_regular_object_literal()`, `OBJECT_LITERAL_REGULAR`: `TYF_FRESH_OBJECT` for "still widens" plus `anonymous.regular`, so `ty_is_fresh_object()` is false), e.g. an evolving array's elements. Fresh and regular object literals are *unwidened* (`ty_is_unwidened_object_literal()`, tsc's isObjectLiteralType): as relation targets they reject source properties they lack (`props_related_impl()`), so `string | {}` of those stays a union until widened. A variable's destructuring pattern reads its initializer's unwidened type, each element is widened itself (tsc's getTypeForBindingElementParent). A contextual tuple type or `as const` makes an array literal a tuple. `ty_identifier_reference_type()` is the one place the type of an identifier reference comes from (narrowing will live there). An expression's memo is the *last* contextual check's (`check_with()`, `LazyMemo.context`), as tsc's final Normal-mode check writes the node type; `kind_uses_context` decides which kinds are rechecked. `ExprCtx.sig_contextual` is only instantiated where `may_want_signature()` (a perf gate). Side tables in `Checker.links`: `KEY_CONTEXT_IIFE_RETURN` (recorded at an IIFE's first contextual check, tsc's getContextualType(iife)), `KEY_LITERAL_PARENT` (an object literal's parent literal, for outer `ThisType` markers), `KEY_CONTEXT_PARAM_PATTERN` (pattern fallbacks, for the symbols traversal).
- **Outer type parameters** (tsc's outerTypeParameters): a class, interface or type alias declared inside something
  generic captures the type parameters around it (`OuterGenerics`, recorded by the resolve walk). A class or interface's
  `Ty.declared.type_params` are the outer ones followed by its own (`outer_count`; `ty_local_type_params()` are the
  ones type arguments are written for), a reference inside the scope passes the outer ones as themselves, and the
  enclosing function's mapper instantiates them like any type argument: `f(3)` of `function f<T>() { class C {} ...}`
  is `f<number>.C` (printed `f.C`: tsgo drops outer type arguments). A local class's value is its static side applied to the outer parameters.
- **Mixin classes** (`members.c`): a class whose `extends` expression is a type variable `T` (or an intersection with
  one, `ty_class_base_type_variable()`) has the value `typeof C & T`, printed structurally; its base instance comes
  from T's constraint's construct signatures (`class_base()` accepts tsc's isValidBaseType), and an intersection's
  construct signatures follow the mixin rule (`resolve_intersection_members()`). Relations see a class or interface
  that adds no members to its one base as that base (`ty_non_augmenting_base()`).
- **`this` types** (`lower.c`, `members.c`): every class, and every interface that mentions `this` (or extends one that
  does), has a `this` type parameter (`Ty.declared.this_param`, constrained to the type seen from inside). The members
  as declared (`declared_raw_members()`, `Ty.declared.raw`) mention it, bases included, which are taken with the derived
  type's `this` as their this-argument; a reference carries an optional this-argument (`Ty.reference.this_arg`, part of
  its identity) and its members are the raw ones instantiated with the type arguments and `this` = the this-argument or
  the reference itself (`resolve_members_with_this()`); the declared type itself is its own this-argument. When only
  `this` is mapped, members whose declaration can't mention it (`Prop.thisless`, tsc's syntactic rules) are shared.
  The `this` expression is the `this` type parameter, and the apparent type of a type parameter is its constraint
  with the type parameter as this-argument (`t.chain()` is `T` for `T extends C`). An intersection's members see the
  whole intersection as their this-argument (tsc's getApparentTypeOfIntersectionType), wherever its properties are
  read: `find_prop()`, `resolve_intersection_members()`, an intersection target's combined properties
  (`intersection_props_related()`). A tuple reference may carry one too (tsc's tuple targets have a this-type), which
  the array properties that mention `this` (`sort()`) are retargeted to (`resolve_tuple_members()`).
- **Bases that depend on type arguments** (`members.c`): references instantiate the raw members of every class and
  interface (`Ty.declared.raw`), bases' included. That's only right while the members a base adds don't depend on the
  type arguments; when a base is a type parameter (`interface I<T extends object> extends T`), an intersection with
  one, or a class/interface with such a base (`base_is_dynamic()`), the raw members are only the type's own plus
  `Members.bases`, and each instantiation (`instantiate_members()`) or the declared type itself (`complete_members()`)
  adds the bases' members, like tsc's resolveObjectTypeMembers does for every type.
- **Unique symbols and iteration** (`checker.c`, `iterate.c`): a `unique symbol` is a `TY_LITERAL` with
  `TYF_UNIQUE_ES_SYMBOL`, one per declaration (`UniqueSymbolDecl`: the resolve walk marks the `unique symbol` annotation
  and the `Symbol()` initializer of a `const`, a `static readonly` field or a `readonly` property signature, so both
  mean the same type). Its `literal.string` is an escaped property name (`__@iterator@12`) that members are keyed by
  like any other name, and `ty_unique_symbol_of_name()` maps it back (display as `[Symbol.iterator]`, `keyof`).
  `ty_iteration_types_of_iterable()` is tsc's getIterationTypesOfIterable: references to the lib's iterable/iterator
  interfaces by identity, else `[Symbol.iterator]()` -> `next()` -> `IteratorResult`, cached per type id;
  `ty_iterated_type()` is what for-of, spread and array destructuring use (with tsc's ES5 gating and errors).
  Generators infer `Generator<Y, R, N>` from the `yield`s the resolve walk collected (`FunctionImpl.yields`) and their
  returns; a `yield` evaluates to the generator's TNext.
- **Property access** (`access.c`): `ty_access(object, index)` for a known index, through apparent types (`String` for strings, the constraint for a type parameter, `Function`/`Object` members), tuple elements, then index signatures. So is the indexed access *type* `T[K]` once neither operand is generic (`try_resolve_indexed()`). Expressions that read go through `ty_access_reading()` (noUncheckedIndexedAccess adds undefined to index signature and rest element reads); a generic key on a non-generic object is the deferred `O[K]`. Writes: a property can have a write type of its own (`Prop.write_node`, a divergent `set` accessor's parameter type, `prop_write_type()`), which `ty_access_write_type()` finds for definite assignment targets (unions/intersections combine members) and `ty_compound_assignee_type()` for `o.x += v`. `ty_check_indexed_access_type()` checks `O[K]` written as a type (TS2339/2537/2538; the generic TS2536 isn't done).
- **Substitution types** (`TY_SUBSTITUTION`, tsc's): a type in the true branch of a conditional type whose check type it is (`T` in `T extends string ? Lowercase<T> : never`) lowers to (T, string), from the chain of true branches `TypeNode.flow` the resolve walk gives every node (`conditional_flow_type()`, lower.c; the chain also holds the templates of mapped types without `as`, where the key of a homomorphic mapped type over an array-constrained T is also `number | `${number}``); `NoInfer<T>` is one with an unknown constraint. Relations see `base & constraint` as a source and `base` as a target, inference targets the base and infers nothing into NoInfer, instantiation turns it back into the base once that satisfies the constraint (restrictively), and it prints as its base.
- **Conditional types** (`conditional.c`): `ty_conditional()` resolves as soon as the check type isn't generic at the top level: `infer` type parameters are inferred by walking check and extends type in parallel, the extends type is instantiated with the results and related: definitely false (the false branch) when not even the permissive instantiation relates, with every type variable the wildcard (`TY_WILDCARD`, tsc's wildcardType: an `any` that unions, intersections, indexed accesses, conditional and mapped types containing it collapse to), definitely true with the restrictive one (unconstrained stand-ins), deferred otherwise. A deferred conditional type remembers the conditional type it was written as and the mapper that leads from there to it (`Ty.conditional.root`/`.mapper`, tsc's ConditionalRoot), and `ty_instantiate()` always restarts from the root, with the mapper cut down to the root's outer type parameters (the ones its node mentions, `ty_conditional_outer()`) and the result cached by what those map to (tsc's getConditionalTypeInstantiation): that's where distribution happens, when the *written* check type parameter turns out to be a union, however many instantiations later (`Exclude<keyof T, K>` inside `Omit<T, K>`). Branches are lowered on first use (`TyCondBranch`, like tsc's getTypeFromConditionalTypeNode, which only resolves the check and extends types). Array, tuple and generic interface/class references are *deferred references* (`ty_deferred_reference()`, type arguments lowered on first use by `ty_reference_args()`) where tsc's isDeferredTypeReferenceNode says so: the body of an alias (which the reference then goes by: `type B<T> = Box<T>` prints `B<string>`), or inside an alias body (`LowerCtx.in_alias`, tsc's isResolvedByTypeAlias: through unions, intersections, indexed accesses, conditionals, type arguments, arrays and tuples; not into object, function or template literal types) with an element or type argument that may resolve an alias (`may_resolve_type_alias()`) or defaulted type arguments: `type Json = string | Json[]`, `type RD<T> = ... ReadonlyArray<RD<I>>`. Their instantiations are keyed by what the node's outer type parameters map to. The template of a mapped type is lazy too (`ty_mapped_template()`, tsc's getTemplateTypeFromMappedType), and so is the per-key property its properties instantiate (`Prop.template_of`).
- **Diagnostics from deep inside the checker** go where tsc's `error(currentNode, ...)` puts them: `Checker.current_node` is the statement, expression (`compute()`), type reference or indexed access type being checked (`ty_enter_node()`/`ty_enter_expr()`/`ty_leave_node()`, which also start the instantiation count over like checkSourceElement/checkExpression), and `ty_error_at_current_node()`/`ty_error_at()` add straight to the program's diagnostics (only while typechecking, not while a baseline prints types). That's TS2589 (instantiation limits: `ty_instantiation_limit_reached()`, counted in `instantiation_limit_hits` so a check site doesn't add a TS2322 on top; what it cut short is memoized like tsc's errorType, so it's reported once and later users are silently any), TS2456 (a type alias re-entered while resolving: the resolution stack, see LazyTypes), TS2577 (`signature_return_type()`), TS4109/TS4110 (a deferred reference's arguments), TS2615 (a mapped type property) and TS1062 (awaited type).
- **Template literal types and string mappings** (`template.c`): `TY_TEMPLATE_LITERAL` (texts as atoms around the types) and `TY_STRING_MAPPING` (`Uppercase<T>` & co., made where the lib's `type Uppercase<S> = intrinsic` is referenced, `intrinsic_alias_instance()` in lower.c). The constructors are tsc's getTemplateLiteralType / getStringMappingType: literals fold into the texts, unions distribute, only type variables and pattern placeholders (`string`, `number`, `bigint`, `any`, other patterns) stay as types. They carry `TYF_DEFERRED` only when generic: a *pattern* like `` `a${string}` `` is a concrete set of strings. Relations match string literals and templates against a template target by the text parts (`ty_template_matches()`, tsc's inferFromLiteralPartsToTemplateLiteral + isValidTypeForTemplateLiteralPlaceholder), and inference uses the same matching (`infer_to_template()` in infer.c, which also turns a matched `"12"` into `12` for `infer N extends number`). Template literal *expressions* are template types in a const context, an element access index or with a string-literal/template contextual type, and constant ones fold to a string literal through the enum evaluator (`ty_evaluate_string()`).
- **Conditional instantiation keeps a conditional type's own `infer` parameters out of the mapper** (`without_own_infers()`, the list per root recorded at lowering, `ty_conditional_own_infers()`): a recursive `Split<B, D>` in the true branch of `Split` must not see the outer `infer B`'s result in its own extends type. A missing inference or one that violates the `infer X extends C` constraint is the constraint (tsc's getInferredType). Without `extends`, an `infer X` has an implied constraint from where it is written (`ty_implied_infer_constraint()`, tsc's getInferredTypeParameterConstraint, from `InferredType.position` recorded when the scope declares it): the constraint of the type parameter of `Foo<infer X>` instantiated with the reference's arguments, `unknown[]` in rest positions, `string` in a template placeholder, `keyof any` as a mapped type's key type; the intersection of them over several `infer X` of one name.
- **Tuples are normalized when referenced** (`normalized_tuple()` in checker.c, tsc's createNormalizedTupleType): a spread of a tuple is spliced in, of a union distributes, and everything from the first rest element to the last optional or rest element becomes one rest element. A rest element's argument is the spread type as written (`...T[]` keeps `T[]`).
- `lower.c`: `ty_from_node()` is the only producer of `Ty` from syntax; the symbol entry points are described above. Anonymous object types are keyed by the *address* of their node, which is stable because nodes belong to the AST.
- **Alias names**: unions, intersections, object types, arrays/tuples (as deferred references), `T[K]` and conditional types written as the body of an alias carry `Ty.alias` + `alias_args`, instantiation instantiates the arguments, and `ty_realias()` renames the instantiation of a generic alias that is itself the body of another alias (`type Bar = Omit<Foo, "c">` prints as `Bar`). A homomorphic mapped type instantiated with an array or tuple becomes an array or tuple (`instantiate_mapped_over_list()`).
- `ty_display.c` prints like tsc's `typeToString()`: alias name, else reference name + arguments (`T[]`, tuple syntax), else declared name, else structure.
- **Types baseline node reuse** (`TyDisplay.types_baseline`, also declaration emit's): tsc's node builder reuses annotation nodes from the source; `TyDisplay.reused` is set inside a reused node. Where tsc's `serializeTypeForDeclaration` reuses a declaration's annotation (signature parameters, `this`, return types and predicates, type parameter constraints, property annotations, object literal accessors and `as T`), `display_annotated()` checks that the annotation's type is the printed one (optional: without `undefined`) and then `display_node()` prints *the TypeNode*, as written, with tsc's printer layout (`TypeNode.parenthesized` keeps written parentheses). A part whose first name isn't accessible from `enclosing` (`name_accessible()`) prints its type instead, per node like tsc's recovery. Where the declaration has no annotation, tsgo's pseudo type (`ty/pseudo.c`, a port of its pseudochecker: the type as the declaration's syntax says it, a `Pseudo` tree of annotations, literals, object literal members, function expressions' parameters and single `return`, or "inferred") is printed when `pseudo_equivalent()` finds it stands for the printed type (`display_pseudo()`): an object literal's property assignments and accessors (`PropDecl.item`), parameters and return types of signatures with declarations, a namespace's variables as members. The pseudochecker looks at parents (is the node contextually typed, in a const context), which the resolve walk records for it (`ObjectExprItem.pseudo_contextual`/`pseudo_const`, `FunctionImpl.syntactically_contextual`). Error messages printed from nowhere never reuse (no `enclosing`); those printed from their expression (`reuse_nodes`) do. The harness (`add_type_rendered`, `LineNumberedStr.intrinsic_at`) prints an `any`'s intrinsic name (`any`, `error`) when tsc's baseline has no errors, except where tsc's harness prints the type node anyway (`BaselineTestCase.any_keeps_rendering`: property access/qualified name parts, binding elements, labels, import/export names).
- `ty_display()` has a depth safety net past which a runaway print stops with `...`: 1024 where nothing truncates (tsc has only its 1M length limit), 128 in declaration emit, 44 (`MAX_DISPLAY_DEPTH * 4`) in messages.
- The `.types`/`.symbols` test traversal (`src/test/baseline_test_traversal.c`) prints `Ty`s with `TyDisplay.unqualified_names`; the one exception is a declaration whose type is a written type *name*, which prints as written (node reuse, above).

**Members asked for while they are resolved** (`ty_members_resolving()`, members.c): an object type's members have an in-flight state. A class or interface asked again meanwhile gets its early members (its properties, published before its index signatures are lowered: `early_declared_members()`; they live in the resolving checker's `MembersClaim`, never in the shared state, which only gets the finished members), or empty members and the base circularity when its members depend on themselves (`interface A extends A`); anything else (a mapped type expanding) gets empty members. That is tsc's resolveStructuredTypeMembers, which installs empty members before resolveMappedTypeMembers fills them: the outer resolution completes and is what is cached. But what the re-entrant reader builds from the empty members (a lowered conditional branch, a `keyof` union) is cached too, so tttt doesn't expand a mapped type for what tsc reads off its declaration: whether it stays generic (`ty_generic_mapped()`, tsc's isGenericMappedType when its constraint is a generic index), its keys (`ty_keyof()`, getIndexTypeForMappedType), its MappedInfo (`ty_mapped_info_unexpanded()`; an instantiation's is its declaration's instantiated, `declared_mapped_members()`, never the generic declaration's expansion). The expansion relates the `as` clause to the key (tsc's getMappedTypeNameTypeKind, cached per declared mapped type), and `${K}.${keyof Self<T[K]>}` reaches `keyof Self<...>` from there (mappedTypeAsClauseRecursiveNoCrash1).

**Eager base runaways** (`members.c`, `probe_eager_bases()`): tsc's resolveObjectTypeMembers instantiates a reference's bases with its type arguments whenever its members are resolved, and its resolveStructuredTypeMembers has no in-flight state: when that instantiation needs the same members again (`class PersonModel extends AutoModel<PersonModel>` with `AutoModel<T> extends Model<Omit<T, ...>>`, postcss-selector-parser's `_Selector<S> extends Container<Diff<Node, S>>`), tsc starts over with a new mapper until the instantiation stack is 100 deep and reports TS5114/TS5115. tttt's reference members are its target's raw members instantiated (the bases' are in them already), so after a reference's members are resolved (`ty_members()`, still in flight) the bases whose instantiation resolves something (`MembersRare.eager_bases`: a conditional type, indexed access or `keyof` among the type arguments) are instantiated for their side effects only, when the reference's arguments mention something whose members are in flight or a type whose bases mention itself (`MembersRare.recursive_bases`), and not from inside another probe except along the chain of bases. Members asked for again meanwhile (`members_reentered_unguarded()`) are tsc's runaway when nothing was pushed on the resolving stack since they started (tsc's second round would stop at such a guard; `RESOLVING_MAPPED_CONSTRAINT` stands for its mapped type key constraints): the report is tsc's getCircularTypeNames over the instantiation stack with the part since those members started repeated to 100. What tsc's deepest round leaves in its caches (error types) is not modelled.

### Control flow (`flow.h`/`flow.c`, `ty/flow.c`)
The model is tsc's, because the `.types` baseline prints the narrowed type of every reference: a graph of `FlowNode`s built at bind time, which the checker walks *backwards* from a reference (`ty_flow_type()`, below).
- **Nodes**: start, branch label, loop label (antecedent lists; the first antecedent of a loop label is the way in), assignment (`FlowAssign`: which declaration / `=` / `++` / for-of / element of a destructuring assignment, the latter with the recorded `FlowPatternPath` down the pattern since there are no parent pointers), true/false condition (only for expressions that can narrow: `expr_is_narrowing()`; a `true`/`false` literal makes the other branch unreachable), switch clause (`[start, end)`; the empty range is "no clause matched" of a switch without `default`), call (a call statement with a dotted-name callee: maybe an assertion or a `never` call, the checker decides) and reduce label (try/finally). `FLOW_SHARED` marks nodes with more than one successor. Nodes live in the binder's arena and are read-only after resolve; one static `flow_unreachable` node stands for dead code.
- **Who points at it**: `IdentifierExpr.flow` (also `this`/`super`), `PropertyExpr.flow`, `FunctionImpl.outer_flow` (function expressions, arrows, object literal methods: their start node says narrowing may continue outside), `FunctionImpl.end_flow` (non-null: control can fall off the end) and `return_flow` (constructors). References in unreachable code have no flow node, like in tsc.
- **The builder** (`FlowBuilder`) is tsc's binder state (`current`, break/continue/return/exception targets, active labels, `has_flow_effects`), one per flow container (file, namespace body, function, class field initializer, static block) on the stack of whoever walks the container and reached through `Scope.flow`. What tsc finds through parent pointers is handed *down* instead: whoever walks an expression as a condition sets `true_target`/`false_target` first (`expr_lookup_names_condition()`), as an assignment target `assignment_target`, as the object of an optional chain `chain_continues`, and `expr_lookup_names()` takes them on entry so they never leak into operands. A non-async, non-generator IIFE is part of the surrounding flow. Inside an unreachable statement the builder is `dead`: nothing changes `current`.
- **Assignments are marked during the same walk**: `IdentifierExpr`/`PropertyExpr.assignment_target` (definite or compound: such a reference has its declared type), and on *local* variable symbols `is_assigned`, `is_assigned_in_closure` and `last_assignment_end` (tsc's `lastAssignmentPos`: the end of the outermost statement around the assignment that starts after the declaration), which is what narrowing inside closures will ask.
- **Reachability**: the builder reports TS7027 at the first statement of unreachable code (runs of statements in a block; only when `allowUnreachableCode` is explicitly `false`, otherwise it's an editor suggestion) and TS7028. What needs types is the checker's: `ty_flow_reachability()` is `isReachableFlowNode` (a call statement whose callee is *declared* to return `never` or asserts something false, the "no case matched" edge of an exhaustive switch: `is_exhaustive_switch()`), and the statements tsc gives a flow node have one too (`Statement.flow`), so `statement_typecheck()` reports TS7027 for code after `fail()`. Its other consumers: `never` for function expressions that can't return, `| undefined` in inferred return types, TS2355/TS2366/TS7030/TS2534/TS2378.
- **Narrowing** (`ty/flow.c`, a port of tsc's `getFlowTypeOfReference()`; approximations are listed in `agents/hacks.md`, "Control flow and narrowing"): `ty_flow_type(reference, declared, initial, flow)` walks back from the reference's flow node. A matching assignment gives the declared type reduced by what was assigned (a prefix of the reference, `x = ...` while asking about `x.y`, resets to declared); a condition narrows if its expression is about the reference (truthiness, `===`/`!==` with anything, `typeof`, `instanceof`, `in`, calls of type predicates, comparisons with `true`/`false`, `??`/`?.` conditions marked `FLOW_NULLISH`, optional chain containment; and if it is about a *discriminant property* of the reference, `x.kind === "a"`, the members of the union whose property could be what is left: `discriminant_access()` / `narrow_by_discriminant()`; a union of 10+ objects with a unit-typed *key property* maps its values to members once, tsc's getKeyPropertyName: `ty_union_key_property()` / `ty_union_member_for_key()`, which `===`, `switch`, predicate narrowing and relations to the union look up first), all through one table of **type facts** (`type_facts()`, tsc's `TypeFacts` bit for bit, strict and non-strict) that `&&`, `||`, `??` and `!` in `ty/expr.c` use too (`ty_non_nullable()`, tsc's getNonNullableType, is `ty_non_nullish_part()` of them under strictNullChecks: null, undefined and void go, a generic that may be nullish becomes the lib's `NonNullable<T>`; `ty_non_nullable_if_needed()` is getNonNullableTypeIfNeeded); switch clause nodes narrow by their cases (by value, `switch (typeof x)`, `switch (true)`, discriminant); call nodes narrow by assertion signatures (`asserts x`, `asserts x is T`) and answer the *unreachable never* (`TY_UNREACHABLE_NEVER`, which a top-level query turns into the declared type) after a `never` call; branch labels union their antecedents (the bypass edge of a switch last, and only if the switch isn't exhaustive); loop labels iterate to a fixpoint (`Checker.flow_loops` is the stack of loops in progress, a loop met again through its back edge answers the *incomplete* union so far, finished loops are cached by `(label, reference key)`, keys are interned from symbol + property names + declared/initial type); `FLOW_SHARED` nodes are remembered for the rest of one query; a start node of a function expression continues in the flow the function was made in for `const`s, and for parameters and `let`s past their last assignment (`Symbol.last_assignment_end`). The hooks are `identifier_flow_type()` (the tail of tsc's `checkIdentifier()`: only variables and parameters, assignment targets keep the declared type, the initial type is `declared | undefined` unless something says the variable is initialized, and an `undefined` that survives is TS2454, reported by `identifier_expr_typecheck()`) and `access_flow_type()` for property and element access. Destructured discriminants and dependent parameters (`discriminant_access()`, `ty_destructured_narrowed_type()`, `ty_parameter_narrowed_type()`) query flow with a placeholder reference (`FlowQuery.pattern`/`parameters_of`) standing for tsc's pseudo references. Constraint positions (`constraint_position`) are marked by the resolve walk, and so is `IdentifierExpr.outer_reference` (a reference from a nested function); isNeverInitialized is `!symbol->is_assigned`, and "outer variable assumed initialized" is decided at the start node (`Symbol.flow_start`).
- **Auto types and evolving arrays** (tsc's autoType/autoArrayType): under noImplicitAny (or in JavaScript) an unannotated, unexported `let x;` / `let x = null` is `TY_AUTO` and `let x = []` (const too) the auto array `ty_auto_array()` (`any[]` of TY_AUTO, made with the global Array type when the checker starts so it has the lowest array id, like tsc): `auto_type()` in binding.c. Control flow gives them what was assigned last; `[]` assigned (or initialized) is an *evolving array* (`TY_EVOLVING_ARRAY`: element type, final array cached), which the binder's `FLOW_ARRAY_MUTATION` nodes (`x.push(v)`, `x.unshift(v)`, `x[i] = v` with a number-like i; only for objects that may be auto-typed, `flow_array_mutation()`) grow and labels join (`union_or_evolving()`). It never leaves a flow query: `ty_flow_type()` answers its final array type (subtype reduced; the auto array if nothing was pushed), or the auto array itself for an *operation target* (`IdentifierExpr.evolving_op`, set by the resolve walk: `x` of `x.length`, `x.push(...)`, `x[i] = v`). A read that is still the auto type/array is `any`/`any[]` with TS7034 + TS7005 (`identifier_flow_type()`); `x!` starts from `undefined` and takes the non-nullable type. A closure sees a `const x = []` as the auto array (its flow doesn't continue outside).
- **Expression memos vs loops**: the engine asks for expression types (what was assigned, what `x ===` is compared with) through `ty_flow_expr_type()`: a finished memo, else an evaluation in *uncached mode* (`Checker.flow_uncached`: `ty_expr_type()`/`check_with()` neither read unfinished memos nor store anything, all the way down), because `x = f(x)` in a loop asks for `x`, which asks the loop, which asks for the type of `f(x)` while it is being evaluated further up the stack, with an incomplete `x`. The value of a plain `x = v` is checked with the type its target gives it (`ty_flow_assigned_value_type()`, `ty_assigned_value_context()`), as the walk does, so what an assignment narrows to doesn't depend on whether the walk reached it yet. Its results are cached like tsc's `flowTypeCache`: for good when no loop is in progress, else for the walk of one back edge (keyed by back-edge generation in `Checker.links`; stale generations stay until the checker is dropped or recycled). Declarations (every non-expression `LazyType`, inferred return types) evaluate self-contained instead (`ty_flow_isolate()`: not uncached, no loop in progress as far as they can see), so what they remember is complete, and a declaration that depends on itself through a loop (`while (c) { const y = x; x = y + 1; }`) is circular like in tsc. `e as T` doesn't evaluate `e` for its type (tsc defers it too); the statement walk checks it with `T` as the contextual type.
- **Diagnostics of unfinished loops**: tsc reports whatever an evaluation under a loop in progress finds (getTypeOfExpression is a full check, its diagnostics collection drops only identical ones), so an assigned value's errors about the loop's *partial* types stay (`y = arr[y]` with `let y` is TS2538 'undefined' though y ends up any). `compute()` runs the walk's own checks of a property/element access (`expr_property_access_errors()`) and of a spread (`expr_spread_errors()`) on the partial types when `ty_flow_partial_reports()` (uncached, a loop in progress, the checker checking the expression's file in its typecheck phase: K-independent), into the checker's diagnostics; the final sort-and-dedupe drops what the walk says again. A missing property is said once per access, the first time (tsc's reportNonexistentProperty: `KEY_FLOW_PARTIAL_NO_PROPERTY` makes the walk drop its own).
- **Type predicates** are syntax on the function (`FunctionImpl.predicate`, a `TypePredicateNode`; `ret` stays `boolean` / `void`, so everything about return types is unaware), resolved against the parameter list in the resolve walk, and `TyPredicate` on the signature (`signature_predicate()`: lowered or instantiated on demand, never inferring a return type). They are displayed, related (a predicate target wants the same predicate) and inferred through. What a *call* means for control flow is `call_effects()` in `ty/flow.c` (tsc's `getEffectsSignature()`, remembered per call): the callee of a call statement is typed from declarations alone (`type_of_dotted_name()`: every name needs an explicit type, no flow analysis, which is what keeps `assert(x)` from asking for itself), one non-generic signature is taken as is, anything else is resolved by `ty_call_effects()` (`call.c`) in uncached mode. `narrowed_type()` is tsc's `getNarrowedType()` for predicates and `instanceof` (the latter by class derivation: `ty_has_base_type()`).
- **Property access checks** (`check_access()` in `ty/check.c`, reached from `expr_typecheck()`): a possibly `null`/`undefined` object is TS18047-18049 (the object is an entity name, `expr_is_entity_name()`) or TS2531-2533, an `unknown` one TS18046/TS2571, and a property that `ty_access()` doesn't find on the *whole* object type (every member of a union, any member of an intersection) is TS2339, with the first union member that lacks it as elaboration. What remains (bracket access) is in `agents/hacks.md` (`check_access`).
- **Member modifiers** (`ty_check_member_modifiers()` in `ty/check.c`, tsc's checkPropertyAccessibility and isAssignmentToReadonlyEntity): class members carry `PROP_PRIVATE`/`PROP_PROTECTED`/`PROP_STATIC`/`PROP_ACCESSOR`/`PROP_FIELD` (an accessor's writes go by its setter's `PROP_SET_*`), which mapped types and spreads drop. `member_refs()` finds the property on every member of a union/intersection (tsc's synthetic property: readonly if any union member's / every intersection member's is) without making types. Where the access is comes from the resolve walk: `PropertyExpr.enclosing_class` (then `ClassDecl.outer_class`, from `scope_enclosing_class()`), `in_constructor_of` (the flow container is that class's constructor, IIFEs inlined: `FlowBuilder.constructor_of`) and the `this` parameter / contextual-`this` function. A readonly assignment target's type is the error type (`ty_is_readonly_assignment()` in `ty/expr.c`), like `new` of an inaccessible constructor (`ty_constructor_accessible()`, TS2673/2674). A union whose members declare a private/protected property differently has no such property (`ty_union_non_public_conflict()` in access.c). `super.x` is typed (`super_type()` in ty/expr.c: the base instance with `this` as this-argument, in a static member the base constructor); where tsc says `super` is illegal (`Scope.no_super`: computed names, member decorators, constructor parameters; `super()` outside a constructor) it is `any`. `super(...)` resolves against the base constructor (with the heritage clause's type arguments) and is `void`. Where `super` may be used is decided while resolving (`resolve_super()` in expr.c, tsc's getSuperContainer/isLegalUsageOfSuperExpression over scopes, `Scope.no_super` says why a computed name, decorator or constructor parameter is special), as is `this`/`super.x` before `super()` (`check_before_super()`: `flow_is_post_super()` walks the flow graph built so far backwards, tsc's isPostSuperFlowNode). `FunctionImpl.first_super_call` is for TS2377/TS17005. Relations are nominal for non-public properties (`modifiers_related()` in relate.c, tsc's propertyRelatedTo: a private property only relates to its own root declaration, a protected one to one declared in a derived class), and an intersection with separately declared same-named properties, one private, is `never` (`has_conflicting_private()` in checker.c). Two copies of the same package version resolve to the first (`ResolvedModule.package_id`, `Program.files_by_package_id`), so their classes are the same.
- **Private names**: `#x` declared in a class is a name of its own per class, like tsc's `__#12@#x`: `ty_private_name()` makes an `Atom` with the text `#x` that isn't the interned one (keyed by the class symbol), so props are told apart by pointer as always and still print as `#x` (`ty_private_name_class()` goes back; `keyof` skips them, a static one isn't inherited). The resolve walk finds the innermost enclosing class that declares an accessed `#x` (`PropertyExpr.private_class`, `PrivateNameExpr` for `#x in o`); `ty_access_key_type()` is the key an access looks up. TS18013/18014/18016/2803 come from `ty_check_private_name_access()`, TS18028 from `class_decl_typecheck`.
- `TTTT_DUMP_FLOW=1` prints every container's graph in creation order with the references that got each node: start here when narrowing looks wrong.

### Engine
tttt includes a JavaScript interpreter that evaluates an AST. It's not fast, standards complaint, tested, complete, or a priority.

## Phases
The process of loading and typechecking TypeScript code is done in several phases

### Load from the filesystem
Cleat's `Fs` abstraction allows tests to mock the filesystem, so the `Program` sees multiple files without the test runner having to write them to disk. The mock lives in [src/test/mock_fs.c](src/test/mock_fs.c); everything else uses the `fs` global. Each `Program` wraps the `Fs` it is given in a `CachedFs` (`src/cached_fs.{h,c}`, tsc's cached compiler host): `exists`/`is_reg_file`/`is_directory` answers are remembered by path (sharded locks, the load pool probes from every worker), anything that writes forgets them all. The program and its resolvers only see the cached one.

Loading is sequential and depth-first (`program_add_source_idempotent()`: parse a file, then load what it imports, then
append it to `source_files_ordered`), and that order decides everything downstream (file order, error order, the
package-id dedup). **Two phases, like tsgo's filesparser**: the loader loads everything reachable, recording each file's
first package id (`SourceFile.package_id`: any resolution's, relative ones inside node_modules included) and what it
reached from each file in order (`SourceFile.load_children`, `Program.load_roots`); when two files got the same id,
`program_collect_files()` (at the end of `program_load_automatic_types()`) walks that graph depth-first like tsgo's
collectFiles: the first file with an id stands for it, a later one becomes a redirect (`package_redirect`, imports of it
mean the first, `ModuleRef.redirected_from` names it) and the walk skips its imports, so a redirect and what only it
reaches are `excluded`: loaded and findable by path (a redirect as itself, the rest not at all), never bound or
reported, not in `source_files_ordered`. With `--threads N > 1` (the CLI's default; the harness's is 1, `baseline_tests --threads N` to use
it) a **load pool** (`src/load_pool.{h,c}`) runs beside it as a cache warmer: N workers read and parse queued paths
(`program_make_source()`, the part of loading that only reads the program; errors into a per-file `ErrorCtx`) and
queue what the loader will probably load from them (`program_load_ahead_from()`: resolved module refs, reference
directives). The worker's resolutions stay on the file (`SourceFile.preresolved`) and the loader takes them in
`program_load_module_ref()` instead of asking the resolver again (same arguments, so the cache's answer; the shared
resolver's lock was the loader's contention with the workers). The loader takes a preparsed file when it gets there (waiting, and parsing other queued files meanwhile, if
it is in flight) and merges its held errors at that point, or parses the file itself. A wrong guess only costs a
parse, so the output doesn't depend on the pool. `program_load_ahead()` queues the libs, roots and automatic types up
front; workers take files of at least 128 KB first, biggest first (`program_set_file_size()`, a `stat` the workers
make), so one big file (tsc's `checker.ts`, `lib.dom.d.ts`) isn't started last, and the rest by rank: the index path to
the file from the loader's first wants (a root's i-th import is [root, i]), the order the loader takes them in
(`TTTT_LOAD_POOL_INLINE=1` lists the files the loader parsed itself, with their rank and how long they sat queued). The resolver is shared (its caches are under a lock) and so is
the program's cwd (`program_cwd()`); `compiler_options()` is per thread. `program_load_ahead_from()`'s guesses are a simplified copy of `program_load_module_ref()`/`program_handle_statement()` (`TTTT_LOAD_POOL_STATS=1` shows the hits); sizes come from `stat()` in main.c, the harness queues FIFO.

**Source text is mapped, not read** (plan 80): `program_make_source()` maps files read through the real `fs`
(`source_text_map()`, MAP_PRIVATE, read-only) unless a content mapper reads them or they are UTF-16; `contents` is then
a long `cstr` pointing at the mapping that must never be dropped or changed (`SourceFile.text_mapping`;
`source_file_drop()` unmaps). Mappings lie end to end in reserved 256 MB segments (at most 16k files, then read()), so
`source_texts_release()` drops every text's pages from the process with one madvise per segment: after names and at
every checker recycle. They stay in the page cache and come back on the next read (a minor fault), so the process holds
only the text read since (vscode K1 peak -100 MB, +1% wall). The terminator the parser reads is the zero tail of the
mapping's last page: a file whose size is a page multiple is read() instead. Like clang's MemoryBuffer, a file another
process changes during the run is read changed (SIGBUS if truncated); tttt's own writes (declaration emit) call
`source_text_detach()` first, which moves a mapped file's text to a memfd at the same address.

### Parse
The parser creates an AST from the source code string, see below.

### Resolve names
`program_resolve_names()`, three steps over all files. Link is sequential, declare mostly parallel; the resolve walk (85-90% of the phase) runs on `--threads` threads for TypeScript files (plan 45, below). The contract: a walk writes only its own file's AST and symbols (what is shared anyway: "Parallelism contract" below).
1. **Declare** (`*_add_names()`): every file gets its scope (a module also its module symbol), and the declarations of files, namespaces, enums and `declare global` blocks become symbols. Same-table conflicts are reported here. A TypeScript module that declares nothing outside its own tables (`declares_in_isolation()`: no `declare global`, `declare module "m"`, `export as namespace` or top-level expando assignment) declares on the resolve threads into a `ResolveShard` of its own, merged in program order (`program_declare_files()`); `Binder.isolated_declares` makes one that reaches a shared table `log_error()`.
2. **Link** (`binder_link()`): `export *` tables are flattened and every alias is resolved, so that nothing writes to a symbol afterwards; import conflicts (TS2440) are reported.
3. **Resolve** (`*_lookup_names()`): the deep walk. It makes the function and block scopes as it enters them (declaring their names first, so uses before the declaration resolve) and stores on every identifier the symbol it found plus the symbol that has the meaning it is used with (`target`). The same walk builds the control flow graph, so it visits statements and expressions **in evaluation order** (`for`: init, condition, body, afterthought; an IIFE's arguments before its body), see "Control flow" below.

**The parallel walk** (`program_resolve_walk()`): files are walked in any order (biggest first) by a pool,
each into a `ResolveShard` of its own (thread-local `resolve_shard`): `binder_arena()` is the thread's arena,
`binder_errs()` the file's `ErrorCtx` (parent: the program's, frozen meanwhile), new symbols and pending reports go to
the shard's lists. What depends on the files walked before is *deferred* into the shard: spelling suggestions (every
not-found report and misspelling: they look at every file's globals) and expandos (`f.x = v` in a function body) whose host
another file can see. A JavaScript file defers *all* its assignment declarations (`this.x = v`, `F.prototype.x = v`,
expandos, `Object.defineProperty`, a script's `this.x = v`, `@constructor` marks of symbols not local to a function:
`DEFERRED_JS_*`), whose hosts may be other files' and which read what earlier ones declared: replayed in walk order,
nothing in between, and the declaration a walk had yet to reach is linked then (`DeferredEvent.link`,
`expr_link_assignment_declaration()`); `require`'s symbol is made before the walks. Then, in program order, each file's
shard is replayed and merged (`resolve_shard_merge()`), and the files whose class or interface shares type parameter
symbols with an earlier declaration in another file (`binder_mark_serial_resolves()`) are walked on the main thread. The order is the same
at any thread count (the suite runs it at one); `TTTT_PARALLEL_RESOLVE=1` uses the threads even for a few files.

**Parallelism contract** (what the walks share by design). A JavaScript file's walk never sees what its deferred
assignment declarations declare (nothing there reads it). Deferred expandos are those whose host isn't private to the
file (`expando_host_is_private()`, conservative). Cross-file writes: `Symbol.referenced` (atomic OR),
`has_assignment_flow_containers` (atomic store), `flow_start` (written only by the first declaring file;
`outer_reference` treats a symbol first declared elsewhere as outer). A walk's scratch `ErrorCtx` can't be a deferred
report's target (`shard_lasting_errs()` sends it to the shard's discarded one; scratch contexts are dropped, never
merged). Guards: the program's ctx is `frozen` and `Binder.frozen` is set during the walk, so a report there, a new
binder symbol or a first alias resolution `log_error()`s. Not a proof: run TSan (see "Typecheck") after touching it.

Imported files are discovered while loading, from the parser's list of module names (`SourceFile.module_refs`; `program_handle_statement()` only follows `/// <reference>` directives and decides whether a file is a module), before any of this. Between declare and link every `ModuleRef` is resolved to its module symbol, which needs the ambient modules of all files.

### Module resolution
`src/module_resolution.{h,c}` is tsc's `moduleNameResolver.ts`: a **pure function of (filesystem, options, containing file, name, mode)** that knows nothing of programs, syntax or symbols. `module_resolver_resolve()` tries `paths` / `baseUrl` / `rootDirs` first, then by `moduleResolution`: classic (next to the importing file and each ancestor, then `node_modules/@types`), node10 (file with extension probing and `.js` -> `.ts` substitution, directory through package.json `typings`/`types`/`main` and `typesVersions`, `node_modules` walking up with TypeScript before JavaScript, `@types` with `@scope/x` as `scope__x`), node16/nodenext/bundler (package.json `exports` / `imports` with conditions and patterns, self names, `.mts`/`.cts`, no extension or index probing for ESM imports). `moduleSuffixes`, `resolveJsonModule`, arbitrary extensions (`a.d.css.ts`) and symlinks (a `RealpathFn` the program is given: libc's in the CLI, the mock filesystem's in tests; applied to what is found in node_modules, unless `preserveSymlinks`) are in there too. `module_resolver_resolve_type_reference()` is `/// <reference types>` and the `types` option (type roots first, then node_modules), `module_resolver_automatic_types()` lists what is included without being asked for, `module_resolver_file_format()` says whether node16 takes a file for an ES module. The result carries *why* it failed where tsc has a message for that. The only state (shared by the load pool's threads, under a lock held only for lookups and inserts) is a package.json cache by directory (`src/json.{h,c}`: a small JSONC reader with ordered members, because the order of `exports` conditions matters) and a cache of results by (containing directory, mode, name), like tsc's per-directory resolution cache: nothing a resolution looks at depends on the file within the directory, and the filesystem and options don't change while a program loads. A `./`/`../` name that means a file is also cached by (the path it joins to, mode) (`resolves_by_joined_path()`): nothing else of the directory is consulted for it, so a file imported from a thousand directories is looked for once.

`program.c` is the one caller: `program_load_module_ref()` resolves every `ModuleRef` of a loaded file in the mode its syntax asks for (`ModuleRef.syntax`: `import x = require()` is always CommonJS, `import()` always ESM, anything else the format of the file), adds TypeScript results to the program and records anything else on the ref (`ModuleRef.failure`: JavaScript without `allowJs` or from a package, `.tsx` without `jsx`...). A `.json` result (resolveJsonModule) is loaded as a source file too (`SourceFile.is_json`): the parser makes its one expression an `export =` statement. `import * as ns` of an `export =` module gets tsc's interop shapes in `namespace_import_type()` (lower.c: a synthetic `default`, or only the default for an ES module importing JSON). Diagnostics are reported from the ref when names are resolved, not while loading (`module_ref_report_unresolved()`: TS2307, TS2792 for classic, TS7016, TS2732, TS2834/TS2835, TS6142, TS6263; `module_ref_report_resolved()`: TS5097, TS1479/TS1471), so an unresolved import is no reason not to typecheck. `program_load_automatic_types()` adds the `@types` packages after the roots. With `noResolve` nothing is added, but names still find files that are roots.

`src/tsconfig.{h,c}` reads a tsconfig.json: `extends` (paths and packages; one that can't be found is a diagnostic and the rest goes on, `tsconfig_load_diagnosed()`), `compilerOptions` (path options made absolute, `${configDir}`), and the root files from `files` / `include` / `exclude` (the walk only enters directories an include pattern can match something inside, `glob_may_match_inside()`; a found `a.d.ts` or `a.js` next to `a.ts` is left out, tsc's extension priority; `.json` files only for include patterns ending in `.json`, with resolveJsonModule), and `references` (`tsconfig_load_references()`, see "Project references"). The CLI takes `-p`, or finds the nearest tsconfig.json when it is given no files; the test harness applies a `tsconfig.json` unit under the test's directives and takes its files as the roots, like tsc's `compilerRunner.ts`. The harness also mirrors tsc's virtual filesystem: relative `@Filename`s live in `/.src`, which is the working directory (`@currentDirectory` changes it), `@link` / `@symlink` make symlinks in the mock filesystem.

### Content mappers
tsgo 7.1's `contentMappers` (`src/content_mapper.{h,c}`): with `--runExternalCode`, a tsconfig names
packages (resolved from the config's directory, their package.json's `typescript.contentMapper` manifest) whose
program turns files of other extensions into TypeScript. The extensions are root files (`has_source_extension()`) and
module names that name the file itself (`try_adding_extensions()`). `program_make_source()` sends a mapped file's
text to the mapper (`ContentMapperHost`, one per program: a child process per mapper speaking JSON-RPC with LSP
framing over a socket that is its stdin and stdout, behind a lock for the load pool) and parses the reply under the
file's own name as `<file><virtual extension>`; `SourceFile.content_mapped` keeps the span map and the original text
as a file of its own (`ContentMapped.original`, registered, never in the program). The mapper's diagnostics point into
that original; the compiler's are mapped back there by `content_mapped_map_error()` just before printing (CLI:
`print_diagnostics()`; harness: the `.contentmapper` baseline, which the errors component compares, and the errors
baseline leaves mapped files out like tsgo's runner). Diagnostic directives suppress semantic diagnostics in their
virtual ranges (`program_apply_content_mapper_directives()`); supplemental outputs are files of their own,
`<file>.<i><ext>`, added after the file's imports (`program_make_supplementals()`, `program_add_made_source()`), named
by the canonical file in diagnostics. Failures follow tsgo's fileLoader: an initialization failure is one global TS18099
and the mapper's files are empty; a transform failure is TS18069 on an empty placeholder, the fifth one adds TS18070 and
the mapper isn't used any more (counted per tsconfig entry, in program order: the load pool leaves mapped files to the
loader, costing the transforms their parallelism, and tttt reports the first 5 failing files where tsgo's goroutine order
is nondeterministic). Diagnostics of a mapped file and of its original text sort together by offset (`span_cmp()`: one
file to tsgo); a mapper's location-less program diagnostics (TS18099/TS18070) are kept next to the syntactic ones
(`drop_diagnostic_kind()`, tsgo's GetDiagnosticsOfAnyProgram). The suite runs tsgo's Go test mappers as a process:
`test/oracle/tttt-test-mapper` (`thirdparty/typescript/built/tttt-test-mapper NAME`) is put in front of a manifest's
`exec` (`content_mapper_set_launcher()`, `TTTT_CONTENT_MAPPER_LAUNCHER`).

### Project references
`src/project.{h,c}` is the only code that knows about more than one tsconfig (plan 41). A `ProjectSet` loads a config
and, recursively, every config its `references` name (`tsconfig_load_references()`; references aren't inherited
through `extends`), each once by absolute path; a project's root files are listed on first use
(`project_set_root_files()`, which the CLI also takes its roots from, so each include walk runs once).
`project_set_build_order()` is tsc's `-b` order (depth-first, references first, TS6202 on a cycle unless `circular`).

A program checks one project and reads the projects it references, transitively, like tsc's command line
(`program_set_references()`): a resolution (or root file, or `/// <reference path>`) that lands on a referenced
project's source is swapped for its output declaration file (`program_redirect_resolved()`, `program_load()`), read
like any `.d.ts` of the program if it exists, else a TS6305 at the import (`MODULE_REF_NOT_BUILT`, the module is
`any`) or a global one for a root file. `ProjectRedirects` (per program) holds every referenced project's root files
and the output declaration path of each (getOutputDeclarationFileName: `declarationDir`, else `outDir`, below
`rootDir`, composite's config directory or the common source directory; next to the source without either), mapped
both ways. An output declaration file (or a referenced project's own `.d.ts` input) is `SourceFile.resolution_project`:
its module names resolve **from its source** (`program_resolution_containing()`, tsgo's getRedirectForResolution)
with a resolver with *its* project's options (`program_resolver_of()`, `program_options_of()`); its const enums aren't
ambient if that project preserves them (`reference_preserves_const_enums`), an ES module importing it has no synthetic
default if its project emits ES modules (`reference_emits_esm`). Module specifiers name it by its source, the output
first (`program_module_specifier_ending()`), and a referenced project's root file, `.json` too, is never the
program's to emit (`emit_source_may_be_emitted()`).

**`-b`** (plan 87) is tsc -b: each project in build order is its own program that checks, emits its declarations **in
memory** (`EmitStore`, `emit_store.h`; under the conditions tsc writes them: not with noEmitOnError and errors, not a
blocked path), and the programs after it read those like `-p` reads written ones. Each program's `Fs` is an
`EmitView`: the disk with the files of the build positions it sees on top (their directories existing; relative paths
absolutized against the cwd, `..` normalized for the inner fs; lookups through a `node_modules` link by the realpath of
the deepest existing ancestor; `emit_view_real_path()`/`emit_view_file_size()` are the program's realpath and size
callbacks; directory listings show only the disk). A program sees its references, transitively, and every project at
least `--builders` places earlier (default 4, tsgo's builders: they take projects in build order and wait only for
references, so an unreferenced project's outputs, a test config importing another package's `dist`, exist by timing;
tttt's window makes that deterministic, `--builders 1` is tsc 5's sequential `-b`). Build threads take the first ready
job in build order (`build_thread()`), each waiting until everything it sees is done; a position's texts are freed
once its last reader is (`build_job_done()`). What tsgo's emit writes downstream reads, errors inside emitted
declarations and tsgo's own emit bugs included, follows from that. `scripts/scenarios.py` also replays tttt's own
scenarios (`test/scenarios`); `TTTT_BUILD_TIMES=1` prints each job's start and end.

Divergences of `-b` by design: the window above (tsgo races), never stale outputs (tttt always builds everything, no
tsbuildinfo), nothing but declarations emitted (a config that also emits JavaScript gets its declarations into the
store only).

The CLI (`main.c`) prints like tsc's: every diagnostic a program reports is collected (`report_errors()`), then sorted
and deduplicated by file path like tsc's sortAndDeduplicateDiagnostics (`error_vec_sort_and_dedupe()`) and printed
(`print_diagnostics()`) as `--pretty false` (`error_format_plain()`) or pretty (`error_format_pretty()`, the default
on a terminal), with tsc's summary at the end when pretty (`ErrorSummary`, gathered across `-b`'s projects). Nothing
else goes to stdout; exit codes are tsc 7's (0, 1 with any diagnostic, 4 for a reference cycle under `-b`).
`scripts/clidiff.py` diffs the output byte for byte against tsc's. `-p` on a config with references checks that
project with the redirects; on a solution config (no files, only references) it says nothing and exits 0. `-b [PROJECT...]` checks each project in build order as its own program,
freed when done (release builds otherwise leave the last program to the exit; `program_drop()` frees the files on the
program's threads), going on past errors (tsc 5.6+; `--stopBuildOnErrors`). Up to J projects whose inputs are done are
checked at once (2 with 4 threads, each program on threads/J), each into an `Output` buffer that the main thread
prints in build order: the output depends only on the static visibility above, which only an explicit `--builders`
changes (like tsgo's). The project set's root
files and every program's `ProjectRedirects` are made before the build threads start, which only read them. The config diagnostics of references (TS6053, TS6306, TS6310) are reported on the program's
own config; composite's TS6307 and rootDir's TS6059 (`program_verify_project_files()`) go at the import that brought
the file in (`SourceFile.included_at`). `scripts/scenarios.py` replays the first command of tsc's own tsbuild/tsc project
reference baselines against tttt; `scripts/realworld.py --corpus tsc-src` is `-b` on TypeScript's `src`.

### Deferred bodies (plan 78)
The parser skips the body of every outermost function of a TypeScript file (TSX too; not JavaScript, not a declaration
file, not unchecked) where that's safe (`skip_body()`: `skip_balanced_braces()` is sure of its end, stepping over JSX
where an expression starts in a .tsx file, `skip_jsx_element()`, and recording that the file has JSX for
moduleDetection; it gives up on `import` and `require`, which would add module names; no expression in a parameter,
whose walk sees the body's names; no string first, a "use strict" prologue; for an expression no `(` in its signature
after the parameter list's own, a function type whose walk asks whether this one is context sensitive). The body is a
`DeferredBody` (`FunctionImpl.deferred`, `body_.deferred`); an IIFE's is parsed after all when the call shows, so is a
constructor's the class's walk looks into (`undefer_body()`). The skipper records the comments it steps over like the
parser (comment directives, declaration emit's comments). The resolve walk (`function_impl_lookup_names_as()`) does
everything up to the body, records the flow builder's state in the DeferredBody and lists it in the file's
`DeferredBodies`; meanwhile every name the signature's walk looks up through the function's scope is recorded
(`Scope.deferred_body`, `note_deferred_signature_name()`).

**Materialization** (`program_materialize_file()`): the first checker that needs a body (`function_impl_body()`,
`function_impl_walked()` for what the body's walk sets: `end_flow`, returns, yields, `contains_this`, constructors'
`return_flow` and `first_super_call`, fields' `ts_assigned`) parses all of its file's (`parse_deferred_body()`, into
the file's AST arena) and walks them in walk order (`function_impl_lookup_deferred_body()`) under the file's lock, in a
`ResolveShard` of its own (`materialization`: a TypeScript function's expandos are its own locals', not deferred) with
the thread's arenas (`binder_materialize_arenas()`); a check materializes its file before it starts. The walk's
pending reports that ask for types (`resolve_shard_finish_materialized()`) run after the lock is released, into the
file's `DeferredBodies.errs`, which `program_typecheck()` merges into the program's (`program_finish_deferred_bodies()`,
with the resolve phase's comment directives).

**Memory and drops** (stage 2): a materialization's memory is an arena of its own (`DeferredBodies.memory`,
`ast_materialize_begin()`): the bodies' AST and everything their walk makes (the binder's arenas are `Arena.ast_backed`
while it runs: symbols, scopes, tables, flow nodes). It is held by the checker incarnations that read it
(`deferred_bodies_acquire()`: `Checker.held`, a bit per file id for the fast path) and dropped by the last one's
`checker_drop()` (`deferred_bodies_release()`): types, links and memos point into the bodies a checker walked, so a body
can only go with them. A drop gives the pages back (`ast_arena_drop()`, no walk; addresses are never handed out
again, so nothing keyed by a node's address meets another node), puts back what the walk wrote outside the bodies
(the function scopes' locals as the signature's walk left them, `DeferredBodies.snapshots`; the `deferred_bodies_undo()`
log: the functions' walk fields, the outer flow nodes' reference counts and labels, fields' `ts_assigned`, a class's
`computed_this_assignments`, the file's expando containers and unused registrations) and makes the bodies pending again;
the next reader materializes them again (the same parse and walk; its diagnostics are dropped, the first's stand).
After a drop a file whose first walk wrote nothing outside the bodies but what a drop puts back per body
(`DeferredBodies.singly`: no expando container, `this` or field assignment in the undo log) is materialized a body at a
time: a checker that needs one body (`function_impl_body()`, `function_impl_walked()`: 95% are another file's inferred
return types) parses and walks that one alone (`DEFERRED_BODIES_PARTIAL`, `DeferredBody.ready`), a whole-file demand
(the file's own check) the rest; the outer flow nodes a body's walk marks are set to what the first materialization's
walks left (`walked_flow_flags`: a node two bodies reference is shared), and once every body of such a materialization
is made its unused registrations are put back in walk order. The memory goes on in the same arena
(`ast_materialize_begin()` again, its chunks counted once). vscode at the defaults re-materializes ~19% of the bytes it
did (0.80 -> 0.16 s CPU).
A body declaration merged into a parameter pins the file (never dropped). At a recycle the new incarnation keeps what
the old one read for other files (`Checker.cross_files`: modules many files import), so it isn't materialized again at
once, if that materialization was made for another file (`AstArena.lasting`). The materializations' 2 MB chunks may be
huge pages (a tenth of what materializing costs): each counts the materializations in it and is given back whole when
the last is dropped (dropping part of a huge page splits it, and the kernel frees it only under memory pressure), so a
lasting materialization comes from a slab of small pages of its own, given back page by page: kept across recycles,
it would keep its chunk of a segment's files alive. The materialize-ahead helpers hold what they made until a checker takes it, at most `AHEAD_LIMIT_KB` of body
source ahead (`TTTT_AHEAD_KB`), then wait until the checkers took most of it. `TTTT_AST_POISON=1` makes a dropped
materialization's pages fault: a reader that doesn't hold it crashes; the suite runs drops with `baseline_tests
--checker-memory 0` (diagnostics only: recycled checkers take the expression types with them).

**Exactness**: a materialization that can be told from the eager parse and walk sets `program_defer_failed()` and the
program runs again without deferral (`check_files()`, the harness's `run_baseline_test_case()`): a parse error in a
body or an end other than the skipper's (syntax errors), a recorded signature name the body declares that the lookup
would have seen from where it was made (`deferred_signature_sees()`: from the parameters no body variable, from the
return type no local type or `var`, `function_local_hidden()`), or a body declaration a not-found signature name's
spelling suggestion could have picked (same filter, by the not-found lookup's meaning). A return type with `typeof`
isn't deferred at all (`skip_body()`: it sees the body's `const`s). An output that needs
every body's syntax errors without checking (gated by syntactic or options diagnostics, `--listFilesOnly`) parses the
unmaterialized bodies for them and drops them (`program_deferred_bodies_parse()`), running again only if one has one
(the rest of a body's diagnostics are semantic, gated). Real code never pays; error runs pay a second parse. The CLI and the harness defer by default (`--no-defer-bodies` for both: `scripts/oracles.py`
runs the suite both ways); `TTTT_DEFER_STATS=1` prints counts at exit (bodies skipped, files materialized,
cross-file materializations, failures, restarts) and each colliding body (`defer: collided FILE:LINE`).

### Typecheck
The AST is now in it's finished state, so we can traverse it looking for type errors. This is the phase when the `*_evaluate_type()` functions are called (via `ty_from_node()` / `ty_expr_type()` -> `lazy_type_get()` -> `lazy_type_evaluate()` -> `*_evaluate_type()`), each returning a `Ty const*`. Before the walk, `ty_init_global_types()` creates the global types tsc's
initializeTypeChecker creates (Array, Object, Function, String, ..., RegExp) in tsc's order: type ids break the stable
type order's last ties, so creation order is still (a little) part of the output.

**Thread safety** is checked, not proven: `scripts/threadcheck.sh` (corpus output at `--threads 1` vs 4, byte for byte), `scripts/checkerdiff.py` (`--checkers K` vs 1), `baseline_tests --checkers 4 --threads 1/4 --dump DIR` (identical), and a TSan build, `meson setup /tmp/tsan --buildtype release -Db_sanitize=thread -Dc_args=-g`, run on the corpora at `--threads 4` and on `TTTT_PARALLEL_RESOLVE=1 baseline_tests --threads 4` (`ulimit -s 4000000`): it was clean on every corpus when checking, loading and the resolve walk went parallel. The frozen guards (`log_error` on a report into the program's ErrorCtx, a new binder symbol or a first alias resolution while checking) catch the common mistakes on the suite. Per-checker caches assumed pure in the type ids, as tsc's: `ty_union` of two types (`KEY_UNION_PAIR`), `ty_intersection` without an alias (`KEY_INTERSECTION_OF`), flow's `assignment_reduced_type` (`KEY_ASSIGNMENT_REDUCED`); a result computed while something it reads is in flight (constraints in `remove_constrained_type_variables`, members for empty-object checks) is pinned. Disable these first when a union or narrowing depends on order.

**--shared-graph** (`program_set_shared_graph()`, `TTTT_SHARED_GRAPH=1`; plan 86 stage 4, off by default): the checkers share one type graph (`ty/graph.{h,c}`) instead of each building its own. Identities (interned types, symbols' links) go into shared tables at creation; memo kinds' entries (`graph_kind_class()`: GRAPH_MEMO) are published as their computation ends (`graph_memo_flush()`), declaration memos into a shared store by slot, variances by groups (`graph_variances_publish()`), relations into shared relation caches. A lazily computed value on a shared object (members, property types, signature resolution, constraints, declared types, inferred returns, conditional branches...) is a write-once `SharedWord` (`ty/overlay.h`): empty, then once a clean value, NONE, or POISON. **Nothing a worker has in flight is visible to another**: its claims and the values it keeps privately live in its own ClaimSet and Overlay, and a worker that finds a word empty computes it itself, so nobody waits and there is no redo. Whether a result may be published is decided by the cheap taint counter (`graph_taint_now`, `taint.h`): a computation that saw a taint event (its own cycle, a private value, a deep-nesting cut, a limit, a done-ness peek that selects a result, per-worker side data: plan 86 "Clean, precisely") keeps its value private and poisons the word; a clean one CASes it in, and a loser adopts the winner's. Without the flag the same words are written whatever the taint, with a state byte next to each for in flight (the default path is today's semantics). A worker whose tainted value lost to another's clean one is "shadowed" (its fast paths read its Overlay first) until its file ends, then hands over to a fresh worker (`graph_fresh_worker()`). The oracles: `scripts/sharedgraph/` (README there: 20-run tables against K1, seeded schedules, the fingerprint-at-publish oracle, TSan, the recheck gate), `scripts/kdiff.py` with the flag. The flag's open items (its K1 cost, the kdiff groups) are plan 86's "Stage 4f".

File-less diagnostics (`error_ctx_global_error_s()`) have a null span and sort first; `error_ctx_error_s()` drops invalid spans and reports from unchecked lib files.

After its files are checked, each checker runs `declaration_diagnostics_check()` (`ty/declaration_emit.c`) on
them with `declaration`/`composite`: the diagnostics tsc's declaration transformer reports, without emitting anything
(plan 40). It walks what a `.d.ts` would contain (the visible statements, then the late painted ones: non-exported
declarations an emitted one names) and ports the syntactic type builder's decisions; with isolatedDeclarations each
fallback is a TS9xxx. Each emitted declaration has tsc's accessibility diagnostic (`Emitting`, the TS4xxx table by
declaration kind). Written types check their entity names (isEntityNameVisible); where the syntactic builder falls
back, the declaration's checker type is printed by `ty_display()` with a `DeclTracker` (`TyDisplay.tracker`), which
reports what tsc's SymbolTracker does: every symbol the printer names (trackSymbol: `symbol_accessibility_at()` in
`symbol_chain.c`, tsc's isSymbolAccessible with hasVisibleDeclarations and isDeclarationVisible), computed names,
inaccessible unique symbols and `this` (TS2527), private members of classes written as type literals (TS4094),
properties that can't be named (TS4118), output past 1M characters (TS7056). In declaration mode the printer reuses
annotations like the types baseline does, prints class expressions and classes it can't name structurally
(WriteClassExpressionAsTypeLiteral) and aliases only when accessible. They go into an ErrorCtx of their own, merged
after comment directives (tsc's getDeclarationDiagnostics is apart from the checker's), and the CLI drops them with
noEmit/noEmitOnError when anything else was reported, like tsc's emitFilesAndReportErrors
(`TTTT_DECLARATION_DIAGNOSTICS=1` keeps them, to audit a corpus with other errors). A program whose semantic
diagnostics are gated (options diagnostics) but that emits declarations is not checked at all
(`program_set_declarations_only()`: every file gets only the declaration walk, like a `noCheck` file), as tsgo's emit
resolver types only what the declarations print; `TTTT_DECLARATIONS_ONLY=1` forces that on any program (CLI and
harness): the written declarations and the declaration diagnostics must not change, the walk doesn't depend on a check.

Where the printer roots a name at `import("...")` of a file (`DeclTracker.track_module_file`), the walk asks how a
`.d.ts` of its file would name that module: `program_module_specifier()` (an import of the file that resolves to it,
else `module_specifier_generate()` in `src/module_specifiers.c`, tsc's moduleSpecifiers.ts in reverse of
`module_resolution.c`: every name of the file through the symlinked directories the program met, a package name
through node_modules unless `exports` blocks it, `paths`, else relative). A specifier through a `/node_modules/` is
TS2742. The same specifiers order the containers a symbol can be named through (getSymbolChain's sortByBestName,
`symbol_chain_set_module_specifier()`); without a walk, files go by their path, as tsc's printer without a host. The
program's `SymlinkCache` learns links from every resolution that followed one (`ResolvedModule.original_path`) and
from resolving the dependencies of the importing file's package.json (per package scope, so the answer doesn't depend
on which checker asked first).

**Declaration emit** (plan 64): with `program_set_emit_declarations()`, a file whose first walk reported nothing gets a
second walk that writes its `.d.ts` into `SourceFile.declaration_output` (tsc writes no declaration file whose
transform reported something). It runs on the checker that checked the file, with the first walk's painted set (so a
painted declaration is written where it is, tsc's transformAndReplaceLatePaintedStatements), and its diagnostics go to
a scratch ErrorCtx. The writer (`emit_*()`) prints from the AST like tsc's printer lays a declaration file out (4
spaces, one declaration or member per line; `newLine` crlf in the harness, which is tsgo's harness default); the types
it writes are what the `serialize_*()` functions decide, written into `Walk.type_out`: the pseudo type where it says
the declaration's type (`ty_display_pseudo()`), else the checker's type. Written annotations go through
`ty_display_node()`. `TyDisplay.multiline` prints object types and type literals one member per line (mapped types the
node builder makes stay single line, written ones don't); `TyDisplay.transformer_node` marks nodes the declaration
transformer visits (written annotations) apart from those the node builder reuses (single line mapped types and tuples,
numbers normalized). Comments are copied like tsc's printer does (`ty/decl_comments.c`): the parser records every
comment's range where declarations are emitted (`SourceFile.comments`), which gives a node's full start (back from its
first token over whitespace and comments); leading comments are those past the first line break after it, trailing ones
those on the node's line, only JSDoc-like and pinned ones (OnlyPrintJSDocStyle) except list elements' intervening
ones. The writer calls them around statements, members, parameters, specifiers; `TyDisplay.comments` around reused and
printed members (properties printed from types copy their declaration's: setCommentRange). A namespace body drops its members' `export`s unless a
painted declaration needs an `export {};` (offsets in `Walk.export_offsets`), a module whose output has no import or
export gets `export {};`. A preserved `/// <reference path>` names the referenced file's declaration output relative to
this file's (`SourceFile.declaration_output_path`, which `program_typecheck()` sets for every file when emitting;
`SourceDirectiveStatement.referenced`). The suite compares it as the `dts` component (`baseline_tests --dts`, the `.js` baselines'
declaration sections, `scripts/dtsstats.py`), real projects with `scripts/dtsdiff.py` (the CLI's writes, in a sandbox), the
CLI's stdout, exit code and written tree with `scripts/clidiff.py --emit`.

**JavaScript declaration emit** (plan 64 stage 6) is the same walk over what tsgo's reparser makes of a JavaScript file.
JSDoc declarations (`@typedef`/`@callback` type aliases, dotted ones' namespaces, `@import`s as `import type`) are
synthesized statements that the parser appends after the statement whose comments hold them; `emit_statements()`
writes them before it, like tsgo's reparsed nodes, without comments, exported in a module (IsImplicitlyExportedJSDocDeclaration). A class
gets a property for each `this.x = v` (or `this["x"]`) its members' bodies assign and it doesn't declare
(`js_this_properties()`, tsgo's collectThisPropertyAssignments: the member symbols' first assignment in source order,
with its statement's comments, skipped where a base class member already says it), and its expandos (`C.x = v`) as a
namespace after it. `@overload`s are a function's or method's declarations (`js_overload_count()`), the implementation
dropped. A CommonJS file's exports come first (tsgo's appendCjsExports), collected by `collect_commonjs()` from the
whole file in source order: the last `module.exports = v` through `emit_export_assignment_of()` (the `export default`
writer: `export = x`, a function or class declaration of the expression's name or `_exports`, else `declare const
_exports: T`), then each `exports.x = v` once per name (`emit_commonjs_member()`: `export { a as x }` for a top-level
alias, a class declaration (in a `_ns` namespace when its name differs from the export's or its members name it), `export
declare var x: T`, or `_exported`/`_default` variables), each in a namespace of the `export=`'s name where it has one.
`const x = require("m")` is `import x = require("m")`. The first walk paints what all of these name
(`check_commonjs_exports()`, into a scratch context: `check_js_commonjs_exports()` reports what the exports' types
name), and reports the rest of a JavaScript file's diagnostics like a TypeScript file's. JavaScript annotations go
through tsgo's node builder (`TryJSTypeNodeToTypeNode`), not its transformer: `w_node()` sets `TyDisplay.builder_part`
(single-line mapped types and tuples, no `@property` description comments), `w_node_visited()` is for what the
transformer visits in JavaScript too (a type alias's type, heritage type arguments, index signatures); a JSDoc name
the JSDoc fallback makes a type of (a constructor function, a `require`d `module.exports = { X }` property) isn't
tracked (`ty_jsdoc_name_is_type()`), so its import is elided like tsgo's. A `@typedef`'s/`@callback`'s literal members
get their tags' descriptions as comments (`Interface.jsdoc_described`, preservePartialJsDoc). The suite's `dts`
component counts JavaScript tests too (`baseline_tests --dts-js` shows their diffs, `scripts/dtsstats.py --js`).

**Declaration maps** (`declarationMap`, plan 64 stage 5, `ty/decl_map.c`): tsc's printer maps the start (past trivia) and
the end of every node it prints that has a source position, and of every comment it copies; what the transformer or
node builder makes up has none (synthesized modifiers, inferred types, new member nodes), what it reuses keeps its range
(names, written annotations, the source's own modifiers when ensureModifiers leaves their flags alone, a node-builder
type parameter's name: its declaration's). The writer and `TyDisplay.map` (the file being written) put a *mark* into the
output text where a node starts or ends: `DECL_MAP_MARK` (0x01) and the source offset in 8 control bytes, so marks
travel with the text through the writer's splices, temporary buffers and erasures (`erase_text()` erases the marks
among the characters it takes back; code that looks at the output's last character skips marks:
`decl_map_last_char()`). `decl_map_take()` takes them out at the end (before CRLF and the BOM) and encodes them like
tsgo's `sourcemap.Generator` (whose dedup of mappings at one generated position is part of the format), columns in
UTF-16 units. Reused type nodes know their start from `TypeNode.pos` (the parser's, in the header's free bytes) and
compute their end from their parts (`decl_map_type_end()`, scanning past `)`/`>` where needed); declarations use their
spans, scanning the source for tokens the AST doesn't keep (modifiers: `source_modifiers()`, `{` of a named import
list, `?`, `...`). `program_set_declaration_paths()` names the source in the map and the trailer's URL
(`SourceFile.declaration_map_source`/`_url`: sourceRoot, mapRoot); the CLI writes `SourceFile.declaration_map` beside
the `.d.ts`, before it. The suite's `dts` component compares the `.js.map` baselines' `.d.ts.map` sections,
`scripts/dtsdiff.py` the maps of real projects (bucketed by their first differing mapping), `scripts/mapshow.py` decodes
and compares two maps.

## Memory Management
The source code and ASTs of all parsed files is kept valid until after all above phases have finished. The AST holds references to the code (via spans) and any types created from the AST may hold references into the AST, so it would not be safe to free either the code or the AST while anything created from it remains in use. Furthermore the AST should not be structurally modified after parsing to keep pointers valid (ex pushing to a vec that's part of the AST is generally unsafe, since it may trigger a reallocation and invalidate other elements).

### Node layout
Nodes are sized for the common case (plan 43 cut the AST and binder by a third to a half): what few nodes need sits in
one owned side struct per node kind (`FunctionImplRare`, `InitializedBindingRare`, `IdentifierTypeRare`,
`InterfaceMember`'s index/mapped keys and accessor box, `ScopeRare`, `SymbolRare`, `PropDeclRare`...), read through
`*_rare()`, which returns a shared all-null static when there is none, and written through `*_rare_mut()`, which
allocates on first write (only from the parser or the single-threaded resolve walk for AST nodes); optional children are
null pointers rather than empty inline nodes; spans that must lie in the node's own file are packed as u32 offsets
(`expr_outer_span()`, `FunctionSpan`, `Binding`'s type and element spans), and an `IdentifierExpr`'s name is its `Expr`'s
`inner_span`. A `Ty` is allocated with only its kind's variant (`ty_size_of_kind()`). Parser lists are built with
`list_push()` and finished at their exact size by `shrink_list()`.

**The AST lives in per-file arenas** (`ast_alloc.h`, plan 63): while `parse_file()` runs, its thread's `ast_malloc()`
family bumps out of the file's `AstArena` (`SourceFile.arena`); elsewhere it is plain malloc. Every AST list type is
declared with `#define g_allocator ast`, node boxes are made with `ast_new()` and freed with `ast_delete()`/`ast_free()`
(with the allocated size: a dot `PropertyExpr` is short). Arena memory lies in 256 MB address segments marked in
`ast_segment_map`, so `ast_owns()` is one load and frees and reallocs take either kind at any time: arena memory is
never passed to free() (glibc aborts if it is), a later phase's realloc of an arena list copies it out to malloc, and
the drop functions still walk the AST to free its malloc'd parts (cstrs, what resolve attached), the arena parts being
no-ops. The parser seals the long strings it keeps (literals, template texts, object keys: `ast_cstr_seal()` copies a
cstr's out-of-line text into the arena), the resolve walk's lists and boxes are the AST's too (`AstSpans`,
`AstSymbols`, `AccessSite`, a generator's yields): a materialization of deferred bodies is then wholly in its arena.
AST strings are dropped with `ast_cstr_drop()` (`value_drop()` too) and taken out of the AST with `ast_cstr_take()`. During the parse freed blocks are reused (exact size classes up to 1 KB, best fit with splitting above:
speculation's dead nodes and outgrown lists); the blocks still free when the file ends are lost (~3% on vscode).
Threads bump files end to end through 64 MB slabs, prefaulting 2 MB ahead (`MADV_POPULATE_WRITE`: a trap per page was
a tenth of the parse; the checker and binder arenas prefault a MB ahead too), each 2 MB as a huge page while
`huge_pages_take()`'s budget (the free blocks of order >= 9 in `/proc/buddyinfo`) lasts: past it, a madvised fault
compacts memory synchronously, which cost vscode a third of its wall time on a machine with fragmented memory; `ast_arena_drop()` gives a file's whole pages back (`TTTT_AST_POISON=1` makes them fault instead,
to find readers of a dropped AST) and its addresses are never reused. `TTTT_AST_STATS=1` prints the arenas' churn at
exit; `TTTT_AST_MALLOC=1` turns them off (the AST in malloc, which `scripts/memtrack.sh` sees: it sets it).
`scripts/arenasites.sh` shows the binder and checker arenas. Invariants of the compact layout:
- The shared all-null statics are const (`initialized_binding_no_value` is in rodata: a stray write segfaults). Absent
  parts are shared all-zero stand-ins too (`type_node_none` from `binding_type()`, `symbol_table_empty` from
  `scope_locals()`): write only through `binding_set_type()`/`scope_locals_mut()`, and check the pointer, not just
  `has_explicit_type`. Packed spans panic if set from another file.
- `identifier_expr_name()` reads the Expr's inner_span through `offsetof`: never copy an `IdentifierExpr` out of its
  Expr. Its rare pointers (`module_ref_`, `this_function_`, `evolving_index_`, `extends_entity_`) share a union
  discriminated by keyword/require_call/evolving_op: keep them exclusive.
- A dot `PropertyExpr` is malloc'd only up to `name_` (`property_dot_new()`): never copy one by value or read `index`
  without checking `form`. Synthetic accesses (`synthetic_access()`, lower.c) are whole arena structs.
- Walk-only scopes (parameter list, return type, block, type literal, interface/class `this`, class field, computed
  name...) go back to the binder's scope arena (`scope_release()`, `binder_scope_arena()`) when still its latest
  allocation, they declared nothing, no symbol or SymbolDecl was made meanwhile (`ScopePendingMark.made`) and no pending
  report (`PendingNotFound`, `PendingExportMerge`, deferred events) holds them. Anything new that stores a `Scope*` must
  block the release like those do, or clear its pointer (`Block.scope`). A `-DTTTT_POISON_SCOPES` build fills released
  scopes with 0xA5; suite and corpora output must stay byte-identical.
- `Statement.flow` (8 bytes per statement) exists for TS7027 only.

### Types
`TypeNode`s are owned by the AST. `Ty`s, their members, signatures, mappers and everything else the checker makes live in the arena of their `Checker` and are freed with it; nothing in the type core is individually freed or reference counted. `program_drop()` drops the checker before the AST, because types point into the AST.

Node-keyed memos are two tables: `Checker.node_links` (`ty_link_get()`/`ty_link_set()`, value-based, two-word keys with the kind packed into the top byte of the subject's address by `link_key()`) and `links`, for the kinds that still need stable `intern_slot()` slots; a kind moves to node_links once all its uses are plain gets/sets. Interned unions, intersections and references key their member lists by pointer and their TyLists point into the key block (`intern_key_list()`): never write through one. Pointer keys hash differently per run (ASLR), which only changes probe lengths: nothing iterates the tables.

Lazy name indexes trust their owners: `MembersBuilder.by_name` (members.c) maps names to positions in `props`, so whatever reorders `props` calls `builder_unindex()` (`builder_late_bound_last`, `builder_sort_stable_from`, `builder_prototype_last` do) or `builder_find_prop()` misses members past 16; `LiteralBuilder.slots` (ty/expr.c) needs `props` to grow only through `literal_builder_add()` and copies through `literal_builder_clone()`; `ClassDecl.namesake_*` are built once at lookup and assume the items never change.

A function type or signature written as a type (`TYPE_CALLABLE`) is a `CallableType { FunctionImpl* }` (both in one allocation): a `FunctionImpl` without a body and with `is_type` set, so there is one way to resolve a signature (`signature_resolve()` reads parameters and return type off the `FunctionImpl`, `is_type` only decides how they're lowered). A node that declares a symbol (`GenericItem`, `InferredType`, a mapped key) has both `owned_symbol` and `symbol_ref`, a leftover from when nodes were cloned.

### Declarations
In TypeScript multiple declarations in the source code can contribute to a single logical declaration (this is known as declaration merging). `scope_init_declaration()` hands back the `Symbol` the declaration ended up in: a fresh one, an existing one it merged with (the declaration is appended to `Symbol.decls`), or a detached one when merging was an error. Symbols belong to the `Binder` and live as long as the program; AST nodes don't own them.

## Parsing
As mentioned above the parsing framework is custom, but it should be fairly straightforward.

### Parser struct
Each parse function (generally) creates it's own instance of `Parser` named `p`. This stores a current position in the source code, a pointer to the parser one level up (it's "parent") and some other things.

Each perse function receives a pointer to it's parent parser as an argument, as well as a pointer to an instance of the data structure it will attempt to populate, called `ret`. It returns a bool:
- `parse_success(&p)` - the function successfully parsed it's thing, `ret` is populated, the parent's current position is updated to match `p`'s position and any errors added to this parser or children **are** added to the parent
- `parse_fail(&p)` - the function did not parse it's thing, `ret` is undefined (could be unchanged, could be 0s, could be junk data, does **not** need to be dropped), the parent's position is not changed and any errors added to this parser or children are dropped (**not** added to parent)

`parse_success()` **always** returns true and `parse_fail()` **always** returns false. This makes it easy to return the correct value along with calling the corresponding parser cleanup function. It's **almost always** incorrect for these not to match up 1:1. The exceptions are simple low-level parse functions that avoid creating their own parser instances for performance, and a couple places where child parsers are created in the same function as their parents.

Note that a parser can succeed without errors, succeed with one or more errors or fail without errors. It **cannot** fail with errors (any errors added are silently dropped on fail). The idea is a parser either parsed something and advanced the current position (success) or did not (failure). Errors are only relevant when a parser parsed something, and understood a way that thing is wrong.

There are no parent pointers: every construction site that names an anonymous class calls `mark_named_evaluation()` (tsc's isNamedEvaluation walks up).

### Tokens
Because there are no tokens, `/` needs no rescanning: `parse_expr()` is only ever called where an expression may start, so a `/` there is a regular expression literal (`parse_regex()`, `EXPR_REGEX`), and anywhere else it's a division.

Unlike other typescript/javascript parsers, tttt doesn't tokenize before parsing. Sometimes tokens are needed though (such as when an error message for an unexpected token is to be added), which is what `hop_token()` is for. It's not called for most code.

### Anchors
Anchors are helpful for making spans. They are created with `anchor(&p)`. `span_from(a)` creates a span from the parser's position when the anchor was created to the parser's current position.

### Error recovery
Recovery follows tsc's parser rules without its tokens (plan 27):
- `parse_error()` drops an error that starts where the previous one does (tsc's parseErrorAtPosition), and an error at
  a character no token starts with (`invalid_char_size()`) becomes TS1127, which tsc's scanner would have reported
  first. `ParserShared.errors_attempted` counts the calls, dropped ones too, for code that asks "did that parse with
  errors".
- Lists. `ParserShared.parsing_context` is tsc's ParsingContext mask, a bit per list being parsed (`list_enter()` /
  `list_leave()`; statements, class/type/enum/object literal members, switch clauses, parameters, arguments, array
  literals, variable declarations so far). When a list's element can't be parsed, `list_abort_or_skip()` reports the
  list's error (tsc's parsingContextErrors) and ends the list if the token terminates it or starts an element or
  terminator of any enclosing list, else skips one token. One deviation: a token that starts an element of the list
  itself is skipped, since tsc's element parser would have consumed it. Delimited lists report a missing `,` and go
  on. The mask only matters when recovering, so the fail cache ignores it (a position that failed under one mask is
  only replayed under another in invalid code).
- The element and terminator predicates are tsc's `isStartOf*` lookaheads over `Tok`s (`tok_peek()`, `tok_next()`,
  `tok_scan_end()`: a cheap scanner, no values). They run only once an element parser failed or parsed with errors
  (`parse_list_member()`), never on valid code's path.
- Commit points: where tsc stops speculating, the tttt function succeeds with errors instead of failing:
  `arrow_function_tristate()` (tsc's isParenthesizedArrowFunctionExpression) in front of arrow functions, parameter
  lists after their `(` (`commit_on_paren`), property names after a `.`, `[]` (TS1011), object literal members
  after their name or `*`, parenthesized expressions, a binary operator where an expression should start (a missing
  left operand). A missing name is an empty span, which the symbols baseline prints as `(Missing)`.
- Grammar errors the parser reports for tsc's checker (`is_grammar_code()`: modifiers, TS1162...) don't count as parse
  errors and are dropped in a file that has parse errors, like tsc's grammarErrorOnNode.
- Modifiers are parsed wherever tsc's parseModifiers takes them (declarations, members, parameters, object literal
  members, in front of import/export statements) and checked once the node's kind is known by
  `modifier_list_check_grammar()` (modifier_list.c, tsc's checkGrammarModifiers): the caller says what the node is
  (`ModifiedKind`) and where (`ModifiedParent`, ambient or not; `ParserShared.in_ambient`/`statement_parent` track it).

### Whitespace
`hop_whitespace(&p)` needs to be called anywhere whitespace may appear.

Performance: the parser tries alternatives, so what a failed attempt costs is what parsing costs. The dispatchers (`parse_statement()`, `parse_expr()`, `parse_expr_right_side()`, `parse_type()`) test the first character before trying a branch that can only start with some, and keyword probes (`hop_start_if_ends_on_word_break()`) compare in place without a child parser. A new branch should get its first-character test too.

Newlines are generally ignored but change how js/ts are parsed in some cases. For this reason parsers keep track of if the last whitespace they hopped contained a newline. This gets propagated to the parent on success.

### JSX
In a JSX file (`SourceFile.is_jsx`: `.tsx` and JavaScript files, tsc's `LanguageVariant.JSX`) a `<` where an expression starts, followed by a name or `>`, is an element (`parse_jsx_element()`, tsc's parseJsxElementOrSelfClosingElementOrFragment), never a type assertion, and a generic arrow function has to be written `<T,>` or `<T extends X>` (`jsx_generic_arrow_start()`). There's no scanner mode: text between tags is read straight from the source, where `//` isn't a comment and `'` isn't a string. The AST is one `JsxElement` for `EXPR_JSX_ELEMENT` and `EXPR_JSX_FRAGMENT` (tag name as an identifier / `this` / property access expression, type arguments, attributes as one `EXPR_JSX_ATTRIBUTES` expression, children, the closing tag's name). Error recovery follows tsc's: a child that swallowed its parent's closing tag gives it back, `<a/><b/>` where one element is expected is a comma expression with TS2657, and only the first error at a position counts (see Error recovery). Value tags (`<Comp>`, `<this.x>`) are references in the resolve walk; intrinsic ones (`<div>`, `<my-elem>`, `<a:b>`, `jsx_element_is_intrinsic()`) aren't.

The factory is resolved in the resolve walk (`jsx_lookup_factory()` in expr.c). A file whose JSX imports its factory implicitly (react-jsx/react-jsxdev, `jsxImportSource`, `@jsxImportSource`/`@jsxRuntime` pragmas: `source_file_jsx_runtime_import()`) has a synthetic `SourceFile.jsx_runtime_ref` (`react/jsx-runtime`), loaded like an import in modules and JS files and `ambient_only` in scripts, like tsc's synthesized import. When that module exists it is `JsxElement.runtime_module`, whose `JSX` is the JSX namespace (`ty_jsx_namespace()`), and nothing else is referenced; when it doesn't, the file's first element gets TS2875 (TS2792 under classic resolution). Otherwise every element references the factory's first name (`React` of `React.createElement`: TS2874, or TS2552 for a misspelling, under `jsx: react`), fragments the fragment factory too (TS2879 once per file, TS17016/TS17017 without one). The factory options and pragmas are validated like tsc's (`compiler_option_is_entity_name()`): an invalid one counts as not given.

### JSDoc (JavaScript files)
`hop_comment()` records every `/** */` comment of a JavaScript file (`ParserShared.jsdoc_comments`, sorted, backtracking-safe). Whoever parses a JSDoc host (a statement, class member, object literal member, parameter, parenthesized expression) calls `jsdoc_before()` with the host's first token: the last one among its leading comments (other comments may come between, like tsc's getJSDocCommentRanges) is parsed into transient `JsDocTag`s, again each time (parse errors inside it are kept for JS files through `ParserShared.jsdoc_errors`; tsc's parseJSDocCommentWorker rules for where a tag starts; tags after `@callback`/`@typedef` are theirs, `nested`). A tag's `{T}` is parsed by the type parser pointed into the comment with `ParserShared.in_jsdoc` set: `hop_whitespace` skips a line's leading `*`, and the JSDoc-only forms tsgo 7 kept parse (`*`, `?T`/`T?` as `T | null`, `!T`, `Array.<T>`, and at the top of a type expression only `T=` as a `jsdoc_optional` union with `undefined` and `...T`, which is `T[]` on a `@param` and a rest parameter of type T in a `@callback`). Closure's `function(...)` type, a standalone `?` and `module:` namepaths are gone: `function` is a type reference (the Function type) followed by `'}' expected`, `?` alone is TS1110. A `@param` tag takes the parameter it names or, nameless after a parse error, the one at its position (tsgo's findMatchingParameter). JSDoc isn't stored: the host moves what the tags say into its own slots right away (`@type` -> a single variable declaration's or a class property's `explicit_type`, `@param`/`@returns` -> a function's parameters and return type, `@type` on a getter -> its return type, found through the host tsc's getNextJSDocCommentLocation walks up to; `@type {(a) => R}` -> a function's signature; `/** @type {T} */ (x)` -> an `EXPR_AS_TYPE`, `@satisfies` a satisfies expression), marked `from_jsdoc` (the baseline walk skips them). More slots of that kind: `@template` -> a function's, class's or class expression's `Generic` (`GenericItem.jsdoc`), `@returns {x is T}` -> the predicate, `@type` on an object literal property/method -> `ObjectExprItem.jsdoc_type` (declared and contextual type of the value), on an assignment -> `BinaryOpExpr.jsdoc_type` (handed to the `SymbolDecl` it declares, `SymbolDecl.jsdoc_type`: the declared type of `this.x`/`exports.x`/`module.exports`), a non-literal `@type {F}` on a function -> `FunctionImpl.jsdoc_signature_type` (applied by the checker as the function's contextual signature, `ty_function_apply_jsdoc_type()`), nested `@param {Object} o` + `@param {T} o.a` -> a type literal. Function and arrow function expressions are hosts of their own. JSDoc names (`String`, `Object`, `array`...) resolve by tsc's getIntendedTypeFromJSDocTypeReference (`IdentifierType.jsdoc_intrinsic`), otherwise a JSDoc type name resolves exactly like a TypeScript one (tsgo removed Strada's value references: a value is TS2749, `import("./m")` of a value-only module TS1340), from where tsgo's reparser puts the type (a `@param`/`@returns` type sees the parameters but not the body's locals, like an annotation); a name that is a namespace only through expandos isn't one in types (`namespace_from_expandos_only()`: tsgo's expandos add no Namespace meaning). `@implements` tags are a JS class's implemented types, `@private`/`@protected`/`@readonly` its members' modifiers (`jsdoc_modifiers()`; on `this.x = v` through `BinaryOpExpr.jsdoc_modifiers` -> `SymbolDecl.jsdoc_modifiers`).

TypeScript-only syntax in a JavaScript file (tsgo's checkJSSyntax, which the parser runs on every node it finishes: TS8002-TS8017, TS8037) is reported by the parser where it parses each construct (`js_syntax_error()`: type annotations, type parameters, `?`, TS-only modifiers in `check_js_modifiers()`, interface/enum/namespace/type alias declarations, signatures, `implements`, `import =`, `export =`, type-only imports and exports, `!`, `as`, `satisfies`). They are syntactic diagnostics of their own (`is_js_syntax_code()`): not parse errors, never deduplicated against them, kept for unchecked files. tsgo checks inside reported constructs too (a signature declaration is the whole node, its parameters are checked), except in type contexts: what's inside a type annotation, an interface, a type alias or an `implements` clause is dropped again with `js_syntax_skip_since()`.

Declarations made by tags are synthesized statements. Each statement list (`parse_append_statement_sequence()`) claims the JSDoc comments inside its statements that no inner list claimed (`JsDocRange.claimed`, `jsdoc_bind_comments()`): tsc binds a typedef in the block scope of its host, which is the innermost list. `@typedef`/`@callback` become `STATEMENT_DECL_TYPE`s (`TypeDecl.jsdoc`: exported from a module's top level, tsc's jsdocTreatAsExported; `@typedef {Object}` + `@property` a literal, `@callback` + `@param`/`@returns` a signature, every `@template` of the comment the parameters), `@import` at the top level a type-only `STATEMENT_IMPORT_EXPORT` parsed by the import statement parser pointed into the comment (`PortStatement.jsdoc`: no module indicator, allowed in scripts, references to it aren't reused by the types printer) (`@enum` is an unknown tag in tsgo 7, and a `@typedef` without a name is TS1003 and declares nothing). The baseline walk skips all of them; the symbols baseline's `Decl` of a tag is its `@`. A CommonJS module's typedefs are found next to its `export=` (tsgo's bindCommonJSTypeExports: named imports look in the module first, so does `import_type_lookup_names()`). Calls in JavaScript infer any where nothing is inferred (`Inference.any_default`).

### CommonJS (JavaScript files)
The parser notes `require(x)` calls (`IdentifierExpr.require_call` on the callee, a `MODULE_REF_REQUIRE` ModuleRef for a string literal) and assignments to `exports.x`/`module.exports` (`expr_commonjs_target()`); such a file without ES imports/exports is a module, `SourceFile.is_commonjs`. The assignments and calls that may declare an export are collected right after parsing, on the load pool's thread (`source_collect_commonjs_candidates()`, `SourceFile.commonjs_candidates`: a walk of the whole file, tsgo's getAssignmentDeclarationKind is syntactic, an assignment anywhere, in functions too); in the declare step `scope_add_commonjs_module()` replays them in walk order and turns `exports.x = v`/`module.exports.x = v`/`Object.defineProperty(exports, "x", ...)` into exports (an alias for a name, else a `SYMBOL_DECL_ASSIGNMENT` value) and `module.exports = v` into `export=` (`binary_commonjs_declaration()` is the shared test), then declares the file's `module` (`SYMBOL_DECL_COMMONJS_MODULE`, typed `{ exports: ... }`, `ty_commonjs_module_object()`) and `exports` (`SYMBOL_DECL_COMMONJS_EXPORTS`) variables, declared by the file at its start like tsgo's declareCommonJSVariable, unless the file declares them. Both `exports` and `module.exports` are what the module exports (`ty_commonjs_exports_type()`: the `export=`'s type, else the module's namespace type, `typeof import(".")` from inside). Top-level `this` is `globalThis`, like a script's. `require` in a require call is the binder's `require_symbol` (any) and the call has the module's type. `const x = require("m")` and `const { a } = require("m")` declare aliases (`const a = require("m").a` is a plain variable since TS 7): the parser synthesizes `PortItem`s on the `InitializedBinding` (`require_ports`) and the declare step adds them with `scope_add_port()`. A named import of a CommonJS module with an `export=` sees its typedefs and the assigned value's properties only. A CommonJS module mixing `module.exports =` with other value exports is TS2309 (`check_module_exports()`, run for CommonJS JS files too; repeated `exports.x =` aren't redeclarations); its type and namespace exports (typedefs) become exports of the `export=` symbol itself, which is a namespace by them (`bind_commonjs_type_exports()`, tsgo's bindCommonJSTypeExports): an aliasing `module.exports = C` then isn't a pure alias, `module_export_equals()` returns the alias (its value is still C's through `symbol_for_meaning()`), the symbol chain doesn't name C through the module, and a qualified name `X.Y` falls back to C's exports (`symbol_namespace_member()`, tsc's resolveQualifiedName). An export's assignments union their regular types (`assignment_symbol_type()`: literals kept, object literals widened together, a first `undefined` ignored, alias declarations' values from `SymbolDeclJs.commonjs_value`); an export only ever assigned aliases is its last alias's target. `export const x = require()` is a variable, `export=` assigned several times is TS6424 under declaration emit.

Exported class expressions (`exports.C = class {}`, `module.exports = class {}`) are aliases of the class, so it is usable as a type: the declare step creates the class's scope early and the resolve walk re-parents it (`scope_reparent()`). Statement-level `Object.defineProperty(o, "x", {...})` on a plain object, `F.prototype` or `exports` declares x (`expr_is_define_property_call()`), with the descriptor's value/get/set types. A JavaScript file of a program without checkJs or a `// @ts-check` (`SourceFile.plain_js`) is checked in full, but only tsc's plainJSErrors codes are reported (`plain_js_reports()` in error.c).

### Assignment declarations: expandos and JavaScript classes
`f.x = v` declares a member x of f (an expando, tsgo's bindExpandoPropertyAssignment/bindDeferredExpandoAssignment) when the entity name `f` (in JavaScript also `a.b`, each name before the last an expando of its own) names, in the block or else its function or file only (tsgo's lookupEntity), a symbol whose first value declaration in this file is a function declaration, a JavaScript class, a variable (a const outside JavaScript) initialized with a function or arrow function, in JavaScript also a class expression or an unannotated `{}`, or a JavaScript assignment declaration of one (`ns.a = {}`): `expando_host()`, `symbol_is_expando_host()` (tsgo's getInitializerSymbol), `expando_initializer()` (IsExpandoInitializer: no defaulted `ns || {}`, no parentheses). The member is declared only when nothing but assignments declares that name in the host. `scope_add_expandos()` runs at the end of `block_add_names()` over the block's expression statements and `var` initializers; the resolve walk declares the other ones (`scope_add_nested_expando()`). The member goes into the host's `exports` as a `SYMBOL_DECL_ASSIGNMENT`; a function or class host gets a nameless `SYMBOL_DECL_EXPANDO` declaration (`mark_expando_host()`), whose value is the host's namespace type, so a function with expandos is a function type with those members (printed structurally like tsgo, `typeof f` only within itself); a variable's function initializer gets the members through `FunctionImpl.expando_host`, a class expression's static side through `ClassDecl.expando_host`, a `{}` container is the namespace type of its variable or member, and the literal itself has that type (`SourceFile.expando_containers`, `Expr.expando_container`). A member's type is the union of what is assigned (`assignment_symbol_type()`, tsgo's getWidenedTypeForAssignmentDeclaration), any with TS7022 if an assigned value reads the member again (`guarded_assignment_symbol_type()`). There are no global expandos (a name the file doesn't declare is no host), no `F.prototype.x` members, no `this` aliases, `void 0` is assigned like anything else. In JavaScript files TS2339 is reported like in TypeScript, except on an object literal of a JavaScript file without noImplicitAny (`Ty.anonymous.js_literal`, tsc's isJSLiteralType).

In JavaScript, `this.x = v` in a class declares x in the class symbol's `members` table (`Symbol.members`, statics in `exports`), and in an object literal's method or accessor the literal's members (`FunctionImplRare.this_literal`, symbols baseline only): tsgo's bindThisPropertyAssignment (`scope_add_this_property()`, called by the resolve walk right after an assignment's target is resolved). Constructor functions are gone (tsgo): a function is never a class, `new f()` is TS7009 and `this` in it TS2683 like in TypeScript. `SymbolDecl.assignment` says which kind of assignment declared a member, which the type needs (tsgo's isConstructorDeclaredThisProperty): the type `this.x` has at the end of the constructor if one assigns it (unless only null/undefined), else the base class member's type for method-only members, else the union of the assigned values that don't read `this.x` themselves (plus undefined for method-only ones); only-nullish is any; such a member always overrides the base class's; a constructor-declared `this.x = v` is any as a target in its constructor, and a class field without type or initializer has the constructor's type (`ClassItem.field.js_assigned`). In TypeScript under noImplicitAny such a field has the type `this.x` has at the end of the constructor (or of the first static block that assigns more than null/undefined), tsc's getFlowTypeInConstructor: `field_type_from_assignments()` queries the flow engine with the first `this.x =` target the resolve walk saw (`ClassItem.field.ts_assigned`) at `FunctionImpl.return_flow` / `ClassItem.static_block_return_flow`. Class instance types add the `members` the class body doesn't declare (`builder_add_assignment_members()`). Untyped JavaScript functions (no parameter with a type, a typed `@param` or its own `@type`, and no host `@type`: tsgo's isUntypedSignatureInJSFile) take any number of arguments (`function_is_untyped_js()`, `FunctionImpl.jsdoc_type_tagged`, min_args 0).

### Function context
Whether `await` and `yield` are operators or plain identifiers depends on the function being parsed. `ParserShared` keeps `in_async`, `in_generator` and `function_depth`; `function_ctx_enter()`/`function_ctx_leave()` wrap the parsing of every function's parameters and body (see `parse_non_arrow_function()` and `parse_arrow_function()`), and `FunctionFlags` carries `async`/`*` from whoever saw the keyword to the function parser. Since a source position is always inside the same function, this doesn't conflict with the fail cache. `await_is_operator`, `yield_is_operator_outside_generator` and `yield_await_is_keyword_here` decide from these flags plus a character peek where tsc looks a token ahead (nextTokenIsIdentifierOrKeywordOrLiteralOnSameLine). The parser tags each `await` expression and `for await` with where it is (`AwaitPlace`: allowed, in a non-async function, at the top level); the resolve walk reports what isn't allowed there (`await_check_grammar()`, shared with `await using`), since that needs the containing function (for TS1356) and the file's module status.

### Lexical level
There is no scanner, but the scanner's decisions live in a few helpers. A file's text is first made what tsc sees
(`text_decode()` at load: UTF-16 files decoded, invalid UTF-8 replaced by U+FFFD, which at a token start means a binary
file, TS1490). Identifiers are scanned by `identifier_char_size()`: the ASCII table, then tsc's unicode tables by target
(`unicode_identifiers.c`, generated by `unicode_identifiers.py`) and unicode escapes; the fast paths (`hop_whitespace`,
`hop_start_if_ends_on_word_break`, the identifier loop) are hot enough that any extra work in them shows in parse time.
Numbers are `scan_numeric_literal()` (tsc's scanNumber), strings/templates `parse_string_or_tagged()`/`parse_template()`
with `parse_string_escape()` (escape errors reported by `parse_error_in_literal()` unless in a tagged template), trivia
`hop_whitespace_slow()` (comments, conflict markers after a newline). A regex literal is only delimited by the parser
(`parse_regex()`, TS1161); its body and flags are checked by `regex_check.c` from the checker, like tsc's
checkGrammarRegularExpressionLiteral. Columns are UTF-16 code units (`span_col_index`, `utf8_byte_utf16_units()`).
### Fail cache
The fail cache is used to cache specific locations where specific parse functions have failed to parse before. There are some cases (such as arrow functions vs parenthesized expressions) where the correct way of parsing something is not obvious until after the parser has parsed some sub-expressions. If these cases are nested the time complexity of doing this naively is Not Good. However if you keep track of where you've tried and failed to parse specific things it's fine, so that's what we do. For details on precisely how it works you'll have to decipher the code.

## Builds
`scripts/fastbuild.sh` is the one definition of the fastest build and leaves it at `fast/tttt` (today: `scripts/pgobuild.sh`,
LTO + GCC PGO trained on a few pinned corpora into `pgo/tttt`, then `scripts/boltbuild.sh`, llvm-bolt's layout into
`bolt/tttt`; `fast/tttt` is a symlink to the last step). When the pipeline changes, that script changes and the path
doesn't; the measuring scripts (`bench.sh`, `instrcount.sh`, `perfsweep.py`, `cgrank.py`) take their binary from
`scripts/fastbuild.sh --measured`. The development builds, which every test script makes for itself: `release/`
(`meson setup release --buildtype release`, plain -O3, the edit-test loop and the suite), `debug/` (asserts, the
debug allocator, what `scripts/test.sh -d` runs under valgrind). None of them is the binary to benchmark.
