# tttt Documentation

## Programs
The repository contains three programs.

### tttt
The actual typechecker, drop-in replacement for tsc. See `build/tttt --help` for usage.

Can be compiled and run with `./run.sh`. This makes a debug build and runs it under Valgrind, so won't be fast.

Completely written in C. Code lives in [src](src/). The only dependency is [cleat](https://codeberg.org/sphi/cleat), an MIT-licensed standard library for C which comes with its own vendored copy of the STC container library (no relation to the swc-related project of the same name). It's included in this repository under [thirdparty/cleat](thirdparty/cleat/), and automatically compiled by the build system. `thirdparty/refresh.sh` re-downloads it at the pinned commit.

### baseline_tests
Runs tttt against TypeScript's official test suite. See `build/baseline_tests --help` for usage.

Can be compiled and run with `./test.sh` (debug build, under Valgrind, takes minutes) or `./fasttest.sh` (release build, not under Valgrind, takes seconds). Features like regex filtering and displaying diffs are supported, see `./test.sh --help` for details.

Like tsc's harness, a multi-file test whose last file mentions `require(` or `reference path` (or that sets `@noImplicitReferences`) has that file as its only root: the others are part of the program only if something refers to them, and the root comes first in the baselines.

The tests target includes most `tttt` code, as well as additional C code in [src/test](src/test/).

### diffapp
A graphical app that allows you to edit TypeScript code and see tsc's and tttt's test output for that code in real time. It watches for changes to tttt's source code, and recompiles and re-runs tttt on save.

Generally run via `./diffapp.sh`. A test name or source file can be specified. If there's already a running instance the script will send the given test to that instance.

It's a nodejs web app with an html/css/js frontend in [test/diffapp](test/diffapp/). It's intended to run locally (basically uses the browser as a GUI toolkit only). The tttt integration lives in [src/test/diffapp_runner.c](src/test/diffapp_runner.c).

## Architecture
To keep development fast, LoC down, Tess sane and (in specific cases) tttt fast, we do things the most straightforward way wherever possible.

### AST
At the core of tttt is a TypeScript AST (Abstract Syntax Tree). This is a data structure that maps to parsed source code, and on which the typechecker runs. AST nodes are:
- `Block` - sequence of statements, often surrounded by `{` `}`s
- `Statement` - chunk of code that does not result in a value, often each on their own line or separated by `;`
- `Binding` - assignments and function parameter lists use bindings. They are often simply identifier names, but can be more complicated in the case of destructuring
- `Expr` - nestable expression, such as a function call or value literal
- `TypeNode` - the *syntax* of a type, as written (functions are named `type_*()`, tags `TYPE_*`). The checker's semantic types are a different thing, `Ty`, see "The type core" below

This list is not exhaustive as there are other structs owned by these. Each of these structs has it's own `.h` and `.c` files. Look through them for more details.

There is no AST node struct, interface or visitor. The AST is simply a *concept* that includes these structs, and is relevant for reasoning about the architecture.

### Span
A span is a reference to a section of source code, often used for error messages. Spans don't own anything, and don't need to be dropped. Identifier names are generally stores as spans.

### Display
tttt has its own rendering pass for AST nodes in [src/display.c](src/display.c), driven by a `Display` struct (`display_type()`, `display_expr()`, ...). It stays separate from [cleat's display system](thirdparty/cleat/docs/display.md) because it's on the typechecker's hot path (every failed type comparison renders both types into a message) and because it has rendering modes cleat knows nothing about: `debug` (the developer-facing tree), `brief` (the same, truncated), `parsed` and `underline` (used by the test runner to underline a type within its rendering).

The two systems are bridged in [src/display.h](src/display.h). `declare_ast_display()`/`impl_ast_display()` generate a cleat display function per AST node, so `Span`, `TypeNode const*`, `Expr const*`, `Error const*` and friends are all in `DISPLAYABLES`, and so is `Ty const*` (a semantic type, printed the way tsc prints it in messages) and can be passed straight to `println()`, `cstr_d()`, `panic()`, `log_error()`, `error_ctx_error_d()` and so on. A plain sequence gets the TypeScript-diagnostic form, `debug_d(x)` gets the developer form and `brief_d(type)` gets the truncated one.

Everything that isn't an AST node goes through cleat's display system directly; `src/` has no `printf`-style format strings left apart from JavaScript's number-to-string precision in `value.c`.

### Parser
The parser (including a minimal custom parsing framework) lives in `parser.c`. We do not compile grammars, combinate or tokenize. We simply take a const char* and use it to build an AST. Like real men.

See dedicated section below for details.

### Program
The `Program` struct owns the source code buffers and ASTs of all loaded files, manages imports, etc.

### CompilerOptions
`CompilerOptions` ([src/compiler_options.h](src/compiler_options.h)) is what tsc calls the same: every boolean option (one X-macro list, with which ones belong to the `strict` family), `target`, `module`, `moduleResolution`, `jsx`, `moduleDetection` and `lib`. `compiler_options_set(options, "strictNullChecks", "false")` takes names and values as they're written in a tsconfig, on the command line (`tttt --target es2020 --strictNullChecks false`) or in a test's `// @target: es2020`; `compiler_options_resolve()` then applies tsc's dependent defaults (`strict` to its family, `module` from `target`, `moduleResolution` from `module`, `useDefineForClassFields` from `target`...), so every field holds the effective value. `compiler_options_lib_files()` gives the standard library files to load: the `lib` list, else the default library of the target (`lib.d.ts`, `lib.es6.d.ts`, `lib.es2016.full.d.ts`...).

Each `Program` owns one (`program_options()`, change it before loading files). Code that parses, resolves names or checks reads the current program's through the global `compiler_options()`, which `program.c` sets around each phase. Most options are parsed but not acted on yet.

### Test configurations
A tsc test whose directives give several values for an option (`// @target: es5,es2015`, `// @strict: *`, `// @module: *,-amd`) is several tests, each with baselines named `name(option=value,other=value)`. `baseline_test_configurations()` (`src/test/baseline_test_case.c`) follows tsc's `getFileBasedTestConfigurations()`: only boolean and enum options vary (a comma in `@lib` or `@types` is a list), `*` means every value of the option, `-x` excludes one, spellings of the same value (`es6`/`es2015`) collapse, option names are sorted. The suite holds one `BaselineTestResult` per configuration; `-f someTest` matches all configurations of a test, `-f 'someTest\(target=es5\)'` one. Tests with `// @noTypesAndSymbols: true` have no `.types`/`.symbols` baselines and are compared on errors alone.

### Symbols, tables, scopes (the binder, `scope.h`/`scope.c`)
The model is tsc's, because the symbols baseline, the merging rules and the diagnostics encode it:
- A `Symbol` has tsc's `SymbolFlags` (what it *means*: value, type, namespace, alias), its `parent` container (set for exports only, like tsc), every declaration that contributed to it as a `SymbolDecl { kind, flags, node, name, full }` (the AST node: `Binding`, `FunctionImpl`, `ClassDecl`, `InterfaceDecl`, `EnumDecl`, `EnumCase`, `TypeDecl`, `GenericItem`, `InferredType`, mapped key, `NamespaceDecl`, `PortItem`, `export default` expression, builtin) and, for namespaces, enums and modules, one `exports` table **shared by all declaration blocks**. Symbols, tables and scopes live in the arena of the program's `Binder` and are never copied or freed individually; what only aliases and modules need is in side structs (`SymbolAlias`, `SymbolModule`).
- **Merging is `declare_symbol(table, name, includes, excludes)`** with tsc's `*Excludes` masks verbatim: `var`+`var`, function+namespace, class+interface, enum+enum, interface+anything that isn't a type, alias+anything that isn't an alias merge; anything else is TS2300 / TS2451 (block scoped) / TS2567 (enums) on every declaration of both sides, and the newcomer gets a detached symbol. Side rules (TS2434, TS2440, duplicate type parameters) are checks next to it.
- A `SymbolTable` is insertion ordered (namespace members come out in declaration order), scanned linearly up to 8 entries and indexed beyond, keyed by views into the source, and may overlay a read-only `parent` table: a test program sees the globals of the cached lib program without copying them, and adding to a lib symbol clones it into the overlay first (`clone_parent_symbol`). Nothing is written to the frozen original; references inside the lib AST still point at it, so the checker maps every symbol it is handed through `binder_redirect()` (`Binder.overlays`, only consulted by programs that have overlays) and lib-internal uses see the program's additions.
- A `Scope` is `{ parent, kind, locals, container }` and **persists**: the file scope is on the `SourceFile`, a namespace block's on its `NamespaceDecl`; function/block/type-parameter scopes are made by the resolve walk (nothing keeps a pointer to those yet: plan 05's flow nodes will). Declarations made in a module/namespace/enum scope go to the container's `exports` when exported (or when the scope is an ambient *export context*), to `locals` otherwise; scripts and `declare global` declare into `Binder.globals`. `var`s hoist: `block_add_names()` of a function/module/namespace/static-block scope also runs `statement_hoist_names()`, a statement-only walk that declares the `var`s of nested blocks, which those blocks then skip.
- **Lookup is by meaning and sees through aliases**: `scope_resolve(scope, name, meaning)` walks the parents, checking locals and then the container's exports (so a second `namespace N {}` sees the first one's exports, and non-exported members stay out of `typeof N`); a symbol matches when its flags have the meaning or when it is an alias whose target does. That is what lets `import { Node } from "./types"` (an interface) merge with a local `function Node()`.
- **Imports and exports are alias symbols** (`scope_add_port()`): import/export specifiers, default imports, `import * as`, `export * as`, `import x = A.B.C` (resolved lexically from the scope it was written in), `export default x`. `symbol_resolve_alias()` is memoised with an in-flight state. A module's `export *` targets are a list on the module symbol; `module_resolved_exports()` flattens them once (own exports shadow stars, first star wins, `default` doesn't travel, cycles are fine). What can't be resolved becomes a *placeholder* symbol that has every meaning and is `any`.
- **Modules.** The parser records every module a file names in `SourceFile.module_refs` (`ModuleRef { path, span, file, module }`: import/export declarations, `import x = require("m")`, `import("m")` types and expressions, `declare module "m"`), wherever it is written; the program loads the files from that list. `binder_module_of_ref()` says what a name refers to: an ambient module of that name (`Binder.ambient_modules`: every `declare module "m" {}` block of every script declares into one module symbol), else the module symbol of the file the program found, else a pattern ambient module (`"*.css"`, longest prefix). `declare module "./a" {}` inside a *module* is an augmentation: its declarations go straight into the exports of the module it names (everything in it is exported). `declare module "m";` is a shorthand module: imports from it are placeholders (any). `export = x` is an export named `export=` (an alias, or a variable for other expressions) and `module_export_equals()` is what importing the module gives (`import x = require()`, `import * as`, default imports, named imports look into it). `export as namespace N` is a global alias of the module. `globalThis` is a namespace symbol whose exports *are* the globals table (`binder_redirect()` maps the shared lib program's one to the current program's).
- **Import types** (`import("./a").B<T>`, `typeof import("./a")`) are `IdentifierType`s with an `import_ref`: the names are looked up in the module's exports instead of the scope, for `typeof` as values and then as properties from `import_prop_start` on. `import("./a")` the expression is a call of the keyword identifier `import` (`KEYWORD_IDENTIFIER_IMPORT`, carries the `ModuleRef`) and gives a `Promise` of the module's type.
- **Symbol accessibility when printing** (`out_symbol_name()` in `ty/ty_display.c`, a simplified `getAccessibleSymbolChain`): with `TyDisplay.enclosing` set (the scope a type is printed from; the test traversal tracks file and namespace scopes) a name is qualified only as far as needed: bare if the name resolves to the symbol from there, an import's name if an alias in scope names it, `import("a").T` for a member of another module nothing names, `N.T` otherwise. Without it (error messages) names are fully qualified.
- **Symbols are what the checker knows things by.** AST nodes that declare something keep a `Symbol*` (`symbol`), identifiers keep the symbol the name found (`symbol`, maybe an alias: what the symbols baseline shows) and the one that has the meaning the name is used with (`target`, aliases resolved: `symbol_for_meaning()`, cached so checking never chases alias chains). `this` is a `ThisRef { kind, symbol }` found through `Scope.this_ref` (class instance, class static side, `any`, or a `this` parameter). Nothing in a `Symbol` is written after `binder_link()`; per-symbol checker state is `SymbolLinks` in `Checker.links`.

### LazyType
`LazyType` is a struct owned by the AST: the memoised, cycle-detecting type of whatever contains it (an `Expr`, an `InitializedBinding`, a for-each variable, a `FunctionImpl`, a class field or accessor). It exists so that something can *refer* to a type during name resolution, long before the type can be evaluated. Declared things (classes, interfaces, enums, aliases, namespaces) don't have one: their types are memoised per `Symbol` by the type core.

The process goes something like this:
1. An AST struct, for example `Expr`, contains a `LazyType`
2. In the resolve names phase, it calls `lazy_type_bind(&lazy, LAZY_TYPE_EXPR)`, which sets the tag and gives the LazyType a *slot* number
3. Whoever needs to refer to that type keeps a pointer to the LazyType or to what contains it: a `Binding` points at the LazyType of what is assigned to it (`Binding.source`, the initializer or the for-each variable type), an element of a destructuring pattern at its parent pattern (`Binding.parent`), a class property at its field/accessor LazyType (`Prop.lazy`). There are no link nodes: a `TypeNode` is syntax only, exactly what the parser made
4. Later, in the typecheck phase, whoever wants the type calls `lazy_type_get()` (`ty_binding_type()` for a binding: the written type, else what is assigned, else the property/element of the parent pattern's type)
5. The tag of the LazyType is `LAZY_TYPE_EXPR`, so `lazy_type_evaluate()` uses the pointer to the LazyType to calculate a pointer to its containing `Expr` and calls `expr_evaluate_type()`, which returns a `Ty const*`
6. That goes into the LazyType's memo (`LazyMemo`), and future calls to `lazy_type_get()` return it directly

LazyTypes play a critical role in detecting self-referential types. While a LazyType is being evaluated its memo is in an in-flight state. If something tries to evaluate it again in the same call stack its type becomes the error type (`TY_ERROR`, an `any`).

**The memo is not in the LazyType.** The LazyType itself never changes after the resolve names phase: it's a tag and a slot number, and the memo lives in the slot storage (`LazySlots`, a sparse three level table allocated on first touch) of the current `Checker` (`current_checker` / `current_lazy_slots`, thread local). Each `Program` has one checker, created by `program_make_current()`, which `program_typecheck()` calls; call it yourself to look at the types of a program that wasn't typechecked. This keeps the AST read-only while checking, which is what lets many programs share one lib AST (the test harness does) and later lets several checkers work on one AST. `LAZY_TYPE_EVALUATED` is the tag of `expr_implicit_any()`: nothing to evaluate, no slot.

### The type core (`src/ty/`)
Semantic types are `Ty` (`src/ty/ty.h`), and everything that has a type evaluates to one: written types are lowered from their `TypeNode` (`ty_from_node()`), expressions are checked by `ty_check_expr()`, functions, classes, interfaces, enums, namespaces and merged declarations have their types built from the AST. There is no other representation: the value-semantic `Type` trees this project started with (cloned, dropped, substituted into) are gone, and `TypeNode` is never created, cloned or resolved by the checker (there is no `type_clone()`).

The statement/expression walk (`statement_typecheck()`, `expr_typecheck()`, `binding_typecheck()`, `class_decl_typecheck()`...) stays in the AST files and asks the type core for types and checks: `ty/check.c` has the ones with tsc's error wording (`ty_check_assignable()` for TS2322 and its elaboration, `ty_check_property_access()`, `ty_is_comparable_either_way()`), and `ty_of_node()` lowers a written type with the current checker.

- **Symbols know their AST nodes** (`Symbol.decls`, filled by `scope_init_declaration()`), and `lower.c` turns a symbol into types from them. `ty_declared_type_of(symbol)`: interface / class instance type (one `TY_DECLARED` per symbol, the type parameters of later interface declarations unified with the first's), enum, enum member, type alias body, type parameter (`SYMBOL_TYPE_PARAMETER`: declared ones, `infer X`, mapped type keys), in-flight detection for circular aliases. `ty_static_type_of(symbol)`: the static side of a class, the object of an enum. `ty_type_of_symbol(symbol)`: the symbol as a value, from the declarations that contribute one (the first variable declaration, function signatures, class static side, enum object, namespace object, enum member, `export default` expression); one contribution is that type, several are `ty_merged_value_type()`. Variables aren't memoised per symbol: the binding's own LazyType is the memo and the cycle detector. The members of a declared type come from the same nodes: every merged interface body, a class's fields/methods/accessors (overloads hide the implementation signature), inherited instance members, and for the static side `prototype`, static members, inherited static members and the construct signatures (the class's own, else the base class's with this class as the return type).
- **Enums** (`enums.c`): an enum's type is the union of its members' types with the enum as the union's alias (that's how it prints as `E`, and `formatUnionTypes`-style collapsing prints a full run of members inside a bigger union as `E` too). A member's type is a literal type keyed by (value, enum), so members with equal values share a type, like in tsc; a member whose initializer isn't a compile time constant gets an opaque "computed" type (`TYF_ENUM`). Values come from a small constant evaluator over `Expr` (literals, unary/binary operators, references to other members). The enum object (`typeof E`) has a readonly property per member and the numeric reverse mapping.

- A `Checker` owns an arena, a type id counter and the intern tables. Every `Ty` is immutable once published and interned, so **pointer equality is type identity**: `List<string>` is one pointer no matter how often or where it's written. Ids are handed out in creation order and intrinsics are created in tsc's order, because unions print in id order.
- Intern keys are small arrays of `u64` words (a `KEY_*` tag followed by ids/pointers, `ty_internal.h`) in one open addressing table type (`InternTable`). `Checker.types` holds literals, unions/intersections, references, tuple targets, deferred types and instantiated anonymous types; `Checker.links` holds everything that is *about* an AST node or `Symbol` (`SymbolLinks`: declared and static types; merged value types, type parameters, anonymous types by node, alias instantiations), so the AST is never written to. `intern_slot()` pointers die on the next insert into the same table; use `intern_get()` and look the slot up again when the value takes interning to compute.
- Kinds: intrinsic, literal (incl. enum members), type parameter, declared (interface, class instance/static side, enum object, namespace value, tuple target), reference (generic declared type + arguments; arrays are references to the global `Array`, tuples to a tuple target), anonymous (type literal / function type by AST node, or `{target, mapper}` instantiation), union/intersection (sorted by id, cheap reductions only, alias is part of the identity like in tsc), and the deferred `keyof`/indexed access/conditional types, whose constructors resolve eagerly when they can. A mapped type becomes ordinary properties and index signatures once its key type is known (`expand_mapped()`).
- **Members are lazy** (`members.c`): `ty_members()` resolves props, call/construct signatures and index signatures on first use; `prop_type()` and `signature_resolve()` lower or instantiate the types inside on first use. That is what makes recursive types legal and cheap.
- **Instantiation never copies** (`instantiate.c`): `ty_instantiate(ty, mapper)` returns `ty` itself unless it has `TYF_COULD_CONTAIN_TYPE_VARIABLES`, rebuilds interned kinds through their constructors, and turns an anonymous type into an interned `{target, mapper}` pair restricted to the type parameters the node actually mentions (`free_params`).
- **Functions** (`function.c`): the type of a function declaration, function expression, method, accessor or constructor is an anonymous object type with one signature that is read straight off its `FunctionImpl` (`Ty.anonymous.function`, `Signature.function`): type parameters from its `Generic`, parameter types from the bindings, and the return type from the annotation or, lazily, from the `return` statements of the body (`ty_function_return_type()`: the union of what `block_collect_return_types()` finds, subtype reduced and widened, `void` without returns, wrapped in `Promise` for async functions, memoised per function with an in-flight state so a function that returns its own call is `any`). A function *type* (`(a: T) => R`) is a `TYPE_CALLABLE` node that owns a body-less `FunctionImpl`.
- **Namespaces and merged declarations** (`lower.c`, `members.c`): the value of a namespace (or of a module, for `import * as ns`) is a declared type by `Symbol` with a property per value among its exports, by export name and in declaration order (`ty_namespace_type()`; the type of such a property is `ty_type_of_symbol()` of the member, `Prop.symbol`). A symbol several declarations give a value to (function overloads, a function/class/enum merged with a namespace) gets the members of all of them (`ty_merged_value_type()`): anonymous for overloads alone, by name (`typeof f`) otherwise.
- **Relations** (`relate.c`): `ty_is_related(source, target, relation)` for assignable, comparable, strict subtype (union reduction) and an assignable variant with strict nulls. It follows tsc's structure because the observable results depend on it: simple relations by flags first, then a per-relation cache on the checker keyed by `(source id, target id)`, a "maybe" stack for pairs that are being compared further up (assumed related, made definitive when the outer comparison finishes), a deep-nesting check on the generic target of the types on the stack (what terminates infinitely expanding generics), and for two references to the same generic type a comparison of the type arguments by *measured variance* (`get_variances()`, marker type parameters, cached in `Checker.links`). `ty_explain_unrelated()` reruns a failed check in reporting mode and returns tsc's elaboration chain, outermost line first; the first line is either the generic TS2322 head or something that replaces it (TS2741 missing property...). `TTTT_DEBUG_RELATE=1` logs every top-level query, `TTTT_DUMP_VARIANCES=1` every measured variance.
- **Calls** (`call.c`): `resolve_call()` collects the call or construct signatures of the callee's apparent type (a union is called member by member, an intersection through all its members' signatures), and `resolve_with_signatures()` takes the first candidate that fits, like tsc's `resolveCall`: arity (`ParamShape` spreads a tuple rest parameter out, `Args` spreads tuple spread arguments out), type arguments inferred from the arguments, every argument related to its parameter, with a subtype round before the assignable round when there are overloads. Arguments are checked with the candidate's parameter types as contextual types; a generic candidate infers in two passes (context-sensitive arguments, ie lambdas with unannotated parameters and literals containing them, come second and see the parameter type instantiated with what the first pass found), also from the contextual type of the call to the return type at low priority. Explicit type arguments (`f<A>(x)`, a `GenericParamsExpr` around the callee) select candidates by type parameter count (TS2558), replace inference, and are checked against the constraints (TS2344). When nothing fits the errors are tsc's: TS2554/2555/2575 for arity, the argument error of a lone candidate, TS2769 with one "Overload n of m" branch per candidate otherwise.
- **Inference** (`infer.c`): one walker (`infer_types()`) for generic calls and for `infer X` in conditional types. It keeps covariant and contravariant candidates apart (parameters flip the direction under `strictFunctionTypes`, reference type arguments by measured variance), knows priorities (a naked type parameter in a union gets what the other members didn't match), and records whether the type parameter was only seen at the top level of a parameter type. `inference_call_result()` is tsc's `getInferredType` for calls (literal widening unless the constraint is primitive or the type parameter is at the top level of the return type, common supertype, covariant preferred over contravariant when it fits, `unknown`/default/constraint fallbacks are in `infer_type_arguments()`); `inference_conditional_result()` is union / intersection. `InferParam.fixed` is the seam for the context-sensitive second pass that comes with contextual typing.
- **Expressions** (`expr.c`): `ty_check_expr(expr, contextual)` is the one entry point. There are no parent pointers to find a contextual type through, so the rule is the other way around: **whoever knows an expression's contextual type checks it with that type before anything else asks**, and the result is the expression's memo (`lazy_type_set()`, with the contextual type it was computed for in `LazyMemo.context`); `ty_expr_type()` reads the memo and only checks without context if nobody got there first. A variable declaration checks its initializer with the annotation, `return` with the function's return type (`Checker.return_context`), an assignment with the target's type, a call checks each argument with its parameter type (per overload candidate), object and array literals pass the property/element type of their own contextual type down (`contextual_prop_type()`, `contextual_element_type()`), and `expr_typecheck()` evaluates an expression's own type before walking into it. A function expression takes the types of its unannotated parameters from the first contextual signature it meets and keeps them (`assign_contextual_signature()`: links keyed by parameter, read back by the parameter's own LazyType; tsc does the same), while literals are simply checked again for a new contextual type. Literal types widen at mutable locations unless the contextual type has room for them (`check_for_mutable_location()`, `ty_widened_for_declaration()`, `ty_widened_return_type()`; there are no fresh/regular literal pairs yet). A contextual tuple type or `as const` makes an array literal a tuple. `ty_identifier_reference_type()` is the one place the type of an identifier reference comes from (narrowing will live there).
- **Property access** (`access.c`): `ty_access(object, index)` for a known index, through apparent types (`String` for strings, the constraint for a type parameter, `Function`/`Object` members), tuple elements, then index signatures. `index_type_evaluate_type()` is a wrapper around it, and so is the indexed access *type* `T[K]` once neither operand is generic (`try_resolve_indexed()`).
- **Conditional types** (`conditional.c`): `ty_conditional()` resolves as soon as the check type isn't generic at the top level: `infer` type parameters are inferred by walking check and extends type in parallel, the extends type is instantiated with the results and related. A deferred conditional type remembers the conditional type it was written as and the mapper that leads from there to it (`Ty.conditional.root`/`.mapper`, tsc's ConditionalRoot), and `ty_instantiate()` always restarts from the root with the composed mapper: that's where distribution happens, when the *written* check type parameter turns out to be a union, however many instantiations later (`Exclude<keyof T, K>` inside `Omit<T, K>`). Branches that mention the alias being resolved are lowered on first use (`TyCondBranch`), like array and tuple nodes in that position (`ty_deferred_reference()`, tsc's deferred type references: `type Json = string | Json[]`).
- `lower.c`: `ty_from_node()` is the only producer of `Ty` from syntax; the symbol entry points are described above. Anonymous object types are keyed by the *address* of their node, which is stable because nodes belong to the AST.
- **Alias names**: unions, intersections, object types, arrays/tuples (as deferred references), `T[K]` and conditional types written as the body of an alias carry `Ty.alias` + `alias_args`, instantiation instantiates the arguments, and `ty_realias()` renames the instantiation of a generic alias that is itself the body of another alias (`type Bar = Omit<Foo, "c">` prints as `Bar`). A homomorphic mapped type instantiated with an array or tuple becomes an array or tuple (`instantiate_mapped_over_list()`).
- `ty_display.c` prints like tsc's `typeToString()`: alias name, else reference name + arguments (`T[]`, tuple syntax), else declared name, else structure.
- The `.types`/`.symbols` test traversal (`src/test/baseline_test_traversal.c`) prints `Ty`s with `TyDisplay.unqualified_names`; the one exception is a declaration whose type is a written type *name*, which prints as written (see `hacks.md`).

### Engine
tttt includes a JavaScript interpreter that evaluates an AST. It's not fast, standards complaint, tested, complete, or a priority.

## Phases
The process of loading and typechecking TypeScript code is done in several phases

### Load from the filesystem
Cleat's `Fs` abstraction allows tests to mock the filesystem, so the `Program` sees multiple files without the test runner having to write them to disk. The mock lives in [src/test/mock_fs.c](src/test/mock_fs.c); everything else uses the `fs` global.

### Parse
The parser creates an AST from the source code string, see below.

### Resolve names
`program_resolve_names()`, three steps over all files. This is also the intended parallelism contract: declare and resolve are meant to run per file, writing only to the file's own AST and symbols, with the small sequential link step in between being the only one that touches what files share (`agents/hacks.md`, "Parallelism contract audit", lists what still breaks that: globals, ambient modules, the one binder arena).
1. **Declare** (`*_add_names()`): every file gets its scope (a module also its module symbol), and the declarations of files, namespaces, enums and `declare global` blocks become symbols. Same-table conflicts are reported here.
2. **Link** (`binder_link()`): `export *` tables are flattened and every alias is resolved, so that nothing writes to a symbol afterwards; import conflicts (TS2440) are reported.
3. **Resolve** (`*_lookup_names()`): the deep walk. It makes the function and block scopes as it enters them (declaring their names first, so uses before the declaration resolve) and stores on every identifier the symbol it found plus the symbol that has the meaning it is used with (`target`).

Imported files are discovered while loading, from the parser's list of module names (`SourceFile.module_refs`; `program_handle_statement()` only follows `/// <reference>` directives and decides whether a file is a module), before any of this. Between declare and link every `ModuleRef` is resolved to its module symbol, which needs the ambient modules of all files.

### Typecheck
The AST is now in it's finished state, so we can traverse it looking for type errors. This is the phase when the `*_evaluate_type()` functions are called (via `ty_from_node()` / `ty_expr_type()` -> `lazy_type_get()` -> `lazy_type_evaluate()` -> `*_evaluate_type()`), each returning a `Ty const*`

## Memory Management
The source code and ASTs of all parsed files is kept valid until after all above phases have finished. The AST holds references to the code (via spans) and any types created from the AST may hold references into the AST, so it would not be safe to free either the code or the AST while anything created from it remains in use. Furthermore the AST should not be structurally modified after parsing to keep pointers valid (ex pushing to a vec that's part of the AST is generally unsafe, since it may trigger a reallocation and invalidate other elements).

### Types
`TypeNode`s are owned by the AST. `Ty`s, their members, signatures, mappers and everything else the checker makes live in the arena of their `Checker` and are freed with it; nothing in the type core is individually freed or reference counted. `program_drop()` drops the checker before the AST, because types point into the AST.

A function type or signature written as a type (`TYPE_CALLABLE`) is a `CallableType { FunctionImpl* }`: a `FunctionImpl` without a body and with `is_type` set, so there is one way to resolve a signature (`signature_resolve()` reads parameters and return type off the `FunctionImpl`, `is_type` only decides how they're lowered). A node that declares a symbol (`GenericItem`, `InferredType`, a mapped key) has both `owned_symbol` and `symbol_ref`, a leftover from when nodes were cloned.

### Declarations
In TypeScript multiple declarations in the source code can contribute to a single logical declaration (this is known as declaration merging). `scope_init_declaration()` hands back the `Symbol` the declaration ended up in: a fresh one, an existing one it merged with (the declaration is appended to `Symbol.decls`), or a detached one when merging was an error. Symbols belong to the `Binder` and live as long as the program; AST nodes don't own them.

## Parsing
As mentioned above the parsing framework is custom, but it should be fairly straightforward.

### Parser struct
Each parse function (generally) creates it's own instance of `Parser` named `p`. This stores a current position in the source code, a pointer to the parser one level up (it's "parent") and some other things.

Each perse function receives a pointer to it's parent parser as an argument, as well as a pointer to an instance of the data structure it will attempt to populate, called `ret`. It returns a bool:
- `parse_success(&p)` - the function successfully parsed it's thing, `ret` is populated, the parent's current position is updated to match `p`'s position and any errors added to this parser or children **are** added to the parent
- `parse_fail(&p)` - the function did not parse it's thing, `ret` is undefined (could be unchanged, could be 0s, could be junk data, does **not** need to be dropped), the parent's position is not changed and any errors added to this parser or children are dropped (**not** added to parent)

`parse_success()` **always** returns true and `parse_fail()` **always** returns false. This makes it easy to return the correct value along with calling the corresponding parser cleanup function. It's **almost always** incorrect for these not to match up 1:1. The exceptions are simple low-level parse functions that avoid creating their own parser instances for performance, and a couple places where child parsers are created in the same function as their parents.

Note that a parser can succeed without errors, succeed with one or more errors or fail without errors. It **cannot** fail with errors (any errors added are silently dropped on fail). The idea is a parser either parsed something and advanced the current position (success) or did not (failure). Errors are only relevant when a parser parsed something, and understood a way that thing is wrong.

### Tokens
Because there are no tokens, `/` needs no rescanning: `parse_expr()` is only ever called where an expression may start, so a `/` there is a regular expression literal (`parse_regex()`, `EXPR_REGEX`), and anywhere else it's a division.

Unlike other typescript/javascript parsers, tttt doesn't tokenize before parsing. Sometimes tokens are needed though (such as when an error message for an unexpected token is to be added), which is what `hop_token()` is for. It's not called for most code.

### Anchors
Anchors are helpful for making spans. They are created with `anchor(&p)`. `span_from(a)` creates a span from the parser's position when the anchor was created to the parser's current position.

### Whitespace
`hop_whitespace(&p)` needs to be called anywhere whitespace may appear.

Newlines are generally ignored but change how js/ts are parsed in some cases. For this reason parsers keep track of if the last whitespace they hopped contained a newline. This gets propagated to the parent on success.

### Function context
Whether `await` and `yield` are operators or plain identifiers depends on the function being parsed. `ParserShared` keeps `in_async`, `in_generator` and `function_depth`; `function_ctx_enter()`/`function_ctx_leave()` wrap the parsing of every function's parameters and body (see `parse_non_arrow_function()` and `parse_arrow_function()`), and `FunctionFlags` carries `async`/`*` from whoever saw the keyword to the function parser. Since a source position is always inside the same function, this doesn't conflict with the fail cache.

### Fail cache
The fail cache is used to cache specific locations where specific parse functions have failed to parse before. There are some cases (such as arrow functions vs parenthesized expressions) where the correct way of parsing something is not obvious until after the parser has parsed some sub-expressions. If these cases are nested the time complexity of doing this naively is Not Good. However if you keep track of where you've tried and failed to parse specific things it's fine, so that's what we do. For details on precisely how it works you'll have to decipher the code.
