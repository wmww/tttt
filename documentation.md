# tttt Documentation

## Programs
The repository contains three programs.

### tttt
The actual typechecker, drop-in replacement for tsc. See `build/tttt --help` for usage.

Can be compiled and run with `./run.sh`. This makes a debug build and runs it under Valgrind, so won't be fast.

Completely written in C. Code lives in [src](src/). The only dependency is [cleat](https://codeberg.org/sphi/cleat), an MIT-licensed standard library for C which comes with its own vendored copy of the STC container library (no relation to the swc-related project of the same name). It's included in this repository under [thirdparty/cleat](thirdparty/cleat/), and automatically compiled by the build system. `thirdparty/refresh.sh` re-downloads it at the pinned commit.

### baseline_tests
Runs tttt against TypeScript's official test suite. See `build/baseline_tests --help` for usage.

Can be compiled and run with `./test.sh` (debug build, under Valgrind, takes minutes) or `./fasttest.sh` (release build, not under Valgrind, takes seconds). Features like regex filtering and displaying diffs are supported, see `./test.sh --help` for details.

Like tsc's harness, a multi-file test whose last file mentions `require(` or `reference path` (or that sets `@noImplicitReferences`) has that file as its only root: the others are part of the program only if something refers to them, and the root comes first in the baselines.

Like tsc's harness, tsc's `tests/lib` folder is at `/.lib` in the mock filesystem (copied in only for tests that mention `/.lib/` or set `@libFiles`): `/// <reference path="/.lib/react16.d.ts" />` finds it, and `@libFiles: react.d.ts,lib.d.ts` makes those files roots after the test's own (a `lib.*.d.ts` among them is shown as `Decl(lib.d.ts, --, --)` and, saying `no-default-lib`, replaces the default lib). The types and symbols baselines go through tsc's `removeTestPathPrefixes` (`/.src/`, `/.lib/`, `/.ts/` disappear). The `=== Performance Stats ===` block tsc's harness puts at the top of big tests' types baselines (its own checker's cache sizes and type counts, rounded: `generateBaseLine` in harnessIO.ts) is dropped from the expected side before comparing (`perf_stats_block()` in `test/baseline_test_result.c`): it measures tsc, not the types.

The tests target includes most `tttt` code, as well as additional C code in [src/test](src/test/).

### diffapp
A graphical app that allows you to edit TypeScript code and see tsc's and tttt's test output for that code in real time. It watches for changes to tttt's source code, and recompiles and re-runs tttt on save.

Generally run via `./diffapp.sh`. A test name or source file can be specified. If there's already a running instance the script will send the given test to that instance.

It's a nodejs web app with an html/css/js frontend in [test/diffapp](test/diffapp/). It's intended to run locally (basically uses the browser as a GUI toolkit only). The tttt integration lives in [src/test/diffapp_runner.c](src/test/diffapp_runner.c).

## Architecture
To keep development fast, LoC down, Tess sane and (in specific cases) tttt fast, we do things the most straightforward way wherever possible.

### AST
At the core of tttt is a TypeScript AST (Abstract Syntax Tree). This is a data structure that maps to parsed source code, and on which the typechecker runs. AST nodes are:
- `Block` - sequence of statements, often surrounded by `{` `}`s
- `Statement` - chunk of code that does not result in a value, often each on their own line or separated by `;`
- `Binding` - assignments and function parameter lists use bindings. They are often simply identifier names, but can be more complicated in the case of destructuring
- `Expr` - nestable expression, such as a function call or value literal
- `TypeNode` - the *syntax* of a type, as written (functions are named `type_*()`, tags `TYPE_*`). The checker's semantic types are a different thing, `Ty`, see "The type core" below

This list is not exhaustive as there are other structs owned by these. Each of these structs has it's own `.h` and `.c` files. Look through them for more details.

There is no AST node struct, interface or visitor. The AST is simply a *concept* that includes these structs, and is relevant for reasoning about the architecture.

### Span
A span is a reference to a section of source code, often used for error messages. Spans don't own anything, and don't need to be dropped. Identifier names are generally stores as spans.

### Display
tttt has its own rendering pass for AST nodes in [src/display.c](src/display.c), driven by a `Display` struct (`display_type()`, `display_expr()`, ...). It stays separate from [cleat's display system](thirdparty/cleat/docs/display.md) because it's on the typechecker's hot path (every failed type comparison renders both types into a message) and because it has rendering modes cleat knows nothing about: `debug` (the developer-facing tree), `brief` (the same, truncated), `parsed` and `underline` (used by the test runner to underline a type within its rendering).

The two systems are bridged in [src/display.h](src/display.h). `declare_ast_display()`/`impl_ast_display()` generate a cleat display function per AST node, so `Span`, `TypeNode const*`, `Expr const*`, `Error const*` and friends are all in `DISPLAYABLES`, and so is `Ty const*` (a semantic type, printed the way tsc prints it in messages) and can be passed straight to `println()`, `cstr_d()`, `panic()`, `log_error()`, `error_ctx_error_d()` and so on. A plain sequence gets the TypeScript-diagnostic form, `debug_d(x)` gets the developer form and `brief_d(type)` gets the truncated one.

Everything that isn't an AST node goes through cleat's display system directly; `src/` has no `printf`-style format strings left apart from JavaScript's number-to-string precision in `value.c`.

### Parser
The parser (including a minimal custom parsing framework) lives in `parser.c`. We do not compile grammars, combinate or tokenize. We simply take a const char* and use it to build an AST. Like real men.

See dedicated section below for details.

### Program
The `Program` struct owns the source code buffers and ASTs of all loaded files, manages imports, etc.

### CompilerOptions
`CompilerOptions` ([src/compiler_options.h](src/compiler_options.h)) is what tsc calls the same: every boolean option (one X-macro list, with which ones belong to the `strict` family), `target`, `module`, `moduleResolution`, `jsx`, `moduleDetection` and `lib`. `compiler_options_set(options, "strictNullChecks", "false")` takes names and values as they're written in a tsconfig, on the command line (`tttt --target es2020 --strictNullChecks false`) or in a test's `// @target: es2020`; `compiler_options_resolve()` then applies tsc's dependent defaults (`strict` to its family, `target` from a node `module`, `module` from `target`, `moduleResolution` from `module`, `useDefineForClassFields` from `target`...), so every field holds the effective value. `moduleDetection` is applied when a file is loaded (`program_add_source_idempotent()`): besides imports and exports, `force` makes every non-declaration file a module and `auto` (the default) does for `import.meta`, `.mts`/`.cts`/`.mjs`/`.cjs`, an ES module package format, and JSX under react-jsx. `compiler_options_lib_files()` gives the standard library files to load: the `lib` list, else the default library of the target (`lib.d.ts`, `lib.es6.d.ts`, `lib.es2016.full.d.ts`...).

Each `Program` owns one (`program_options()`, change it before loading files). Code that parses, resolves names or checks reads the current program's through the global `compiler_options()`, which `program.c` sets around each phase. Most options are parsed but not acted on yet. The resolution options (`baseUrl`, `paths` with the directory they are relative to, `rootDirs`, `typeRoots`, `types`, `moduleSuffixes`, `customConditions`, `config_dir`) are strings and `StrList`s as written; `module_resolution.c` makes them absolute.

### Test configurations
A tsc test whose directives give several values for an option (`// @target: es5,es2015`, `// @strict: *`, `// @module: *,-amd`) is several tests, each with baselines named `name(option=value,other=value)`. `baseline_test_configurations()` (`src/test/baseline_test_case.c`) follows tsc's `getFileBasedTestConfigurations()`: only boolean and enum options vary (a comma in `@lib` or `@types` is a list), `*` means every value of the option, `-x` excludes one, spellings of the same value (`es6`/`es2015`) collapse, option names are sorted. The suite holds one `BaselineTestResult` per configuration; `-f someTest` matches all configurations of a test, `-f 'someTest\(target=es5\)'` one. Tests with `// @noTypesAndSymbols: true` have no `.types`/`.symbols` baselines and are compared on errors alone.

### Symbols, tables, scopes (the binder, `scope.h`/`scope.c`)
The model is tsc's, because the symbols baseline, the merging rules and the diagnostics encode it:
- A `Symbol` has tsc's `SymbolFlags` (what it *means*: value, type, namespace, alias), its `parent` container (set for exports only, like tsc), every declaration that contributed to it as a `SymbolDecl { kind, flags, node, name, full }` (the AST node: `Binding`, `FunctionImpl`, `ClassDecl`, `InterfaceDecl`, `EnumDecl`, `EnumCase`, `TypeDecl`, `GenericItem`, `InferredType`, mapped key, `NamespaceDecl`, `PortItem`, `export default` expression, builtin) and, for namespaces, enums and modules, one `exports` table **shared by all declaration blocks**. Symbols, tables and scopes live in the arena of the program's `Binder` and are never copied or freed individually; what only aliases and modules need is in side structs (`SymbolAlias`, `SymbolModule`).
- **Merging is `declare_symbol(table, name, includes, excludes)`** with tsc's `*Excludes` masks verbatim: `var`+`var`, function+namespace, class+interface, enum+enum, interface+anything that isn't a type, alias+anything that isn't an alias merge; anything else is TS2300 / TS2451 (block scoped) / TS2567 (enums) on every declaration of both sides, and the newcomer gets a detached symbol. Side rules (TS2434, TS2440, duplicate type parameters) are checks next to it.
- A `SymbolTable` is insertion ordered (namespace members come out in declaration order), scanned linearly up to 8 entries and indexed beyond, keyed by views into the source, and may overlay a read-only `parent` table: a test program sees the globals of the cached lib program without copying them, and adding to a lib symbol clones it into the overlay first (`clone_parent_symbol`). Nothing is written to the frozen original; references inside the lib AST still point at it, so the checker maps every symbol it is handed through `binder_redirect()` (`Binder.overlays`, only consulted by programs that have overlays) and lib-internal uses see the program's additions.
- A `Scope` is `{ parent, kind, locals, container }` and **persists**: the file scope is on the `SourceFile`, a namespace block's on its `NamespaceDecl`; function/block/type-parameter scopes are made by the resolve walk (nothing keeps a pointer to those; every scope knows the function it is in, `Scope.function`, and during the walk the flow builder of its container, `Scope.flow`). Declarations made in a module/namespace/enum scope go to the container's `exports` when exported (or when the scope is an ambient *export context*), to `locals` otherwise; scripts and `declare global` declare into `Binder.globals`. `var`s hoist: `block_add_names()` of a function/module/namespace/static-block scope also runs `statement_hoist_names()`, a statement-only walk that declares the `var`s of nested blocks, which those blocks then skip.
- **Lookup is by meaning and sees through aliases**: `scope_resolve(scope, name, meaning)` walks the parents, checking locals and then the container's exports (so a second `namespace N {}` sees the first one's exports, and non-exported members stay out of `typeof N`); a symbol matches when its flags have the meaning or when it is an alias whose target does. That is what lets `import { Node } from "./types"` (an interface) merge with a local `function Node()`.
- **Imports and exports are alias symbols** (`scope_add_port()`): import/export specifiers, default imports, `import * as`, `export * as`, `import x = A.B.C` (resolved lexically from the scope it was written in), `export default x`. `symbol_resolve_alias()` is memoised with an in-flight state. A module's `export *` targets are a list on the module symbol; `module_resolved_exports()` flattens them once (own exports shadow stars, first star wins, `default` doesn't travel, cycles are fine). What can't be resolved becomes a *placeholder* symbol that has every meaning and is `any`.
- **Modules.** The parser records every module a file names in `SourceFile.module_refs` (`ModuleRef { path, span, file, module }`: import/export declarations, `import x = require("m")`, `import("m")` types and expressions, `declare module "m"`), wherever it is written; the program loads the files from that list. `binder_module_of_ref()` says what a name refers to: an ambient module of that name (`Binder.ambient_modules`: every `declare module "m" {}` block of every script declares into one module symbol), else the module symbol of the file the program found, else a pattern ambient module (`"*.css"`, longest prefix). `declare module "./a" {}` inside a *module* is an augmentation: its declarations go straight into the exports of the module it names (everything in it is exported). `declare module "m";` is a shorthand module: imports from it are placeholders (any). `export = x` is an export named `export=` (an alias, or a variable for other expressions) and `module_export_equals()` is what importing the module gives (`import x = require()`, `import * as`, default imports, named imports look into it). `export as namespace N` is a global alias of the module. `globalThis` is a namespace symbol whose exports *are* the globals table (`binder_redirect()` maps the shared lib program's one to the current program's).
- **Import types** (`import("./a").B<T>`, `typeof import("./a")`) are `IdentifierType`s with an `import_ref`: the names are looked up in the module's exports instead of the scope, for `typeof` as values and then as properties from `import_prop_start` on. `import("./a")` the expression is a call of the keyword identifier `import` (`KEYWORD_IDENTIFIER_IMPORT`, carries the `ModuleRef`) and gives a `Promise` of the module's type.
- **Symbol accessibility when printing** (`symbol_chain.c`, a port of tsc's getSymbolChain / getAccessibleSymbolChain / needsQualification / getContainersOfSymbol): how a symbol is named from a `Scope`. The tables in scope are tsc's, from the inside: block/function locals, a module's or namespace's locals (with its exported declarations, like tsc's locals with an `exportSymbol`) and then its exports, the globals. A symbol is named by the first table that has it by name, or through an alias in it (`import * as ns` gives `ns.x`, `import b = a.E` gives `b.x`), else by its container's chain (`N.x`); a module that nothing names starts no chain (symbols baseline) or `import("m")` (types, `yield_module`). The symbols baseline passes no meaning (tsc's `symbolToString(symbol, node.parent)`), so shadowing never qualifies there; the types printer passes one (`out_symbol_name()` in `ty/ty_display.c` with `TyDisplay.enclosing`). The test traversal tracks the enclosing file/namespace scope (`BaselineTestCase.enclosing`); function and block scopes don't change how anything is named. Without an enclosing scope (error messages) names are bare, like tsc's lookupSymbolChainWorker (`N.E` prints `E`; enum members keep their enum: `E.A`), and fully qualified (`TyDisplay.fully_qualified`) only where a message shows a source and a target that would print the same (`display_pair()` in `ty/relate.c`, tsc's getTypeNamesForErrorDisplay).
- **Symbols are what the checker knows things by.** AST nodes that declare something keep a `Symbol*` (`symbol`), identifiers keep the symbol the name found (`symbol`, maybe an alias: what the symbols baseline shows) and the one that has the meaning the name is used with (`target`, aliases resolved: `symbol_for_meaning()`, cached so checking never chases alias chains). `this` is a `ThisRef { kind, symbol }` found through `Scope.this_ref` (class instance, class static side, `any`, or a `this` parameter). Nothing in a `Symbol` is written after `binder_link()`; per-symbol checker state is `SymbolLinks` in `Checker.links`.

### LazyType
`LazyType` is a struct owned by the AST: the memoised, cycle-detecting type of whatever contains it (an `Expr`, an `InitializedBinding`, a for-each variable, a `FunctionImpl`, a class field or accessor). It exists so that something can *refer* to a type during name resolution, long before the type can be evaluated. Declared things (classes, interfaces, enums, aliases, namespaces) don't have one: their types are memoised per `Symbol` by the type core.

The process goes something like this:
1. An AST struct, for example `Expr`, contains a `LazyType`
2. In the resolve names phase, it calls `lazy_type_bind(&lazy, LAZY_TYPE_EXPR)`, which sets the tag and gives the LazyType a *slot* number
3. Whoever needs to refer to that type keeps a pointer to the LazyType or to what contains it: a `Binding` points at the LazyType of what is assigned to it (`Binding.source`, the initializer or the for-each variable type), an element of a destructuring pattern at its parent pattern (`Binding.parent`), a class property at its field/accessor LazyType (`Prop.lazy`). There are no link nodes: a `TypeNode` is syntax only, exactly what the parser made
4. Later, in the typecheck phase, whoever wants the type calls `lazy_type_get()` (`ty_binding_type()` for a binding: the written type, else what is assigned, else the property/element of the parent pattern's type)
5. The tag of the LazyType is `LAZY_TYPE_EXPR`, so `lazy_type_evaluate()` uses the pointer to the LazyType to calculate a pointer to its containing `Expr` and calls `expr_evaluate_type()`, which returns a `Ty const*`
6. That goes into the LazyType's memo (`LazyMemo`), and future calls to `lazy_type_get()` return it directly

LazyTypes play a critical role in detecting self-referential types. While a LazyType is being evaluated its memo is in an in-flight state. If something tries to evaluate it again in the same call stack its type becomes the error type (`TY_ERROR`, an `any`). That is the job of *declarations* (where tsc detects and reports circularity): an expression's memo that is hit again while in flight just evaluates again (control flow analysis of a loop re-enters the expressions of the loop body, see "Control flow"; `LazyMemo.hits` stops a runaway), so that the answer doesn't depend on who asked first.

**The memo is not in the LazyType.** The LazyType itself never changes after the resolve names phase: it's a tag and a slot number, and the memo lives in the slot storage (`LazySlots`, a sparse three level table allocated on first touch) of the current `Checker` (`current_checker` / `current_lazy_slots`, thread local). Each `Program` has one checker, created by `program_make_current()`, which `program_typecheck()` calls; call it yourself to look at the types of a program that wasn't typechecked. This keeps the AST read-only while checking, which is what lets many programs share one lib AST (the test harness does) and later lets several checkers work on one AST. `LAZY_TYPE_EVALUATED` is the tag of `expr_implicit_any()`: nothing to evaluate, no slot.

### The type core (`src/ty/`)
Semantic types are `Ty` (`src/ty/ty.h`), and everything that has a type evaluates to one: written types are lowered from their `TypeNode` (`ty_from_node()`), expressions are checked by `ty_check_expr()`, functions, classes, interfaces, enums, namespaces and merged declarations have their types built from the AST. There is no other representation: the value-semantic `Type` trees this project started with (cloned, dropped, substituted into) are gone, and `TypeNode` is never created, cloned or resolved by the checker (there is no `type_clone()`).

The statement/expression walk (`statement_typecheck()`, `expr_typecheck()`, `binding_typecheck()`, `class_decl_typecheck()`...) stays in the AST files and asks the type core for types and checks: `ty/check.c` has the ones with tsc's error wording (`ty_check_assignable()` for TS2322 and its elaboration, `ty_check_property_access()`, `ty_is_comparable_either_way()`), and `ty_of_node()` lowers a written type with the current checker.

- **Symbols know their AST nodes** (`Symbol.decls`, filled by `scope_init_declaration()`), and `lower.c` turns a symbol into types from them. `ty_declared_type_of(symbol)`: interface / class instance type (one `TY_DECLARED` per symbol, the type parameters of later interface declarations unified with the first's), enum, enum member, type alias body, type parameter (`SYMBOL_TYPE_PARAMETER`: declared ones, `infer X`, mapped type keys), in-flight detection for circular aliases. `ty_static_type_of(symbol)`: the static side of a class, the object of an enum. `ty_type_of_symbol(symbol)`: the symbol as a value, from the declarations that contribute one (the first variable declaration, function signatures, class static side, enum object, namespace object, enum member, `export default` expression); one contribution is that type, several are `ty_merged_value_type()`. Variables aren't memoised per symbol: the binding's own LazyType is the memo and the cycle detector. The members of a declared type come from the same nodes: every merged interface body, a class's fields/methods/accessors (overloads hide the implementation signature), inherited instance members, and for the static side `prototype`, static members, inherited static members and the construct signatures (the class's own, else the base class's with this class as the return type).
- **Enums** (`enums.c`): an enum's type is the union of its members' types with the enum as the union's alias (that's how it prints as `E`, and `formatUnionTypes`-style collapsing prints a full run of members inside a bigger union as `E` too). A member's type is a literal type keyed by (value, enum), so members with equal values share a type, like in tsc (the member's declared type is the fresh twin, the enum union holds the regular ones, a written `E.x` is regular); a member whose initializer isn't a compile time constant gets an opaque "computed" type (`TYF_ENUM`). Values come from a small constant evaluator over `Expr` (literals, unary/binary operators, references to other members). The enum object (`typeof E`) has a readonly property per member and the numeric reverse mapping.

- A `Checker` owns an arena, a type id counter and the intern tables. Every `Ty` is immutable once published and interned, so **pointer equality is type identity**: `List<string>` is one pointer no matter how often or where it's written. Ids are handed out in creation order and intrinsics are created in tsc's order, because unions print in id order.
- Intern keys are small arrays of `u64` words (a `KEY_*` tag followed by ids/pointers, `ty_internal.h`) in one open addressing table type (`InternTable`). `Checker.types` holds literals, unions/intersections, references, tuple targets, deferred types and instantiated anonymous types; `Checker.links` holds everything that is *about* an AST node or `Symbol` (`SymbolLinks`: declared and static types; merged value types, type parameters, anonymous types by node, alias instantiations), so the AST is never written to. `intern_slot()` pointers die on the next insert into the same table; use `intern_get()` and look the slot up again when the value takes interning to compute.
- Kinds: intrinsic, literal (incl. enum members; a regular literal and its fresh twin are two `Ty`s, see Freshness under Expressions), type parameter, declared (interface, class instance/static side, enum object, namespace value, tuple target), reference (generic declared type + arguments; arrays are references to the global `Array`, tuples to a tuple target), anonymous (type literal / function type by AST node, or `{target, mapper}` instantiation), union/intersection (sorted by id, cheap reductions only, alias is part of the identity like in tsc), and the deferred `keyof`/indexed access/conditional types, whose constructors resolve eagerly when they can. A mapped type becomes ordinary properties and index signatures once its key type is known (`expand_mapped()`).
- **Members are lazy** (`members.c`): `ty_members()` resolves props, call/construct signatures and index signatures on first use; `prop_type()` and `signature_resolve()` lower or instantiate the types inside on first use. That is what makes recursive types legal and cheap. An instantiated signature (`{target, mapper}`) gets fresh copies of its own type parameters that have a constraint or default (`clone_type_params()`, `TyParamState.clone_of`); `ty_signature_instantiation()` replaces a signature's type parameters by type arguments (memoised), `ty_instantiate_signature_in_context_of()` infers them from another signature's parameters (tsc's instantiateSignatureInContextOf), which is how a generic source signature is related to any target (`compare_signatures()`).
- **Instantiation never copies** (`instantiate.c`): `ty_instantiate(ty, mapper)` returns `ty` itself unless it has `TYF_COULD_CONTAIN_TYPE_VARIABLES`, rebuilds interned kinds through their constructors, and turns an anonymous type into an interned `{target, mapper}` pair restricted to the type parameters the node actually mentions (`free_params`).
- **Functions** (`function.c`): the type of a function declaration, function expression, method, accessor or constructor is an anonymous object type with one signature that is read straight off its `FunctionImpl` (`Ty.anonymous.function`, `Signature.function`): type parameters from its `Generic`, parameter types from the bindings, and the return type from the annotation or, lazily, from the `return` statements of the body (`ty_function_return_type()`: the union of what `block_collect_return_types()` finds, subtype reduced and widened, plus `undefined` when the end of the body is reachable or there is a bare `return;` (strict), `void` without returns, `never` for a function expression that can't return, wrapped in `Promise` for async functions, memoised per function with an in-flight state so a function that returns its own call is `any`). A function *type* (`(a: T) => R`) is a `TYPE_CALLABLE` node that owns a body-less `FunctionImpl`.
- **Namespaces and merged declarations** (`lower.c`, `members.c`): the value of a namespace (or of a module, for `import * as ns`) is a declared type by `Symbol` with a property per value among its exports, by export name and in declaration order (`ty_namespace_type()`; the type of such a property is `ty_type_of_symbol()` of the member, `Prop.symbol`). A symbol several declarations give a value to (function overloads, a function/class/enum merged with a namespace) gets the members of all of them (`ty_merged_value_type()`): anonymous for overloads alone, by name (`typeof f`) otherwise.
- **Relations** (`relate.c`): `ty_is_related(source, target, relation)` for assignable, comparable, strict subtype (union reduction) and an assignable variant with strict nulls. It follows tsc's structure because the observable results depend on it: simple relations by flags first, then a per-relation cache on the checker keyed by `(source id, target id)`, a "maybe" stack for pairs that are being compared further up (assumed related, made definitive when the outer comparison finishes), a deep-nesting check on the generic target of the types on the stack (what terminates infinitely expanding generics), and for two references to the same generic type a comparison of the type arguments by *measured variance* (`get_variances()`, marker type parameters, cached in `Checker.links`). Signatures follow tsc's signaturesRelatedTo (instantiations of one type pair up, a single signature on each side keeps its type parameters, N x M erases them and only the first source signature explains a failure) and compareSignaturesRelated (two callback parameters are compared as signatures, the other way around: `CallbackMode`). Which comparisons run with `report` is observable, because a cached failure is only computed again (and a pair on the stack only assumed related) for a comparison that reports. `ty_explain_unrelated()` reruns a failed check in reporting mode and returns tsc's elaboration chain, outermost line first; the first line is either the generic TS2322 head or something that replaces it (TS2741 missing property...). Lines are collected innermost first in `RelationState.lines`; a step down ("Types of property 'a'", signature return types, tuple positions) is pushed as a pending `incompatible` line by `report_incompatible()` and stands in for the next "not assignable" line, and consecutive pending steps collapse into one path line ("The types of 'a.b' are incompatible between these types.") when anything else is reported (`flush_incompatible()`, tsc's reportIncompatibleStack). `TTTT_DEBUG_RELATE=1` logs every top-level query, `TTTT_DUMP_VARIANCES=1` every measured variance.
- **Calls** (`call.c`): `resolve_call()` collects the call or construct signatures of the callee's apparent type (a union is called member by member, an intersection through all its members' signatures), and `resolve_with_signatures()` takes the first candidate that fits, like tsc's `resolveCall`: arity (`ParamShape` spreads a tuple rest parameter out, `Args` spreads tuple spread arguments out), type arguments inferred from the arguments, every argument related to its parameter, with a subtype round before the assignable round when there are overloads. Arguments are checked with the candidate's parameter types as contextual types; a generic candidate infers in two passes (context-sensitive arguments, ie lambdas with unannotated parameters or context-sensitive returned expressions and literals containing them, come second and see the parameter type instantiated with what the first pass found), also from the contextual type of the call to the return type at low priority. The second pass also takes, in argument order, generic function arguments where the parameter wants a non-generic signature (instantiated in its context, or, if the call returns a function and not everything is inferred yet, propagated: the argument's type parameters become the returned function's, tsc's higher-order inference, `Candidate.inferred_type_params`) and calls of generic functions that return functions (which then see the other arguments' inferences through `Checker.outer_inference`). Explicit type arguments (`f<A>(x)`, a `GenericParamsExpr` around the callee) select candidates by type parameter count (TS2558), replace inference, and are checked against the constraints (TS2344). When nothing fits the errors are tsc's: TS2554/2555/2575 for arity, the argument error of a lone candidate, TS2769 with one "Overload n of m" branch per candidate otherwise. A tagged template (`` tag`a${x}` ``) is a call too (`ty_tagged_template_return_type()`): a stand-in `CallExpr` with the tag as callee and the substitutions as arguments, after a `TemplateStringsArray` that `collect_args()` adds for `CallInfo.tagged_template`; an unterminated template is an incomplete call (no minimum arity).
- **Inference** (`infer.c`): one walker (`infer_types()`) for generic calls and for `infer X` in conditional types. It keeps covariant and contravariant candidates apart (parameters flip the direction under `strictFunctionTypes`, reference type arguments by measured variance), knows priorities (a naked type parameter in a union gets what the other members didn't match), and records whether the type parameter was only seen at the top level of a parameter type. `inference_call_result()` is tsc's `getInferredType` for calls (literal widening unless the constraint is primitive or the type parameter is at the top level of the return type, common supertype, covariant preferred over contravariant when it fits, `unknown`/default/constraint fallbacks are in `infer_type_arguments()`); `inference_conditional_result()` is union / intersection. `InferParam.fixed` is the seam for the context-sensitive second pass that comes with contextual typing.
- **Expressions** (`expr.c`): `ty_check_expr(expr, contextual)` is the one entry point. There are no parent pointers to find a contextual type through, so the rule is the other way around: **whoever knows an expression's contextual type checks it with that type before anything else asks**, and the result is the expression's memo (`lazy_type_set()`, with the contextual type it was computed for in `LazyMemo.context`); `ty_expr_type()` reads the memo and only checks without context if nobody got there first. A variable declaration checks its initializer with the annotation, `return` with the function's return type (`Checker.return_context`), an assignment with the target's type, a call checks each argument with its parameter type (per overload candidate), object and array literals pass the property/element type of their own contextual type down (`contextual_prop_type()`, `contextual_element_type()`), and `expr_typecheck()` evaluates an expression's own type before walking into it. A function expression takes the types of its unannotated parameters from the first contextual signature it meets and keeps them (`assign_contextual_signature()`: links keyed by parameter, read back by the parameter's own LazyType; tsc does the same), while literals are simply checked again for a new contextual type. **Freshness** (tsc's model): a literal expression (and `-1`, `!x` of known truthiness, an enum member's value) evaluates to the *fresh* twin of its literal type (`ty_fresh_literal()`, a separate interned `Ty` with `TYF_FRESH_LITERAL`); written types and everything derived from them hold regular ones. Only fresh literals widen (`ty_widened_literal()`; `ty_base_type_of_literal()` widens regardless, for operators and messages): a mutable location (`check_for_mutable_location()`) widens unless the contextual type has room for literals and then regularises, a declaration (`ty_widened_for_declaration()`) widens without regularising (`const e = E.x` holds the fresh `E.x`), an inferred unit return type likewise. Relations normalise to regular (`ty_regular()`) at every entry, so caches never see fresh literals; so do switch clause types, index keys, `typeof`, intersection members, and the `.types` printer (expression types print regular). An object literal expression is a fresh object type too (`TYF_FRESH_OBJECT`, `OBJECT_LITERAL_FRESH`): relations see it as it is and give it excess property checks (`has_excess_properties()`, TS2353 at the property name via `TyReportLine.span`); declarations, inferred return types, inferences, `typeof` and union target members see its regular twin (`ty_widened_objects()`, built lazily with the properties widened recursively). A contextual tuple type or `as const` makes an array literal a tuple. `ty_identifier_reference_type()` is the one place the type of an identifier reference comes from (narrowing will live there).
- **Outer type parameters** (tsc's outerTypeParameters): a class, interface or type alias declared inside something
  generic captures the type parameters around it (`OuterGenerics`, recorded by the resolve walk). A class or interface's
  `Ty.declared.type_params` are the outer ones followed by its own (`outer_count`; `ty_local_type_params()` are the
  ones type arguments are written for), a reference inside the scope passes the outer ones as themselves, and the
  enclosing function's mapper instantiates them like any type argument: `f(3)` of `function f<T>() { class C {} ...}`
  is `f<number>.C`. A local class's value is its static side applied to the outer parameters.
- **`this` types** (`lower.c`, `members.c`): every class, and every interface that mentions `this` (or extends one that
  does), has a `this` type parameter (`Ty.declared.this_param`, constrained to the type seen from inside). The members
  as declared (`declared_raw_members()`, `Ty.declared.raw`) mention it, bases included, which are taken with the derived
  type's `this` as their this-argument; a reference carries an optional this-argument (`Ty.reference.this_arg`, part of
  its identity) and its members are the raw ones instantiated with the type arguments and `this` = the this-argument or
  the reference itself (`resolve_members_with_this()`); the declared type itself is its own this-argument. When only
  `this` is mapped, members whose declaration can't mention it (`Prop.thisless`, tsc's syntactic rules) are shared.
  The `this` expression is the `this` type parameter, and the apparent type of a type parameter is its constraint
  with the type parameter as this-argument (`t.chain()` is `T` for `T extends C`).
- **Unique symbols and iteration** (`checker.c`, `iterate.c`): a `unique symbol` is a `TY_LITERAL` with
  `TYF_UNIQUE_ES_SYMBOL`, one per declaration (`UniqueSymbolDecl`: the resolve walk marks the `unique symbol` annotation
  and the `Symbol()` initializer of a `const`, a `static readonly` field or a `readonly` property signature, so both
  mean the same type). Its `literal.string` is an escaped property name (`__@iterator@12`) that members are keyed by
  like any other name, and `ty_unique_symbol_of_name()` maps it back (display as `[Symbol.iterator]`, `keyof`).
  `ty_iteration_types_of_iterable()` is tsc's getIterationTypesOfIterable: references to the lib's iterable/iterator
  interfaces by identity, else `[Symbol.iterator]()` -> `next()` -> `IteratorResult`, cached per type id;
  `ty_iterated_type()` is what for-of, spread and array destructuring use (with tsc's ES5 gating and errors).
  Generators infer `Generator<Y, R, N>` from the `yield`s the resolve walk collected (`FunctionImpl.yields`) and their
  returns; a `yield` evaluates to the generator's TNext.
- **Property access** (`access.c`): `ty_access(object, index)` for a known index, through apparent types (`String` for strings, the constraint for a type parameter, `Function`/`Object` members), tuple elements, then index signatures. `index_type_evaluate_type()` is a wrapper around it, and so is the indexed access *type* `T[K]` once neither operand is generic (`try_resolve_indexed()`). Expressions that read go through `ty_access_reading()` (noUncheckedIndexedAccess adds undefined to index signature and rest element reads); a generic key on a non-generic object is the deferred `O[K]`. Writes: a property can have a write type of its own (`Prop.write_node`, a divergent `set` accessor's parameter type, `prop_write_type()`), which `ty_access_write_type()` finds for definite assignment targets (unions/intersections combine members) and `ty_compound_assignee_type()` for `o.x += v`. `ty_check_indexed_access_type()` checks `O[K]` written as a type (TS2339/2537/2538; the generic TS2536 isn't done).
- **Substitution types** (`TY_SUBSTITUTION`, tsc's): a type in the true branch of a conditional type whose check type it is (`T` in `T extends string ? Lowercase<T> : never`) lowers to (T, string), from the chain of true branches `TypeNode.flow` the resolve walk gives every node (`conditional_flow_type()`, lower.c; the chain also holds the templates of mapped types without `as`, where the key of a homomorphic mapped type over an array-constrained T is also `number | `${number}``); `NoInfer<T>` is one with an unknown constraint. Relations see `base & constraint` as a source and `base` as a target, inference targets the base and infers nothing into NoInfer, instantiation turns it back into the base once that satisfies the constraint (restrictively), and it prints as its base.
- **Conditional types** (`conditional.c`): `ty_conditional()` resolves as soon as the check type isn't generic at the top level: `infer` type parameters are inferred by walking check and extends type in parallel, the extends type is instantiated with the results and related: definitely false (the false branch) when not even the permissive instantiation relates, with every type variable the wildcard (`TY_WILDCARD`, tsc's wildcardType: an `any` that unions, intersections, indexed accesses, conditional and mapped types containing it collapse to), definitely true with the restrictive one (unconstrained stand-ins), deferred otherwise. A deferred conditional type remembers the conditional type it was written as and the mapper that leads from there to it (`Ty.conditional.root`/`.mapper`, tsc's ConditionalRoot), and `ty_instantiate()` always restarts from the root, with the mapper cut down to the root's outer type parameters (the ones its node mentions, `ty_conditional_outer()`) and the result cached by what those map to (tsc's getConditionalTypeInstantiation): that's where distribution happens, when the *written* check type parameter turns out to be a union, however many instantiations later (`Exclude<keyof T, K>` inside `Omit<T, K>`). Branches that mention the alias being resolved are lowered on first use (`TyCondBranch`). Array, tuple and generic interface/class references are *deferred references* (`ty_deferred_reference()`, type arguments lowered on first use by `ty_reference_args()`) where tsc's isDeferredTypeReferenceNode says so: the body of an alias (which the reference then goes by: `type B<T> = Box<T>` prints `B<string>`), or inside an alias body (`LowerCtx.in_alias`, tsc's isResolvedByTypeAlias: through unions, intersections, indexed accesses, conditionals, type arguments, arrays and tuples; not into object, function or template literal types) with an element or type argument that may resolve an alias (`may_resolve_type_alias()`) or defaulted type arguments: `type Json = string | Json[]`, `type RD<T> = ... ReadonlyArray<RD<I>>`. Their instantiations are keyed by what the node's outer type parameters map to. The template of a mapped type is lazy too (`ty_mapped_template()`, tsc's getTemplateTypeFromMappedType), and so is the per-key property its properties instantiate (`Prop.template_of`).
- **Diagnostics from deep inside the checker** go where tsc's `error(currentNode, ...)` puts them: `Checker.current_node` is the statement, expression (`compute()`), type reference or indexed access type being checked (`ty_enter_node()`/`ty_enter_expr()`/`ty_leave_node()`, which also start the instantiation count over like checkSourceElement/checkExpression), and `ty_error_at_current_node()`/`ty_error_at()` add straight to the program's diagnostics (only while typechecking, not while a baseline prints types). That's TS2589 (instantiation limits: `ty_instantiation_limit_reached()`, counted in `instantiation_limit_hits` so a check site doesn't add a TS2322 on top), TS2456 (a type alias re-entered while resolving: `Checker.aliases_in_flight`, every alias from it up fails when it finishes, tsc's pushTypeResolution), TS4109/TS4110 (a deferred reference's arguments), TS2615 (a mapped type property) and TS1062 (awaited type).
- **Template literal types and string mappings** (`template.c`): `TY_TEMPLATE_LITERAL` (texts as atoms around the types) and `TY_STRING_MAPPING` (`Uppercase<T>` & co., made where the lib's `type Uppercase<S> = intrinsic` is referenced, `intrinsic_alias_instance()` in lower.c). The constructors are tsc's getTemplateLiteralType / getStringMappingType: literals fold into the texts, unions distribute, only type variables and pattern placeholders (`string`, `number`, `bigint`, `any`, other patterns) stay as types. They carry `TYF_DEFERRED` only when generic: a *pattern* like `` `a${string}` `` is a concrete set of strings. Relations match string literals and templates against a template target by the text parts (`ty_template_matches()`, tsc's inferFromLiteralPartsToTemplateLiteral + isValidTypeForTemplateLiteralPlaceholder), and inference uses the same matching (`infer_to_template()` in infer.c, which also turns a matched `"12"` into `12` for `infer N extends number`). Template literal *expressions* are template types in a const context, an element access index or with a string-literal/template contextual type, and constant ones fold to a string literal through the enum evaluator (`ty_evaluate_string()`).
- **Conditional instantiation keeps a conditional type's own `infer` parameters out of the mapper** (`without_own_infers()`, the list per root recorded at lowering, `ty_conditional_own_infers()`): a recursive `Split<B, D>` in the true branch of `Split` must not see the outer `infer B`'s result in its own extends type. A missing inference or one that violates the `infer X extends C` constraint is the constraint (tsc's getInferredType). Without `extends`, an `infer X` has an implied constraint from where it is written (`ty_implied_infer_constraint()`, tsc's getInferredTypeParameterConstraint, from `InferredType.position` recorded when the scope declares it): the constraint of the type parameter of `Foo<infer X>` instantiated with the reference's arguments, `unknown[]` in rest positions, `string` in a template placeholder, `keyof any` as a mapped type's key type; the intersection of them over several `infer X` of one name.
- **Tuples are normalized when referenced** (`normalized_tuple()` in checker.c, tsc's createNormalizedTupleType): a spread of a tuple is spliced in, of a union distributes, and everything from the first rest element to the last optional or rest element becomes one rest element. A rest element's argument is the spread type as written (`...T[]` keeps `T[]`).
- `lower.c`: `ty_from_node()` is the only producer of `Ty` from syntax; the symbol entry points are described above. Anonymous object types are keyed by the *address* of their node, which is stable because nodes belong to the AST.
- **Alias names**: unions, intersections, object types, arrays/tuples (as deferred references), `T[K]` and conditional types written as the body of an alias carry `Ty.alias` + `alias_args`, instantiation instantiates the arguments, and `ty_realias()` renames the instantiation of a generic alias that is itself the body of another alias (`type Bar = Omit<Foo, "c">` prints as `Bar`). A homomorphic mapped type instantiated with an array or tuple becomes an array or tuple (`instantiate_mapped_over_list()`).
- `ty_display.c` prints like tsc's `typeToString()`: alias name, else reference name + arguments (`T[]`, tuple syntax), else declared name, else structure.
- **Types baseline node reuse and underlines** (`^^^` under each printed type: which parts tsc's node builder synthesised vs reused from the source). `TyDisplay.underline` collects one character per UTF-16 unit printed, a space while `TyDisplay.reused` is set. Where tsc's `serializeTypeForDeclaration` reuses a declaration's annotation (signature parameters, `this`, return types and predicates, type parameter constraints, property annotations, object literal accessors and `as T`), `display_annotated()` checks that the annotation's type is the printed one (optional: without `undefined`) and then `display_node()` prints *the TypeNode*, as written, with tsc's printer layout (`TypeNode.parenthesized` keeps written parentheses). A part whose first name isn't accessible from `enclosing` (`name_accessible()`) prints its type instead, per node like tsc's recovery. Functions without a return annotation look at their single `return` (`single_return_expr()`, tsc's typeFromSingleReturnExpression): `as T` reuses `T`, a function expression is printed with its parameter declarations reused (`TyDisplay.syntactic_function`) unless the resolve walk found it inside a call or annotated initializer (`FunctionImpl.syntactically_contextual`). Error messages never reuse (no `enclosing`). The harness (`add_type_rendered`, `LineNumberedStr.any_underline_at`) drops the underline of `any` when tsc's baseline has no errors, except where tsc's harness keeps it (`BaselineTestCase.any_keeps_underline`: property access/qualified name parts, binding elements, labels, import/export names).
- The `.types`/`.symbols` test traversal (`src/test/baseline_test_traversal.c`) prints `Ty`s with `TyDisplay.unqualified_names`; the one exception is a declaration whose type is a written type *name*, which prints as written (see `hacks.md`).

### Control flow (`flow.h`/`flow.c`, `ty/flow.c`)
The model is tsc's, because the `.types` baseline prints the narrowed type of every reference: a graph of `FlowNode`s built at bind time, which the checker walks *backwards* from a reference (`ty_flow_type()`, below).
- **Nodes**: start, branch label, loop label (antecedent lists; the first antecedent of a loop label is the way in), assignment (`FlowAssign`: which declaration / `=` / `++` / for-of / element of a destructuring assignment, the latter with the recorded `FlowPatternPath` down the pattern since there are no parent pointers), true/false condition (only for expressions that can narrow: `expr_is_narrowing()`; a `true`/`false` literal makes the other branch unreachable), switch clause (`[start, end)`; the empty range is "no clause matched" of a switch without `default`), call (a call statement with a dotted-name callee: maybe an assertion or a `never` call, the checker decides) and reduce label (try/finally). `FLOW_SHARED` marks nodes with more than one successor. Nodes live in the binder's arena and are read-only after resolve; one static `flow_unreachable` node stands for dead code.
- **Who points at it**: `IdentifierExpr.flow` (also `this`/`super`), `PropertyExpr.flow`, `FunctionImpl.outer_flow` (function expressions, arrows, object literal methods: their start node says narrowing may continue outside), `FunctionImpl.end_flow` (non-null: control can fall off the end) and `return_flow` (constructors). References in unreachable code have no flow node, like in tsc.
- **The builder** (`FlowBuilder`) is tsc's binder state (`current`, break/continue/return/exception targets, active labels, `has_flow_effects`), one per flow container (file, namespace body, function, class field initializer, static block) on the stack of whoever walks the container and reached through `Scope.flow`. What tsc finds through parent pointers is handed *down* instead: whoever walks an expression as a condition sets `true_target`/`false_target` first (`expr_lookup_names_condition()`), as an assignment target `assignment_target`, as the object of an optional chain `chain_continues`, and `expr_lookup_names()` takes them on entry so they never leak into operands. A non-async, non-generator IIFE is part of the surrounding flow. Inside an unreachable statement the builder is `dead`: nothing changes `current`.
- **Assignments are marked during the same walk**: `IdentifierExpr`/`PropertyExpr.assignment_target` (definite or compound: such a reference has its declared type), and on *local* variable symbols `is_assigned`, `is_assigned_in_closure` and `last_assignment_end` (tsc's `lastAssignmentPos`: the end of the outermost statement around the assignment that starts after the declaration), which is what narrowing inside closures will ask.
- **Reachability**: the builder reports TS7027 at the first statement of unreachable code (runs of statements in a block; only when `allowUnreachableCode` is explicitly `false`, otherwise it's an editor suggestion) and TS7028. What needs types is the checker's: `ty_flow_reachability()` is `isReachableFlowNode` (a call statement whose callee is *declared* to return `never` or asserts something false, the "no case matched" edge of an exhaustive switch: `is_exhaustive_switch()`), and the statements tsc gives a flow node have one too (`Statement.flow`), so `statement_typecheck()` reports TS7027 for code after `fail()`. Its other consumers: `never` for function expressions that can't return, `| undefined` in inferred return types, TS2355/TS2366/TS7030/TS2534/TS2378.
- **Narrowing** (`ty/flow.c`, a port of tsc's `getFlowTypeOfReference()`; what is still missing is listed in `agents/hacks.md`): `ty_flow_type(reference, declared, initial, flow)` walks back from the reference's flow node. A matching assignment gives the declared type reduced by what was assigned (a prefix of the reference, `x = ...` while asking about `x.y`, resets to declared); a condition narrows if its expression is about the reference (truthiness, `===`/`!==` with anything, `typeof`, `instanceof`, `in`, calls of type predicates, comparisons with `true`/`false`, `??`/`?.` conditions marked `FLOW_NULLISH`, optional chain containment; and if it is about a *discriminant property* of the reference, `x.kind === "a"`, the members of the union whose property could be what is left: `discriminant_access()` / `narrow_by_discriminant()`; a union of 10+ objects with a unit-typed *key property* maps its values to members once, tsc's getKeyPropertyName: `ty_union_key_property()` / `ty_union_member_for_key()`, which `===`, `switch`, predicate narrowing and relations to the union look up first), all through one table of **type facts** (`type_facts()`, tsc's `TypeFacts` bit for bit, strict and non-strict) that `&&`, `||`, `??` and `!` in `ty/expr.c` use too; switch clause nodes narrow by their cases (by value, `switch (typeof x)`, `switch (true)`, discriminant); call nodes narrow by assertion signatures (`asserts x`, `asserts x is T`) and answer the *unreachable never* (`TY_UNREACHABLE_NEVER`, which a top-level query turns into the declared type) after a `never` call; branch labels union their antecedents (the bypass edge of a switch last, and only if the switch isn't exhaustive); loop labels iterate to a fixpoint (`Checker.flow_loops` is the stack of loops in progress, a loop met again through its back edge answers the *incomplete* union so far, finished loops are cached by `(label, reference key)`, keys are interned from symbol + property names + declared/initial type); `FLOW_SHARED` nodes are remembered for the rest of one query; a start node of a function expression continues in the flow the function was made in for `const`s, and for parameters and `let`s past their last assignment (`Symbol.last_assignment_end`). The hooks are `identifier_flow_type()` (the tail of tsc's `checkIdentifier()`: only variables and parameters, assignment targets keep the declared type, the initial type is `declared | undefined` unless something says the variable is initialized, and an `undefined` that survives is TS2454, reported by `identifier_expr_typecheck()`) and `access_flow_type()` for property and element access.
- **Expression memos vs loops**: the engine asks for expression types (what was assigned, what `x ===` is compared with) through `ty_flow_expr_type()`: a finished memo, else an evaluation in *uncached mode* (`Checker.flow_uncached`: `ty_expr_type()`/`check_with()` neither read unfinished memos nor store anything, all the way down), because `x = f(x)` in a loop asks for `x`, which asks the loop, which asks for the type of `f(x)` while it is being evaluated further up the stack, with an incomplete `x`. Its results are cached like tsc's `flowTypeCache`: for good when no loop is in progress, else for the walk of one back edge. Declarations (every non-expression `LazyType`, inferred return types) evaluate self-contained instead (`ty_flow_isolate()`: not uncached, no loop in progress as far as they can see), so what they remember is complete, and a declaration that depends on itself through a loop (`while (c) { const y = x; x = y + 1; }`) is circular like in tsc. `e as T` doesn't evaluate `e` for its type (tsc defers it too); the statement walk checks it with `T` as the contextual type.
- **Type predicates** are syntax on the function (`FunctionImpl.predicate`, a `TypePredicateNode`; `ret` stays `boolean` / `void`, so everything about return types is unaware), resolved against the parameter list in the resolve walk, and `TyPredicate` on the signature (`signature_predicate()`: lowered or instantiated on demand, never inferring a return type). They are displayed, related (a predicate target wants the same predicate) and inferred through. What a *call* means for control flow is `call_effects()` in `ty/flow.c` (tsc's `getEffectsSignature()`, remembered per call): the callee of a call statement is typed from declarations alone (`type_of_dotted_name()`: every name needs an explicit type, no flow analysis, which is what keeps `assert(x)` from asking for itself), one non-generic signature is taken as is, anything else is resolved by `ty_call_effects()` (`call.c`) in uncached mode. `narrowed_type()` is tsc's `getNarrowedType()` for predicates and `instanceof` (the latter by class derivation: `ty_has_base_type()`).
- **Property access checks** (`check_access()` in `ty/check.c`, reached from `expr_typecheck()`): a possibly `null`/`undefined` object is TS18047-18049 (the object is an entity name, `expr_is_entity_name()`) or TS2531-2533, an `unknown` one TS18046/TS2571, and a property that `ty_access()` doesn't find on the *whole* object type (every member of a union, any member of an intersection) is TS2339, with the first union member that lacks it as elaboration. This only became reportable once narrowing existed; the gates that remain (JS files, callables, generic mapped types, classes whose base can't be resolved) are in `agents/hacks.md`.
- **Member modifiers** (`ty_check_member_modifiers()` in `ty/check.c`, tsc's checkPropertyAccessibility and isAssignmentToReadonlyEntity): class members carry `PROP_PRIVATE`/`PROP_PROTECTED`/`PROP_STATIC`/`PROP_ACCESSOR`/`PROP_FIELD` (an accessor's writes go by its setter's `PROP_SET_*`), which mapped types and spreads drop. `member_refs()` finds the property on every member of a union/intersection (tsc's synthetic property: readonly if any union member's / every intersection member's is) without making types. Where the access is comes from the resolve walk: `PropertyExpr.enclosing_class` (then `ClassDecl.outer_class`, from `scope_enclosing_class()`), `in_constructor_of` (the flow container is that class's constructor, IIFEs inlined: `FlowBuilder.constructor_of`) and the `this` parameter / contextual-`this` function. A readonly assignment target's type is the error type (`ty_is_readonly_assignment()` in `ty/expr.c`), like `new` of an inaccessible constructor (`ty_constructor_accessible()`, TS2673/2674). A union whose members declare a private/protected property differently has no such property (`ty_union_non_public_conflict()` in access.c). `super.x` is typed (`super_type()` in ty/expr.c: the base instance with `this` as this-argument, in a static member the base constructor); where tsc says `super` is illegal (`Scope.no_super`: computed names, member decorators, constructor parameters; `super()` outside a constructor) it is `any`. `super(...)` resolves against the base constructor (with the heritage clause's type arguments) and is `void`. Where `super` may be used is decided while resolving (`resolve_super()` in expr.c, tsc's getSuperContainer/isLegalUsageOfSuperExpression over scopes, `Scope.no_super` says why a computed name, decorator or constructor parameter is special), as is `this`/`super.x` before `super()` (`check_before_super()`: `flow_is_post_super()` walks the flow graph built so far backwards, tsc's isPostSuperFlowNode). `FunctionImpl.first_super_call` is for TS2377/TS17005. Relations are nominal for non-public properties (`modifiers_related()` in relate.c, tsc's propertyRelatedTo: a private property only relates to its own root declaration, a protected one to one declared in a derived class), and an intersection with separately declared same-named properties, one private, is `never` (`has_conflicting_private()` in checker.c). Two copies of the same package version resolve to the first (`ResolvedModule.package_id`, `Program.files_by_package_id`), so their classes are the same.
- **Private names**: `#x` declared in a class is a name of its own per class, like tsc's `__#12@#x`: `ty_private_name()` makes an `Atom` with the text `#x` that isn't the interned one (keyed by the class symbol), so props are told apart by pointer as always and still print as `#x` (`ty_private_name_class()` goes back; `keyof` skips them, a static one isn't inherited). The resolve walk finds the innermost enclosing class that declares an accessed `#x` (`PropertyExpr.private_class`, `PrivateNameExpr` for `#x in o`); `ty_access_key_type()` is the key an access looks up. TS18013/18014/18016/2803 come from `ty_check_private_name_access()`, TS18028 from `class_decl_typecheck`.
- `TTTT_DUMP_FLOW=1` prints every container's graph in creation order with the references that got each node: start here when narrowing looks wrong.

### Engine
tttt includes a JavaScript interpreter that evaluates an AST. It's not fast, standards complaint, tested, complete, or a priority.

## Phases
The process of loading and typechecking TypeScript code is done in several phases

### Load from the filesystem
Cleat's `Fs` abstraction allows tests to mock the filesystem, so the `Program` sees multiple files without the test runner having to write them to disk. The mock lives in [src/test/mock_fs.c](src/test/mock_fs.c); everything else uses the `fs` global.

### Parse
The parser creates an AST from the source code string, see below.

### Resolve names
`program_resolve_names()`, three steps over all files. This is also the intended parallelism contract: declare and resolve are meant to run per file, writing only to the file's own AST and symbols, with the small sequential link step in between being the only one that touches what files share (`agents/hacks.md`, "Parallelism contract audit", lists what still breaks that: globals, ambient modules, the one binder arena).
1. **Declare** (`*_add_names()`): every file gets its scope (a module also its module symbol), and the declarations of files, namespaces, enums and `declare global` blocks become symbols. Same-table conflicts are reported here.
2. **Link** (`binder_link()`): `export *` tables are flattened and every alias is resolved, so that nothing writes to a symbol afterwards; import conflicts (TS2440) are reported.
3. **Resolve** (`*_lookup_names()`): the deep walk. It makes the function and block scopes as it enters them (declaring their names first, so uses before the declaration resolve) and stores on every identifier the symbol it found plus the symbol that has the meaning it is used with (`target`). The same walk builds the control flow graph, so it visits statements and expressions **in evaluation order** (`for`: init, condition, body, afterthought; an IIFE's arguments before its body), see "Control flow" below.

Imported files are discovered while loading, from the parser's list of module names (`SourceFile.module_refs`; `program_handle_statement()` only follows `/// <reference>` directives and decides whether a file is a module), before any of this. Between declare and link every `ModuleRef` is resolved to its module symbol, which needs the ambient modules of all files.

### Module resolution
`src/module_resolution.{h,c}` is tsc's `moduleNameResolver.ts`: a **pure function of (filesystem, options, containing file, name, mode)** that knows nothing of programs, syntax or symbols. `module_resolver_resolve()` tries `paths` / `baseUrl` / `rootDirs` first, then by `moduleResolution`: classic (next to the importing file and each ancestor, then `node_modules/@types`), node10 (file with extension probing and `.js` -> `.ts` substitution, directory through package.json `typings`/`types`/`main` and `typesVersions`, `node_modules` walking up with TypeScript before JavaScript, `@types` with `@scope/x` as `scope__x`), node16/nodenext/bundler (package.json `exports` / `imports` with conditions and patterns, self names, `.mts`/`.cts`, no extension or index probing for ESM imports). `moduleSuffixes`, `resolveJsonModule`, arbitrary extensions (`a.d.css.ts`) and symlinks (a `RealpathFn` the program is given: libc's in the CLI, the mock filesystem's in tests; applied to what is found in node_modules, unless `preserveSymlinks`) are in there too. `module_resolver_resolve_type_reference()` is `/// <reference types>` and the `types` option (type roots first, then node_modules), `module_resolver_automatic_types()` lists what is included without being asked for, `module_resolver_file_format()` says whether node16 takes a file for an ES module. The result carries *why* it failed where tsc has a message for that. The only state is a package.json cache by directory (`src/json.{h,c}`: a small JSONC reader with ordered members, because the order of `exports` conditions matters) and a cache of results by (containing directory, mode, name), like tsc's per-directory resolution cache: nothing a resolution looks at depends on the file within the directory, and the filesystem and options don't change while a program loads.

`program.c` is the one caller: `program_load_module_ref()` resolves every `ModuleRef` of a loaded file in the mode its syntax asks for (`ModuleRef.syntax`: `import x = require()` is always CommonJS, `import()` always ESM, anything else the format of the file), adds TypeScript results to the program and records anything else on the ref (`ModuleRef.failure`: JavaScript without `allowJs` or from a package, `.tsx` without `jsx`...). A `.json` result (resolveJsonModule) is loaded as a source file too (`SourceFile.is_json`): the parser makes its one expression an `export =` statement. `import * as ns` of an `export =` module gets tsc's interop shapes in `namespace_import_type()` (lower.c: a synthetic `default`, or only the default for an ES module importing JSON). Diagnostics are reported from the ref when names are resolved, not while loading (`module_ref_report_unresolved()`: TS2307, TS2792 for classic, TS7016, TS2732, TS2834/TS2835, TS6142, TS6263; `module_ref_report_resolved()`: TS5097, TS1479/TS1471), so an unresolved import is no reason not to typecheck. `program_load_automatic_types()` adds the `@types` packages after the roots. With `noResolve` nothing is added, but names still find files that are roots.

`src/tsconfig.{h,c}` reads a tsconfig.json: `extends` (paths and packages), `compilerOptions` (path options made absolute, `${configDir}`), and the root files from `files` / `include` / `exclude` (the walk only enters directories an include pattern can match something inside, `glob_may_match_inside()`). The CLI takes `-p`, or finds the nearest tsconfig.json when it is given no files; the test harness applies a `tsconfig.json` unit under the test's directives and takes its files as the roots, like tsc's `compilerRunner.ts`. The harness also mirrors tsc's virtual filesystem: relative `@Filename`s live in `/.src`, which is the working directory (`@currentDirectory` changes it), `@link` / `@symlink` make symlinks in the mock filesystem.

### Typecheck
The AST is now in it's finished state, so we can traverse it looking for type errors. This is the phase when the `*_evaluate_type()` functions are called (via `ty_from_node()` / `ty_expr_type()` -> `lazy_type_get()` -> `lazy_type_evaluate()` -> `*_evaluate_type()`), each returning a `Ty const*`. Before the walk, `ty_init_global_types()` creates the global types tsc's
initializeTypeChecker creates (Array, Object, Function, String, ..., RegExp) in tsc's order: type ids decide the order
of printed union members, so creation order is part of the output.

## Memory Management
The source code and ASTs of all parsed files is kept valid until after all above phases have finished. The AST holds references to the code (via spans) and any types created from the AST may hold references into the AST, so it would not be safe to free either the code or the AST while anything created from it remains in use. Furthermore the AST should not be structurally modified after parsing to keep pointers valid (ex pushing to a vec that's part of the AST is generally unsafe, since it may trigger a reallocation and invalidate other elements).

### Types
`TypeNode`s are owned by the AST. `Ty`s, their members, signatures, mappers and everything else the checker makes live in the arena of their `Checker` and are freed with it; nothing in the type core is individually freed or reference counted. `program_drop()` drops the checker before the AST, because types point into the AST.

A function type or signature written as a type (`TYPE_CALLABLE`) is a `CallableType { FunctionImpl* }`: a `FunctionImpl` without a body and with `is_type` set, so there is one way to resolve a signature (`signature_resolve()` reads parameters and return type off the `FunctionImpl`, `is_type` only decides how they're lowered). A node that declares a symbol (`GenericItem`, `InferredType`, a mapped key) has both `owned_symbol` and `symbol_ref`, a leftover from when nodes were cloned.

### Declarations
In TypeScript multiple declarations in the source code can contribute to a single logical declaration (this is known as declaration merging). `scope_init_declaration()` hands back the `Symbol` the declaration ended up in: a fresh one, an existing one it merged with (the declaration is appended to `Symbol.decls`), or a detached one when merging was an error. Symbols belong to the `Binder` and live as long as the program; AST nodes don't own them.

## Parsing
As mentioned above the parsing framework is custom, but it should be fairly straightforward.

### Parser struct
Each parse function (generally) creates it's own instance of `Parser` named `p`. This stores a current position in the source code, a pointer to the parser one level up (it's "parent") and some other things.

Each perse function receives a pointer to it's parent parser as an argument, as well as a pointer to an instance of the data structure it will attempt to populate, called `ret`. It returns a bool:
- `parse_success(&p)` - the function successfully parsed it's thing, `ret` is populated, the parent's current position is updated to match `p`'s position and any errors added to this parser or children **are** added to the parent
- `parse_fail(&p)` - the function did not parse it's thing, `ret` is undefined (could be unchanged, could be 0s, could be junk data, does **not** need to be dropped), the parent's position is not changed and any errors added to this parser or children are dropped (**not** added to parent)

`parse_success()` **always** returns true and `parse_fail()` **always** returns false. This makes it easy to return the correct value along with calling the corresponding parser cleanup function. It's **almost always** incorrect for these not to match up 1:1. The exceptions are simple low-level parse functions that avoid creating their own parser instances for performance, and a couple places where child parsers are created in the same function as their parents.

Note that a parser can succeed without errors, succeed with one or more errors or fail without errors. It **cannot** fail with errors (any errors added are silently dropped on fail). The idea is a parser either parsed something and advanced the current position (success) or did not (failure). Errors are only relevant when a parser parsed something, and understood a way that thing is wrong.

### Tokens
Because there are no tokens, `/` needs no rescanning: `parse_expr()` is only ever called where an expression may start, so a `/` there is a regular expression literal (`parse_regex()`, `EXPR_REGEX`), and anywhere else it's a division.

Unlike other typescript/javascript parsers, tttt doesn't tokenize before parsing. Sometimes tokens are needed though (such as when an error message for an unexpected token is to be added), which is what `hop_token()` is for. It's not called for most code.

### Anchors
Anchors are helpful for making spans. They are created with `anchor(&p)`. `span_from(a)` creates a span from the parser's position when the anchor was created to the parser's current position.

### Error recovery
Recovery follows tsc's parser rules without its tokens (plan 27):
- `parse_error()` drops an error that starts where the previous one does (tsc's parseErrorAtPosition), and an error at
  a character no token starts with (`invalid_char_size()`) becomes TS1127, which tsc's scanner would have reported
  first. `ParserShared.errors_attempted` counts the calls, dropped ones too, for code that asks "did that parse with
  errors".
- Lists. `ParserShared.parsing_context` is tsc's ParsingContext mask, a bit per list being parsed (`list_enter()` /
  `list_leave()`; statements, class/type/enum/object literal members, switch clauses, parameters, arguments, array
  literals, variable declarations so far). When a list's element can't be parsed, `list_abort_or_skip()` reports the
  list's error (tsc's parsingContextErrors) and ends the list if the token terminates it or starts an element or
  terminator of any enclosing list, else skips one token. One deviation: a token that starts an element of the list
  itself is skipped, since tsc's element parser would have consumed it. Delimited lists report a missing `,` and go
  on. The mask only matters when recovering, so the fail cache ignores it (a position that failed under one mask is
  only replayed under another in invalid code).
- The element and terminator predicates are tsc's `isStartOf*` lookaheads over `Tok`s (`tok_peek()`, `tok_next()`,
  `tok_scan_end()`: a cheap scanner, no values). They run only once an element parser failed or parsed with errors
  (`parse_list_member()`), never on valid code's path.
- Commit points: where tsc stops speculating, the tttt function succeeds with errors instead of failing:
  `arrow_function_tristate()` (tsc's isParenthesizedArrowFunctionExpression) in front of arrow functions, parameter
  lists after their `(` (`commit_on_paren`), property names after a `.`, `[]` (TS1011), object literal members
  after their name or `*`, parenthesized expressions, a binary operator where an expression should start (a missing
  left operand). A missing name is an empty span, which the symbols baseline prints as `(Missing)`.
- Grammar errors the parser reports for tsc's checker (`is_grammar_code()`: modifiers, TS1162...) don't count as parse
  errors and are dropped in a file that has parse errors, like tsc's grammarErrorOnNode.
- Modifiers are parsed wherever tsc's parseModifiers takes them (declarations, members, parameters, object literal
  members, in front of import/export statements) and checked once the node's kind is known by
  `modifier_list_check_grammar()` (modifier_list.c, tsc's checkGrammarModifiers): the caller says what the node is
  (`ModifiedKind`) and where (`ModifiedParent`, ambient or not; `ParserShared.in_ambient`/`statement_parent` track it).

### Whitespace
`hop_whitespace(&p)` needs to be called anywhere whitespace may appear.

Performance: the parser tries alternatives, so what a failed attempt costs is what parsing costs. The dispatchers (`parse_statement()`, `parse_expr()`, `parse_expr_right_side()`, `parse_type()`) test the first character before trying a branch that can only start with some, and keyword probes (`hop_start_if_ends_on_word_break()`) compare in place without a child parser. A new branch should get its first-character test too.

Newlines are generally ignored but change how js/ts are parsed in some cases. For this reason parsers keep track of if the last whitespace they hopped contained a newline. This gets propagated to the parent on success.

### JSX
In a JSX file (`SourceFile.is_jsx`: `.tsx` and JavaScript files, tsc's `LanguageVariant.JSX`) a `<` where an expression starts, followed by a name or `>`, is an element (`parse_jsx_element()`, tsc's parseJsxElementOrSelfClosingElementOrFragment), never a type assertion, and a generic arrow function has to be written `<T,>` or `<T extends X>` (`jsx_generic_arrow_start()`). There's no scanner mode: text between tags is read straight from the source, where `//` isn't a comment and `'` isn't a string. The AST is one `JsxElement` for `EXPR_JSX_ELEMENT` and `EXPR_JSX_FRAGMENT` (tag name as an identifier / `this` / property access expression, type arguments, attributes as one `EXPR_JSX_ATTRIBUTES` expression, children, the closing tag's name). Error recovery follows tsc's: a child that swallowed its parent's closing tag gives it back, `<a/><b/>` where one element is expected is a comma expression with TS2657, and only the first error at a position counts (see Error recovery). Value tags (`<Comp>`, `<this.x>`) are references in the resolve walk; intrinsic ones (`<div>`, `<my-elem>`, `<a:b>`, `jsx_element_is_intrinsic()`) aren't.

The factory is resolved in the resolve walk (`jsx_lookup_factory()` in expr.c). A file whose JSX imports its factory implicitly (react-jsx/react-jsxdev, `jsxImportSource`, `@jsxImportSource`/`@jsxRuntime` pragmas: `source_file_jsx_runtime_import()`) has a synthetic `SourceFile.jsx_runtime_ref` (`react/jsx-runtime`), loaded like an import in modules and JS files and `ambient_only` in scripts, like tsc's synthesized import. When that module exists it is `JsxElement.runtime_module`, whose `JSX` is the JSX namespace (`ty_jsx_namespace()`), and nothing else is referenced; when it doesn't, the file's first element gets TS2875 (TS2792 under classic resolution). Otherwise every element references the factory's first name (`React` of `React.createElement`: TS2874, or TS2552 for a misspelling, under `jsx: react`), fragments the fragment factory too (TS2879 once per file, TS17016/TS17017 without one). The factory options and pragmas are validated like tsc's (`compiler_option_is_entity_name()`): an invalid one counts as not given.

### JSDoc (JavaScript files)
`hop_comment()` records every `/** */` comment of a JavaScript file (`ParserShared.jsdoc_comments`, sorted, backtracking-safe). Whoever parses a JSDoc host (a statement, class member, object literal member, parameter, parenthesized expression) calls `jsdoc_before()` with the host's first token: the comment that ends right before it (only whitespace between) is parsed into `JsDocTag`s (tsc's parseJSDocCommentWorker rules for where a tag starts; tags after `@callback`/`@typedef` are theirs, `nested`). A tag's `{T}` is parsed by the type parser pointed into the comment with `ParserShared.in_jsdoc` set: `hop_whitespace` skips a line's leading `*`, and the JSDoc-only forms parse (`*`, `?`, `?T`/`T?` as `T | null`, `!T`, `T=` as a `jsdoc_optional` union with `undefined`, `...T`, `Array.<T>`, `function(this: T, new: C, ...)` with tsc's `argN` names). JSDoc isn't stored: the host moves what the tags say into its own slots right away (`@type` -> a single variable declaration's or a class property's `explicit_type`, `@param`/`@returns` -> a function's parameters and return type, found through the host tsc's getNextJSDocCommentLocation walks up to; `@type {(a) => R}` -> a function's signature; `/** @type {T} */ (x)` -> an `EXPR_AS_TYPE`, `@satisfies` a satisfies expression), marked `from_jsdoc` (the baseline walk skips them). More slots of that kind: `@template` -> a function's, class's or class expression's `Generic` (`GenericItem.jsdoc`), `@returns {x is T}` -> the predicate, `@type` on an object literal property/method -> `ObjectExprItem.jsdoc_type` (declared and contextual type of the value), on an assignment -> `BinaryOpExpr.jsdoc_type` (handed to the `SymbolDecl` it declares, `SymbolDecl.jsdoc_type`: the declared type of `this.x`/`exports.x`/`module.exports`), a non-literal `@type {F}` on a function -> `FunctionImpl.jsdoc_signature_type` (applied by the checker as the function's contextual signature, `ty_function_apply_jsdoc_type()`), nested `@param {Object} o` + `@param {T} o.a` -> a type literal. Function and arrow function expressions are hosts of their own. JSDoc names (`String`, `Object`, `array`...) resolve by tsc's getIntendedTypeFromJSDocTypeReference (`IdentifierType.jsdoc_intrinsic`), a value name means its type (a variable or assignment declaration whose value is a class expression or constructor function is its instance type, tsc's getExpandoSymbol), `import("./m")` a value-or-type; a name not in scope in a prototype method (`F.prototype.m = function`, `F.prototype = { m() {} }`: `FunctionImpl.prototype_of`) is looked up in F's type parameters (`jsdoc_prototype_type_param()`, tsc's getAssignmentDeclarationLocation); unresolved names are TS2304 like in tsc. `@implements` tags are a JS class's implemented types, `@private`/`@protected`/`@readonly` its members' modifiers (`jsdoc_modifiers()`; on `this.x = v` through `BinaryOpExpr.jsdoc_modifiers` -> `SymbolDecl.jsdoc_modifiers`), and `/** @type {T} */ a.b;` or `this.x;` declares the property (`Statement.expr_jsdoc_type`, tsc's isSpecialPropertyDeclaration).

TypeScript-only syntax in a JavaScript file (tsc's getJSSyntacticDiagnosticsForFile: TS8002-TS8017, TS8037) is reported by the parser where it parses each construct (`js_syntax_error()`: type annotations, type parameters, `?`, TS-only modifiers in `check_js_modifiers()`, interface/enum/namespace/type alias declarations, signatures, `implements`, `import =`, `export =`, type-only imports and exports, `!`, `as`, `satisfies`). They are syntactic diagnostics of their own (`is_js_syntax_code()`): not parse errors, never deduplicated against them, kept for unchecked files; what tsc's walk skips inside a reported construct is dropped again with `js_syntax_skip_since()`.

Declarations made by tags are synthesized statements. Each statement list (`parse_append_statement_sequence()`) claims the JSDoc comments inside its statements that no inner list claimed (`JsDocRange.claimed`, `jsdoc_bind_comments()`): tsc binds a typedef in the block scope of its host, which is the innermost list. `@typedef`/`@callback` become `STATEMENT_DECL_TYPE`s (`TypeDecl.jsdoc`: exported from a module's top level, tsc's jsdocTreatAsExported; `@typedef {Object}` + `@property` a literal, `@callback` + `@param`/`@returns` a signature, every `@template` of the comment the parameters), `@import` at the top level a type-only `STATEMENT_IMPORT_EXPORT` parsed by the import statement parser pointed into the comment (`PortStatement.jsdoc`: no module indicator, allowed in scripts, references to it aren't reused by the types printer), `@enum {T}` on `const E = {...}` a type alias named E (`TypeDecl.jsdoc_enum`, handed over through `ParserShared.jsdoc_enum`; members are checked against T). The baseline walk skips all of them; the symbols baseline's `Decl` of a tag is its `@`. A CommonJS module's typedefs are found next to its `export=` (tsc's getCommonJsExportEquals: named imports look in the module first, so does `import_type_lookup_names()`). Calls in JavaScript infer any where nothing is inferred (`Inference.any_default`).

### CommonJS (JavaScript files)
The parser notes `require(x)` calls (`IdentifierExpr.require_call` on the callee, a `MODULE_REF_REQUIRE` ModuleRef for a string literal) and assignments to `exports.x`/`module.exports` (`expr_commonjs_target()`); such a file without ES imports/exports is a module, `SourceFile.is_commonjs`. The declare step turns top-level `exports.x = v`/`module.exports.x = v` into exports (an alias for a name, else a `SYMBOL_DECL_ASSIGNMENT` value) and `module.exports = v` into `export=` (`scope_add_commonjs_export()`, `binary_commonjs_declaration()` is the shared test, `void 0` declares nothing). `module` is a local `SYMBOL_DECL_COMMONJS_MODULE` symbol typed `{ exports: ... }` (`ty_commonjs_module_object()`), `exports` is the module symbol (before the globals, like tsc), `require` in a require call is the binder's `require_symbol` (any) and the call has the module's type. `const x = require("m")`, `const { a } = require("m")`, `const a = require("m").a` declare aliases: the parser synthesizes `PortItem`s on the `InitializedBinding` (`require_ports`) and the declare step adds them with `scope_add_port()`. A declaring assignment has its target's type. `a.x = v` is an export too when `a` is a module variable initialized with `module.exports`/`exports` (`is_exports_alias()`, tsc's isExportsOrModuleExportsOrAlias), and exports in blocks nested in the top level are declared with the others (`add_nested_commonjs_exports()`); `const a = require("m").b` is an alias whose initializer isn't checked.

### Assignment declarations: expandos and JavaScript classes
`f.x = v` declares a member x of f (an expando, tsc's bindSpecialPropertyAssignment) when f is a function declaration or a variable initialized with a function or arrow function, in JavaScript also a class, enum, namespace, class expression or `{}` (possibly defaulted, `var ns = ns || {}`), or a JavaScript member that is itself such a container (`ns.a = {}; ns.a.b = 1`). `scope_add_expandos()` runs at the end of `block_add_names()` over the block's expression statements (and `var` initializers), looks the entity name up in the block and then its function or file only (tsc's lookupSymbolForPropertyAccess), declares x in the host's `exports` as a `SYMBOL_DECL_ASSIGNMENT` and gives the host (and each name of `a.b` before it) a `SYMBOL_DECL_EXPANDO` declaration, shown in the symbols baseline only for top-level assignments. The expando declaration's value is the host's namespace type, so a function with expandos is `typeof f` like a function merged with a namespace; a variable's function initializer gets the members through `FunctionImpl.expando_host`, a class expression's static side through `ClassDecl.expando_host`, a `{}` container is the namespace type of its variable or member. A member's type is the union of what is assigned (`assignment_symbol_type()`, tsc's getWidenedTypeForAssignmentDeclaration: literals widened, object literals widened together). A top-level JavaScript `Outer.Inner = v` where the file doesn't declare `Outer` declares `Outer` (and each name before the property) as a global namespace merged with the global of that name (`global_expando_namespace()`, tsc's jsGlobalAugmentations; `binder_link_global_expandos()` gives variable initializers their members once every file is bound); one where `Outer` can't have expandos still gives it the namespace declaration the symbols baseline shows. In JavaScript files TS2339 is reported like in TypeScript, except on an object literal of a JavaScript file without noImplicitAny (`Ty.anonymous.js_literal`, tsc's isJSLiteralType).

In JavaScript, `this.x = v` in a class declares x in the class symbol's `members` table (`Symbol.members`, statics in `exports`), `F.prototype.x = v` (declare step) and `this.x = v` in a function or in `F.prototype.m = function` declare it for the constructor function F, which then has `SYMBOL_CLASS` (`scope_add_this_property()`, called by the resolve walk right after an assignment's target is resolved). So does `var self = this; self.x = v` (`expr_this_or_alias()`), and `this.x = v` in a function expression assigned to a declared property (`exports.F = function`) makes that property's symbol the class (`set_function_class_symbol()`). `F.prototype = {...}` makes a function F a class whose instance type has the literal's members, and `this` in the literal's methods is F's. A JS constructor function's `@template`s are its class's type parameters (`symbol_type_generic()`, `symbol_decl_js_function()`): its construct signature is generic. `SymbolDecl.assignment` says which kind of assignment declared a member, which the type needs: what a constructor assigns wins, method-only members may be undefined (or have the base class member's type), only-nullish is any; a constructor-declared `this.x = v` is any as a target in its constructor, and a class field without type or initializer has the constructor's type (`ClassItem.field.js_assigned`). In TypeScript under noImplicitAny such a field has the type `this.x` has at the end of the constructor (or of the first static block that assigns more than null/undefined), tsc's getFlowTypeInConstructor: `field_type_from_assignments()` queries the flow engine with the first `this.x =` target the resolve walk saw (`ClassItem.field.ts_assigned`) at `FunctionImpl.return_flow` / `ClassItem.static_block_return_flow`. Class instance types add the `members` the class body doesn't declare (`builder_add_assignment_members()`); a JavaScript constructor function (`ty_js_constructor_class()`) also gets a construct signature returning its instance type and prints as `typeof F`, and `this` in it or in its prototype's methods is the class's `this` (`ty_js_this_type()`). Untyped JavaScript functions (no JSDoc `@param`/`@type`) take any number of arguments (`FunctionImpl.jsdoc_typed`, min_args 0).

### Function context
Whether `await` and `yield` are operators or plain identifiers depends on the function being parsed. `ParserShared` keeps `in_async`, `in_generator` and `function_depth`; `function_ctx_enter()`/`function_ctx_leave()` wrap the parsing of every function's parameters and body (see `parse_non_arrow_function()` and `parse_arrow_function()`), and `FunctionFlags` carries `async`/`*` from whoever saw the keyword to the function parser. Since a source position is always inside the same function, this doesn't conflict with the fail cache. The parser tags each `await` expression and `for await` with where it is (`AwaitPlace`: allowed, in a non-async function, at the top level); the resolve walk reports what isn't allowed there (`await_check_grammar()`, shared with `await using`), since that needs the containing function (for TS1356) and the file's module status.

### Lexical level
There is no scanner, but the scanner's decisions live in a few helpers. A file's text is first made what tsc sees
(`text_decode()` at load: UTF-16 files decoded, invalid UTF-8 replaced by U+FFFD, which at a token start means a binary
file, TS1490). Identifiers are scanned by `identifier_char_size()`: the ASCII table, then tsc's unicode tables by target
(`unicode_identifiers.c`, generated by `unicode_identifiers.py`) and unicode escapes; the fast paths (`hop_whitespace`,
`hop_start_if_ends_on_word_break`, the identifier loop) are hot enough that any extra work in them shows in parse time.
Numbers are `scan_numeric_literal()` (tsc's scanNumber), strings/templates `parse_string_or_tagged()`/`parse_template()`
with `parse_string_escape()` (escape errors reported by `parse_error_in_literal()` unless in a tagged template), trivia
`hop_whitespace_slow()` (comments, conflict markers after a newline). A regex literal is only delimited by the parser
(`parse_regex()`, TS1161); its body and flags are checked by `regex_check.c` from the checker, like tsc's
checkGrammarRegularExpressionLiteral. Columns are UTF-16 code units (`span_col_index`, `utf8_byte_utf16_units()`).
### Fail cache
The fail cache is used to cache specific locations where specific parse functions have failed to parse before. There are some cases (such as arrow functions vs parenthesized expressions) where the correct way of parsing something is not obvious until after the parser has parsed some sub-expressions. If these cases are nested the time complexity of doing this naively is Not Good. However if you keep track of where you've tried and failed to parse specific things it's fine, so that's what we do. For details on precisely how it works you'll have to decipher the code.
